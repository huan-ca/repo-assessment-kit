**Scores**

- **Lay-user fit — 8.0/10.** The “careful senior consultant” thesis (§1), explicit unknown path (§2.2), business-consequence-first finding details (§4.4), and 4–7 page executive report (§12.2) fit operators and non-technical owners well. The setup still introduces “provider inference boundary,” overlays, egress, Lima, X25519, SHA-256, and snapshot digests before the design specifies contextual definitions or a novice-safe escalation path for each term.
- **Complete flow and off-paths — 6.5/10.** First launch, expired bootstrap, dirty source, blocked runtime, pause/cancel, recoverable failure, review correction, reconnect, packaging failure, deletion, and restore are all considered. However, recovery, validation issues, review inspection, empty source-handle state, large-list pagination, and post-review correction are not specified against retrievable contract data, and the wizard contradicts itself about when the durable `DRAFT` exists.
- **Visual and typographic craft — 8.5/10.** The fieldbook direction is distinctive without being theatrical; exact palette, spacing, elevation, motion, fluid type, line heights, measure, and print rules form a buildable system. The rust “evidence thread” (`#A94F35`) is visually too close to danger (`#A3342D`) while also representing objections, weakening §2.5’s promise to keep evidence, severity, and validation visually independent.
- **Evidence and limitation clarity — 9.0/10.** Six-state coverage without a false aggregate score, metadata-first evidence, explicit truncation, separate severity/priority/confidence/validation axes, reversal conditions, and the coverage-limitations report are excellent. The preview rules drift from the frozen contract by permitting WebP (§4.4), while the API and architecture permit only trusted re-encoded PNG/JPEG image previews.
- **Safety consent — 7.0/10.** Registered handles, no raw paths, exact egress exceptions, purpose/recipient-first secret upload, no reveal/copy, separate hosted-service approvals, and typed deletion confirmation are strong. But §4.2 Step 7 never specifies the deliberate affirmative control promised by §2.3 before target code is run, and choosing a provider radio card is treated as sufficient for crossing a provider inference boundary without a distinct acknowledgment of repository data disclosure.
- **Accessibility — 7.5/10.** Keyboard order, focus restoration, error summaries, live-region batching, semantic ledgers, 44 px targets, reduced motion, text-spacing, contrast, 400% reflow, and explicit QA paths are unusually concrete. Customer report HTML—the main artifact for the lay recipient—has no explicit language/title/landmark/skip-link/table-header/link-purpose/citation-backlink requirements; Linux is a first-class host but §10.5 has no Linux screen-reader test; and `ChoiceCard`’s “60% contrast” disabled treatment (§6.2) can contradict §10.3’s 4.5:1/3:1 requirements.
- **Responsive behavior — 9.0/10.** Breakpoints, container queries, 320 px support, per-screen reflow, dense-table transformations, safe-area handling, keyboard occlusion, long-identifier wrapping, and no page-level overflow are specified per screen rather than asserted generically. The phrase “400% reflow at 320 px” is ambiguous—WCAG reflow should be tested as a 320 CSS px equivalent viewport—and needs a canonical test setup.
- **Component specificity — 7.5/10.** The component catalog, interaction behavior, state contract, responsive variants, focus rules, and content patterns are enough to build most presentation logic consistently. It omits the equally important data adapters: no component-to-query/mutation mapping, no cursor pagination component/state, no route/URL state schema, and no DTO mapping for discovery conflicts, reviews, recovery plans, or package stages.
- **Implementability — 4.5/10.** The React/Tailwind/Radix implementation direction is clear, but several promised screens cannot be populated from the frozen architecture. `RunDetail` returns only `targetSnapshotId`, not the `TargetSnapshot` needed by §4.2/§3.2; there is no review-list operation for §4.6, no recovery-plan read operation for §4.3, no validation-issues read operation for §4.7, and `PackageView` exposes five coarse states rather than the nine stage rows and certificates required by `ReleaseLedger`.

**Overall**

**7.1/10** — weighted toward implementability and accessibility, per the review lens. The interaction and visual design are strong enough to preserve, but the contender does not clear a frozen-spec handoff because frontend engineers would have to invent or change multiple backend contracts.

**Strongest objection**

The core run workspace is not implementable from the frozen HTTP contract. The design requires a persistent target strip and a “Scope locked” card containing full commit SHA, snapshot mode/digest, dirty-path counts, submodule/LFS treatment, and integrity result (§3.2, §4.2), but `GET /api/v1/runs/{runId}` returns only `RunDocument.targetSnapshotId` and there is no target-snapshot read operation. The same gap repeats for the four-gate Reviews screen (no list-reviews operation), recovery-plan UI (the resume mutation requires a `recoveryPlanId` and attempt IDs but no operation returns them), validation issue ledger (no validation-report/issues operation), and nine-stage release ledger (`PackageView` has only `REQUESTED|STAGING|VALIDATING|VALIDATED|FAILED`). These are not polish omissions: they force the frontend lane either to fabricate state or to redesign the frozen architecture during implementation.

**Other findings**

1. **Must-fix — the wizard’s persistence lifecycle is internally contradictory.** The §4.2 flow places “Create run / save DRAFT” after all eight setup steps, while Step 1 says auto-save starts “only after the run can be created.” Yet Step 7 requires `PUT /runs/{runId}/approvals` and `POST /runs/{runId}/secrets`, both of which require an existing `DRAFT`. The spec must define the exact creation point, local-to-server transition, retry behavior, and what survives reload before source selection.
2. **Must-fix — target execution lacks a concrete consent control.** §2.3 says anything that “runs target code” requires deliberate confirmation, but Step 7 merely describes runtime as recommended when available and egress denied by default. A safe egress policy is not consent to execute an unknown repository. The affected action, scope, isolation boundary, residual risk, and denial outcome need a distinct approval control and durable receipt.
3. **Must-fix — review, recovery, and correction are prose flows rather than stateful UI contracts.** “Return to affected section” and “new input/revision behavior” (§4.6) do not define what is editable in `REVIEW_REQUIRED`, when `REVIEW_REQUIRED -> EXECUTING` occurs, how stale objections are shown, or which prior review remains attached. Recovery likewise has selected attempt IDs and a recommended plan without defining how that plan is loaded, expires, or changes after a row-version conflict.
4. **Must-fix — report accessibility is under-specified.** §10 is detailed for the authenticated app, but §12 treats the static report largely as a visual/print artifact. Require `lang`, unique titles, landmarks, skip link, hierarchical headings, table captions and scoped headers, descriptive evidence links, accessible citation labels/backlinks, meaningful image alternatives, and a keyboard/screen-reader acceptance path for the packaged `index.html`.
5. **Must-fix — discovery form behavior is not mapped to `ProductClaim`.** The conflict composer (§4.2) collects two viewpoints, but the frozen DTO requires a current claim, `conflictsWithClaimIds`, and supporting claim/evidence identities; exactly one current claim is allowed per topic. The spec also exposes only “Owner told us” and “Not yet verified” paths despite seven canonical provenance values. Without a mapping and server-ID lifecycle, frontend and API implementations will disagree.
6. **Should-fix — large assessment lists have no pagination interaction.** Findings and evidence APIs are cursor-paginated with a maximum page size of 200, while §4.4 and §9 specify filters and responsive rows but no load-more/pagination, loading continuation, result count, filter-reset, or focus behavior. Large repositories will appear silently incomplete.
7. **Should-fix — accessibility rules conflict at disabled controls.** `ChoiceCard` says disabled content “keeps 60% contrast” (§6.2), while §10.3 requires text and component contrast thresholds. Specify final token pairs and prohibit parent opacity so help/reason text remains readable; do not rely on a tooltip as the only disabled explanation.
8. **Should-fix — preview media rules drift.** §4.4 allows trusted WebP previews, whereas the frozen preview response and architecture boundary allow only re-encoded PNG/JPEG. Align the format list and define whether JSON/CSV are rendered from escaped text using trusted parsers or shown as plain text.
9. **Should-fix — the verification matrix omits assistive technology on a guaranteed host.** §10.5 makes NVDA testing depend on a Windows/WSL best-effort environment and tests VoiceOver only on macOS; add Orca + Firefox on Linux, or state a supported remote/browser test configuration that is a release requirement rather than best effort.
10. **Nice-to-have — separate evidence identity from objection/error color.** The recurring rust thread is used for citations and objections and sits close to danger red. Use a neutral or blue evidence-thread token and reserve rust/red for objections and destructive/risk semantics, preserving the otherwise strong multi-axis encoding.

**Concrete fixes**

1. Add a design-to-OpenAPI matrix for every screen and action. Either add frozen read models/operations for target snapshot, reviews, recovery plan, validation report/issues, package-stage certificates, and optional-service descriptors, or explicitly remove/replace UI that cannot be backed by the existing contract.
2. Freeze wizard persistence: create the run immediately after minimum source/engagement fields are valid, define when the local draft becomes server-backed, auto-save discovery and approvals with row-version handling, and specify reload/retry behavior. Keep secret creation impossible until the durable run and approval exist.
3. Add explicit, separate consent controls for provider data disclosure, target-code execution, each egress exception, each hosted service, and each credential recipient. For runtime consent, show scope, isolation, residual risk, effective egress, and the static-only result of denial.
4. Define exact correction and recovery state machines in the UI: retrieval payload, plan/version identity, editable fields, stale-plan handling, transition triggers, attempt selection semantics, review supersession, and how objections remain visible across revisions.
5. Add report-specific WCAG 2.2 AA requirements and tests, including semantic tables/citations and screen-reader testing of the extracted offline package. Resolve the disabled-opacity conflict and add a first-class Linux screen-reader run.
6. Specify `DiscoveryPrompt` serialization for all allowed provenance values, unknowns, and conflicts, including temporary IDs, server-assigned IDs, evidence links, validation errors, and the exactly-one-current-claim invariant.
7. Add a reusable cursor-pagination pattern with result continuation, focus retention, filter URL state, empty-after-filter state, and honest “showing N loaded” language.
8. Remove WebP from safe preview output unless the architecture contract is revised; define a single allowlist and parser/rendering path shared by design, OpenAPI, and QA.

**Verdict**

**revise** — the contender clears the lay-user, visual-craft, evidence-honesty, and responsive-design bars, but misses the implementability and complete-accessibility bars. It should not be handed to frontend implementation until the missing read models, wizard lifecycle, runtime consent, and packaged-report accessibility contract are resolved.
