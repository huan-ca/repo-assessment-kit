## Scores

- **Lay comprehension — 8.2/10.** §§1–2, 4.6–4.10, and 12 consistently lead with consequence, separate confidence from severity, avoid an aggregate health score, and keep reversal conditions visible. The remaining operator-facing language—“Resolve immutable target,” “fenced attempt,” “snapshot digest,” and “SSE”—is not consistently translated despite the stated plain-language standard, and the 1024–1179px icon-only run rail in §6.1 removes persistent text labels.
- **Intake completeness without interrogation — 7.5/10.** §4.2 captures all ten frozen discovery topics, separates overlays from hosted services, supports explicit unknowns, and provides a review ledger. However, every unknown makes the user author a reason, confidence effect, coverage effect, and follow-up owner; §7.1 offers no defaults or guided examples, turning “I do not know” into a four-field expert exercise. The six-step flow also never states when `createRun`, `putDiscovery`, and `putApprovals` occur or how a saved draft is restored.
- **Safety clarity — 9.0/10.** “Show the boundary before the button,” scoped disclosure panels, non-echoing secret upload, no unsafe runtime-relaxation shortcut, attachment-only hostile formats, and explicit package blocking make safety unusually visible and actionable. First-run provider authentication is the notable omission: §4.1 starts after a launcher has printed a URL and never designs the required Codex/Claude login, separate-home, environment-credential, or failed-authentication guidance.
- **Capability-gate and blocked-state honesty — 9.0/10.** §§4.5–4.6 accurately distinguish capable, blocked, not applicable, failed, partial, and not tested; require reasons and coverage effects; and explicitly continue the static path. The design should additionally map approval denial and capability expiry to concrete recovery screens rather than relying only on the universal state table.
- **Progress/resume usability — 6.5/10.** §§4.3–4.4 give good human labels, safe-checkpoint messaging, scoped retry copy, disconnect honesty, and cancellation cleanup semantics. But the promised phase durations, outcomes, attempts, recovery plans, limitations, latest 20 events, and “View older events” cannot be reconstructed from the frozen API: `RunDetail` exposes only `PhaseDocument`, the architecture has no attempt/recovery-plan/limitation/event-history reads, and SSE replay is not a durable history endpoint.
- **Evidence traceability — 6.0/10.** The trace rail, finding structure, safe-preview boundary, and decision-cell evidence state are conceptually excellent. They are not implementable through the required generated client: §4.8 promises content digest, byte length/media, provenance agent/activity, sanitized command, config digest, attempt, and redaction transformation summary, while architecture §12.2 `getEvidence` returns only `EvidenceOccurrence` plus two availability booleans; the occurrence contains IDs, not those referenced records.
- **Report readability — 8.8/10.** §13 defines a strong plain-language reading order, sensible page length, consistent option comparison, explicit unknowns, technical appendices, print behavior, and static HTML/Markdown semantics. It does not define how technical and lay reviewers access the pre-package reports in the web app, and the frozen HTTP surface exposes neither report descriptors nor report downloads before packaging.
- **Accessibility — 7.8/10.** §§7, 9, and 11 specify semantics, persistent labels, error summaries, live-region restraint, contrast, target sizes, reduced motion, forced colors, zoom, keyboard paths, and screen-reader checks at a high level. Two concrete conflicts remain: §11.2 focuses the `h1` after every route navigation while §3.3 promises scroll/focus restoration on return from detail, and `DecisionMatrix` requires unspecified “keyboard row navigation” without defining keys, roving focus, or interaction semantics. The tooltip-dependent compact rail also weakens cognitive and low-vision access.
- **Responsive local use — 6.0/10.** The 320px reflow rules, long-token wrapping, mobile definition-list conversions, fixed decision order, safe-area handling, and explicit viewport matrix are strong. The desktop math is internally impossible at the `xl` breakpoint: at 1280px, §6.1 allocates a 240px rail and page padding, while §10.2 requires a 220px + 720px + 280px setup layout (1,220px before gaps); finding and evidence detail similarly require 760px + 360px. These prescriptions necessarily overflow or collapse well before their declared breakpoint.
- **Implementation specificity — 5.0/10.** Tokens, components, routes, states, copy, breakpoints, and QA fixtures are detailed, but §15.3 explicitly says to consume only the frozen OpenAPI client while multiple primary screens require data and operations that client does not expose. Besides evidence and progress, the Context screen has no discovery GET, Reviews & package has no review-list or package-stage-detail GET, Overview/Run home cannot resolve `targetSnapshotId` to commit/mode, and a globally business-priority-sorted 50,000-row findings list is impossible with a cursor API that defines neither sort nor business-priority filtering.

## Overall

**7.4/10.** The contender is strong as an experience and content direction, especially on honest coverage, safety, report reading, and visual/accessibility discipline. It misses the P3 threshold because it labels itself “implementation-ready” while several core screens cannot be populated through the frozen architecture, and its declared `xl` layouts do not fit the shell at the breakpoint where they activate.

## Strongest objection

**Must-fix: §15.3 requires the UI to “Consume only the generated OpenAPI client,” but §§4.3, 4.6–4.8, 4.10–4.11, and 5 depend on canonical resources that frozen architecture §12.2 does not expose.** This is not a minor field omission. Evidence detail cannot fetch provenance activities, agents, blobs, or redaction derivations; Context cannot fetch saved discovery; Reviews & package cannot list reviews or nine package-stage certificates; Overview cannot fetch target snapshot identity, limitations, attempts, recovery plans, or durable event history. Implementers would have to invent endpoints, silently delete promised content, or reach around the public contract, breaking the P1/P6 parallel-build boundary. The design must either constrain itself to available DTOs or formally identify the exact architecture amendments required before calling the spec buildable.

## Other findings

1. **Must-fix — responsive column widths overflow their own shell (§§6.1, 10.1–10.2).** At the tested 1280px width, the 240px rail leaves about 1,040px before padding, but Setup demands 1,220px before gaps and Finding/Evidence detail demand 1,120px before gaps. This contradicts the no-overflow/reflow acceptance and will force frontend engineers to improvise breakpoint behavior.
2. **Must-fix — first-run authentication guidance is absent (§4.1).** The required flow begins with “Launcher prints loopback URL,” assuming provider authentication already succeeded. It does not cover interactive Codex/Claude login, environment credentials, separate provider homes, expired authentication, provider-specific remediation, or returning to the launcher safely, all explicitly required by P3 and DECISIONS.
3. **Must-fix — global findings ordering is not implementable (§4.7, §16.4).** The UI defaults to business priority across a 50,000-row paginated fixture, but architecture `listFindings` has no sort key, business-priority query, or specified server order. Client sorting one cursor page gives misleading ordering.
4. **Must-fix — package and review status has no durable read model (§§4.10–4.11, 7.1).** `PackageStageList` requires nine certificate-backed stages and `ReviewGate` requires four review records, yet `PackageView` exposes only a coarse package state and there is no list-reviews operation. SSE summaries cannot restore the screen after session expiry or event-history expiration.
5. **Should-fix — the “Mark as unknown” path overburdens the least-informed user (§§4.2, 7.1).** Requiring them to formulate confidence and coverage effects assumes assessment expertise. The system should offer plain-language choices/defaults, let the assessor refine them, and preview the consequence without making uncertainty harder to record.
6. **Should-fix — navigation focus rules conflict (§§3.3, 11.2).** Always focusing the new route’s `h1` on browser Back defeats the promised preserved scroll position and loses the originating finding/evidence link. Specify forward-navigation, Back/Forward, mutation, and modal-close focus separately.
7. **Should-fix — compact navigation hides persistent labels (§6.1).** The 72px “icon-plus-tooltip” rail makes seven core destinations dependent on icon recognition or tooltip discovery. Retain visible abbreviated labels, provide an expandable rail, or use the labeled route row earlier.
8. **Should-fix — custom table keyboard behavior is underspecified (§7.1 `DecisionMatrix`).** “Supports keyboard row navigation” does not identify the focus owner, arrow-key contract, Home/End behavior, or whether links remain independently tabbable. Prefer ordinary semantic-table navigation unless a complete composite-widget pattern is specified.
9. **Should-fix — the review reading surface is missing (§§4.10, 13).** The reports are detailed as customer artifacts, but the design does not say what exact rendered input technical and lay reviewers read before approving its digest, nor how they return from cited evidence without losing checklist progress.
10. **Nice-to-have — terminology needs one more operator-language pass (§§4.2–4.4, 12.3).** “Immutable target,” “fenced attempt,” “snapshot digest,” and “reconciled controls” are precise but are exposed as primary labels despite the mandate that non-specialists operate the workflow.

## Concrete fixes

1. Add a UI-to-OpenAPI data matrix for every screen and component, naming operation, DTO fields, pagination/sort behavior, loading/error states, and mutation transition. Mark every missing read model as a blocking architecture change rather than an implementation detail.
2. Resolve the frozen-contract gaps before P6: add or deliberately remove requirements for discovery retrieval, target-snapshot detail, provenance/blob/redaction detail, limitations, attempts and recovery plans, durable event history, review listing, report access, and package-stage certificates.
3. Add server-defined findings ordering and query fields for business priority and sort, including stable cursor tie-breakers; specify the exact default order used by the 50,000-row fixture.
4. Replace viewport-only desktop sizing with available-container rules. Keep Setup one column or two columns until the content container—not the browser—is at least the sum of columns, gaps, and padding; apply the same rule to Finding and Evidence detail and test at 1180, 1280, 1366, and 1440px.
5. Design a pre-bootstrap authentication/troubleshooting branch for both launchers: no login, expired login, environment credential present, provider unavailable, and fresh-link recovery. State which instructions belong in launcher output versus System readiness.
6. Define focus restoration by navigation type: focus `h1` for deliberate forward navigation, restore originating control and scroll for Back/Forward, focus inline result for mutations, and restore the opener after dialogs/sheets.
7. Remove tooltip-dependent primary navigation and unspecified matrix row-key behavior, or provide complete accessible names, visible-label alternatives, focus models, and keyboard interaction tables.
8. Make unknown capture forgiving: offer assessor-owned defaults for confidence/coverage effects, explain each in owner language, preserve “unknown” immediately, and allow later refinement without blocking target resolution.
9. Specify the exact pre-package report/review reader, input digest display, evidence-link return behavior, draft preservation, and how “passed with objections” affects package eligibility.
10. Add contract-backed end-to-end fixtures—not only screenshots—for reload after session expiry, expired SSE history, 50,000-row sorting, Back from evidence at a deep scroll position, all nine package stages after refresh, and every viewport/zoom boundary.

## Verdict

**revise.** The contender clears the bar for a strong design direction and accessibility-minded content system, but it misses the ship bar for implementation readiness. Core Context, progress, evidence, review, and package screens lack frozen data access, first-run authentication is not designed, and the desktop breakpoint math is contradictory. Those are contract and layout blockers, not polish issues.
