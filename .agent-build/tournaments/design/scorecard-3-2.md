## Scores

- **Lay comprehension — 8.8/10.** §§1–3 and §12 consistently translate machine states into consequence-first language, prohibit false safety scores, and keep technical identifiers one disclosure deeper. However, the authenticated-app starting point and §5.1 “Session entry” omit the required first-run Codex/Claude authentication guidance, so the least technical operator is abandoned before the otherwise excellent language system begins.
- **Intake completeness without interrogation — 7.4/10.** §§4.1 and 5.3–5.8 cover the ten required discovery topics, source modes, unknowns, profiles, optional services, credentials, and final review. Requiring every “I do not know yet” answer to supply a reason, confidence effect, coverage effect, and follow-up owner makes uncertainty a four-part expert exercise, and the prescribed ordering cannot complete against the frozen lifecycle.
- **Safety clarity — 8.8/10.** §§2.3, 5.6–5.8, 11.5, and 12.3 make destinations, data categories, expiry, credential purpose, denial effects, revocation, and attachment-only target content unusually explicit. The missing provider-login/authentication branch and the lack of a distinct affirmative target-code-execution decision leave two safety-critical first-run moments implied rather than designed.
- **Capability-gate and blocked-state honesty — 7.5/10.** §§4.2–4.3, 5.11–5.12, and 7 clearly distinguish blocked, not applicable, not tested, denied, and disconnected states without invalidating static work. But the UI promises that a waiting run can “approve / deny / supply safe credential” and that current approvals can be revoked, while architecture §12.2 permits `putApprovals` only in `DRAFT` and exposes no post-start approval-revocation operation.
- **Progress/resume usability — 6.5/10.** The 14-phase ordered map, no fabricated percentage, preserved-work messaging, quiet SSE reconnect, pause/cancel distinction, and stale-tab treatment are sound. The design’s paginated event history, recovery-plan choices, selected attempt retries, durations, and limitation details have no corresponding frozen read operations; `resumeRun` consumes `recoveryPlanId` and `retryAttemptIds`, but no API returns them.
- **Evidence traceability — 6.3/10.** §§4.4, 5.14–5.16, and 6.6 define a strong claim-to-evidence-to-review mental model and a safe transformed-preview boundary. Yet `getEvidence` returns only an `EvidenceOccurrence` plus preview/download booleans, with no joined claims, findings, controls, reviews, activities, derivations, or blobs, so the promised evidence detail and thread cannot be populated through the mandated generated client.
- **Report readability — 9.1/10.** §13 gives the executive, decision, technical, security, and coverage reports precise reading orders, measures, print behavior, semantic structure, evidence labels, and prohibited-claim rules. The missing pre-package report-list/read/download API means the excellent lay-review reading experience is specified as content but not as an operable screen.
- **Accessibility — 9.2/10.** §§6, 9–11 specify native semantics, focus handling, error summaries, restrained live regions, 44px targets, forced-colors behavior, reduced motion, 320px/zoom reflow, static-report semantics, and a serious manual assistive-technology matrix. Minor ambiguity remains around the custom “select-like” topic-navigation dialog and whether filter-dialog edits are discarded or preserved when closed without “Show N results,” but these are bounded refinements.
- **Responsive local use — 9.0/10.** §10 supplies explicit breakpoints, container thresholds, per-screen reflow, 320px behavior, long-token handling, zoom/card fallbacks, and dialog behavior without relying on horizontal scrolling. The three-column decision comparison at a 56rem container should still be fixture-tested with 200% label expansion, but the fallback rule is otherwise implementable.
- **Implementation specificity — 4.5/10.** Tokens, typography, components, route content, states, breakpoints, and QA fixtures are exceptionally detailed, but the primary flow contradicts the frozen transition order and many screens require absent resources: target snapshot detail, saved discovery retrieval, durable event history, recovery plans/attempts, review listing, report access, evidence joins, limitation detail, and package-stage certificates.

## Overall

**7.7/10.** This is the strongest kind of non-shippable spec: the interaction, content, accessibility, and responsive systems are mature, but the design misses the P3 implementation bar because its primary setup flow fails the frozen lifecycle and substantial portions of the workspace cannot be backed by the frozen OpenAPI contract.

## Strongest objection

**Must-fix — the prescribed setup sequence in §§4.1 and 5.3–5.8 cannot reach “Begin assessment” under architecture §§6.1 and 12.2.** The design orders source selection → “Prepare safe copy” → Product context → Access and consent → Setup review. Frozen `resolveTarget`, however, is allowed only in `DRAFT`, validates discovery and source, and transitions the run to `RESOLVING_TARGET` then `READY`; `putDiscovery` and `putApprovals` are allowed only in `DRAFT`. Therefore “Prepare safe copy” fails with `DISCOVERY_INCOMPLETE`, a frozen-working-tree source cannot receive its required approval in time, and—if resolution somehow succeeds—the later discovery/approval saves and §5.8 “Change” actions are illegal because the run is no longer `DRAFT`. This is a guaranteed dead end in the primary flow, not an edge case.

## Other findings

1. **Must-fix — core screens exceed the frozen read model (§§5.4, 5.9–5.18, 15).** `RunDetail` exposes only `targetSnapshotId`, phases, current capabilities, and coverage summary; it cannot supply full commit/snapshot identity, dirty paths, integrity result, attempts, phase duration, recovery plans, limitations, reviews, or package stage certificates. Implementers would have to invent endpoints or omit promised content, breaking the frozen P1/P6 contract boundary.
2. **Must-fix — in-run consent behavior is architecturally impossible (§§2.3, 4.2, 5.6, 5.11).** “Approve / deny” during `WAITING_INPUT`, approval revocation, and approval expiry recovery have no legal mutation after `DRAFT`. Secret revocation exists, but approval revocation is a different action and cannot be inferred from it.
3. **Must-fix — search/filter/sort promises do not match cursor APIs (§§5.2, 5.13, 5.15).** Assessments search, finding search/business-priority sort and multi-select filters, and evidence search are specified globally, while `listRuns`, `listFindings`, and `listEvidence` expose only narrow single-value query fields and no sort contract. Client-side behavior over one cursor page would present incomplete or falsely ordered results.
4. **Must-fix — Reviews and report reading have no reloadable data source (§§4.6, 5.17, 6.16, 13).** There is no list-reviews operation and no report descriptor/list/download operation. A reviewer cannot reopen the page, verify the exact report input digest, follow report evidence, or resume a draft review using only the generated client.
5. **Must-fix — progress is designed as history but exposed only as a stream (§5.10).** The UI requires paginated events grouped by date and phase. Architecture provides SSE replay only; replay can expire with 410, and there is no event-history query. Refresh/session expiry therefore destroys the promised activity view.
6. **Must-fix — first-run authentication guidance is absent (§5.1).** P3 explicitly requires it, but Session entry begins after a loopback token exists and covers only token/server errors. It does not design initial Codex/Claude login, separate provider homes, environment credential alternatives, expired provider auth, or safe launcher recovery.
7. **Should-fix — generic baseline states do not satisfy every route’s off-path contract (§7).** “Every route and component must specify” loading, empty, denied, stale, disconnected, and error behavior, but most screens in §5 provide only purpose/content. Decision-before-synthesis, reviews-before-required, evidence-denied, package-with-prior-valid-release, and retention/deletion-job failures need route-specific copy, action, and focus outcomes.
8. **Should-fix — unknown capture burdens the least-informed user (§§4.1, 5.5).** The architecture requires the four unknown effects, but the product owner should not have to author assessment methodology. The design says only that the UI “supplies plain prompts”; it does not provide safe assessor-owned defaults, selectable plain-language effects, or a nonblocking refinement path.
9. **Should-fix — target execution consent is not a distinct recorded decision (§§5.6, 5.8).** “Runtime/build access” is grouped with destinations and credentials, but executing hostile repository code is materially different from egress approval. The review should explicitly name execution, isolation boundary, residual risk, denial result, and approval receipt.
10. **Nice-to-have — two custom mobile interactions need complete accessibility contracts (§§5.5, 6.10).** The “select-like navigation button opening a dialog list” needs roles, current-topic announcement, arrow/Tab behavior, and focus return; the filter dialog needs explicit draft/apply/cancel semantics so closing it does not silently apply or discard selections.

## Concrete fixes

1. Re-sequence setup to match the frozen state machine: create the `DRAFT`, capture complete discovery and required approvals, review editable setup, then call `resolveTarget`; after `READY`, show immutable target identity and allow only “Begin assessment” or an explicit new revision.
2. Add a screen-to-OpenAPI matrix naming every query, mutation, DTO field, legal run state, pagination/sort rule, and reload behavior. Treat missing operations as architecture amendments that must be frozen before P6, not frontend improvisation.
3. Resolve the minimum contract gaps for target-snapshot detail, discovery retrieval, recovery plans/attempts, limitation detail, durable event history, review listing/drafts, report access, joined evidence provenance, and package-stage certificates—or remove the unsupported UI promises.
4. Freeze server-side list semantics for run search, finding business-priority/default ordering, multi-value filters, and evidence search, including stable cursor tie-breakers and honest result-count language.
5. Decide whether approvals are intentionally mutable after start. If yes, add scoped post-`DRAFT` approval/revocation operations and transitions; if no, remove in-run approval actions and design “continue blocked” or “create revision” as the only honest outcomes.
6. Add a pre-session/provider-authentication branch for both launchers covering first login, environment credentials, provider-home separation, expired authentication, and recovery without exposing tokens.
7. Specify an explicit hostile-target execution approval separate from network/service consent, including isolation, residual risk, expiry, denial effect, and audit record.
8. Replace generic state assertions with per-route state tables for every required empty/loading/error/denied/stale condition and add contract-backed fixtures for reload, expired SSE replay, partial cursor lists, and cross-tab conflicts.
9. Make unknown capture forgiving with plain-language choices or system-proposed confidence/coverage effects that the assessor can refine, while preserving the required canonical fields.
10. Add focused accessibility fixtures for the topic navigator, unapplied filter dialog, 56rem decision comparison with 200% label expansion, and pre-package report review with evidence-link focus restoration.

## Verdict

**revise.** The contender clears the lay comprehension, report, accessibility, responsive, and visual-system bars, but misses the implementation threshold. The primary setup flow is illegal under the frozen run contract, first-run authentication is missing, and progress/evidence/review/package screens depend on absent read models. Those must be reconciled before frontend implementation.
