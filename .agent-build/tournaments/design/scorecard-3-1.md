## Scores

- **Lay comprehension — 9.2/10.** The “meaning, then machinery” rule (§2.1), complete human translations of run states (§3.2), consequence-first finding detail (§5.14), and concrete vocabulary/microcopy rules (§12) are exceptionally well matched to non-specialist owners; first-run provider authentication and several setup terms still lack an equally concrete novice journey.
- **Intake completeness without interrogation — 6.5/10.** The flow captures both source types, immutable identity, all ten discovery topics, provenance, approvals, secrets, and unknowns (§§4.1, 5.3–5.8), but it orders target resolution before the discovery and approval data that the frozen lifecycle requires, and it makes “I do not know yet” trigger four separate impact/ownership judgments (§4.1 lines 129–135).
- **Safety clarity — 8.7/10.** The consent ledger exposes destination, data categories, methods, duration, credentials, benefit, and denial effect with no approve-all path (§5.6), and secret handling is unusually explicit (§5.7); provider login/readiness failure is not designed, and target-code execution is described only as another access card rather than given a named, end-to-end authorization state.
- **Capability-gate and blocked-state honesty — 7.7/10.** The six coverage statuses have exact definitions (§4.3), static assessment remains usable when dynamic work is blocked (§5.19), and rerunning the gate is bounded (§5.12), but there is no runtime-capability screen or complete gate-result flow showing attempted steps, effective policy, prerequisites, approval state, and the transition into dynamic work or static-only continuation.
- **Progress/resume usability — 8.2/10.** The phase map avoids false percentages, tab closure and SSE reconnect behavior are candid, and pause/cancel/recovery effects are well framed (§§4.2, 5.9–5.11). Recovery-plan retrieval, scoped retry selection, failed-review correction, and return-to-packaging behavior remain prose-level, while the specified paginated activity history has no frozen read operation.
- **Evidence traceability — 9.4/10.** The evidence thread, safe transformed previews, separate severity/priority/confidence/validation axes, audit-preserving disputed findings, and recommendation-to-occurrence path (§§4.4, 5.13–5.16, 6.6) closely implement the evidence integrity goals without creating a misleading score.
- **Report readability — 9.5/10.** The static index, five audience-specific reports, executive reading order, equal-depth option comparison, prominent limitations report, evidence-link language, print behavior, and plain-language constraints (§13) form a coherent customer package that directly addresses the brief.
- **Accessibility — 9.6/10.** The spec gives implementable WCAG 2.2 AA semantics, focus, error, live-region, forced-colors, zoom, screen-reader, touch, report, and QA requirements (§11), with only minor unresolved product mechanics around reviewer identity/handoff rather than accessibility technique.
- **Responsive local use — 9.5/10.** It defines a 320 px floor, fluid type, container queries, explicit breakpoints, per-screen reflow, long-content behavior, 200% zoom fixtures, and no-overflow rules (§10); unlike a generic “responsive” claim, dense decision, findings, evidence, and review screens each have a concrete narrow-width transformation.
- **Implementation specificity — 5.8/10.** Tokens, components, screen states, content rules, and QA fixtures are unusually detailed, but the main setup order contradicts the frozen state machine, and several mandatory views require data the frozen OpenAPI does not expose: target snapshot detail, paginated events, review lists, recovery plans, validation/package-stage certificates, and cross-page project search.

## Overall

**8.4/10** — unweighted average across the full P3 rubric. This clears the tournament’s numerical bar because the plain-language, evidence, report, accessibility, and responsive systems are excellent, but it does not clear the implementation-ready bar: the primary intake sequence is illegal under the frozen lifecycle and several release-critical screens cannot be populated from the frozen API.

## Strongest objection

**Must-fix: the primary setup flow cannot reach “Begin assessment” under the frozen architecture.** Section 4.1 and the screen order in §§5.3–5.8 place “Prepare safe copy” immediately after source choice, then collect Product context, Access and consent, credentials, and Setup review. Frozen architecture §12.2 says `resolveTarget` validates discovery/source and changes `DRAFT` to `RESOLVING_TARGET`; `putDiscovery` and `putApprovals` are legal only while the run is `DRAFT`, and target success leads toward `READY`, where those mutations are no longer legal. The design therefore either receives `DISCOVERY_INCOMPLETE` at Target preparation or resolves successfully and strands the later discovery/consent screens. This is the product’s most important journey, not an edge case, and implementation cannot repair it without contradicting either the design or the frozen contract.

## Other findings

1. **Must-fix — first-run provider authentication guidance is absent (§§4.1, 5.2, 5.19).** P3 explicitly requires it, but the design moves from choosing Codex/Claude Code to repository input and describes System readiness only as a status inventory. It has no unauthenticated, expired, unavailable, wrong-launcher/provider, login-in-progress, login-failed, environment-credential alternative, or successful-return flow. A first-time operator can complete substantial setup before learning that the selected provider cannot run.
2. **Must-fix — the runtime-capability gate is referenced but not designed (§§4.3, 5.12, 5.19).** “Rerun safe runtime check” and a readiness summary do not define the phase-five experience: what was attempted, isolation/effective egress, which prerequisite/approval failed, whether a safe corrective action exists, how denial differs from unsupported, and exactly how the operator continues static-only. Engineers would have to invent the highest-risk conditional flow.
3. **Must-fix — multiple core screens are not implementable from frozen read contracts.** Target preparation (§5.4) requires full commit, snapshot digest, dirty-tree treatment, exclusions, and integrity result, but `RunDetail` exposes only `targetSnapshotId` and there is no target-snapshot GET. Progress (§5.10) promises paginated events, but only SSE exists. Reviews (§5.17) requires a review map, but only `createReview` exists. Recovery (§5.11) asks users to choose plans/attempts required by `resumeRun`, but no operation returns them. Package (§5.18) promises nine stages and certificates while `PackageView` exposes five coarse states and one validation-report ID.
4. **Must-fix — failed-review correction is a label, not a flow (§§4.6, 5.17).** “Corrections create another assessment revision or return to execution” and “Create corrected revision according to state rules” do not define which input or conclusion is editable, what is copied, what becomes stale, how objections remain visible, which phases and independent reviews rerun, or how the corrected run returns to packaging. Because reviews are a release gate, this omission creates a terminal-feeling dead end.
5. **Should-fix — unknown capture is not forgiving enough for its target user (§§4.1, 5.5).** Requiring reason, confidence effect, coverage effect, and follow-up owner precisely when the operator lacks knowledge asks them to perform assessment modeling rather than answer an interview. It encourages boilerplate or fabricated impacts and works against the rubric’s “without interrogation” requirement.
6. **Should-fix — provider choice is not reconciled with launcher authority (§§4.1, 5.3).** The design offers Codex and Claude Code as a choice, while architecture `getSystem.launcherProvider` and launcher behavior bind the running environment to one provider. It never says whether the alternate choice is disabled, prompts a relaunch, or is actually executable, so the wizard can promise an unavailable path.
7. **Should-fix — assessment-home search exceeds the API contract (§5.2).** The design specifies project search plus opaque-cursor pagination, but `listRuns` supports only state and cursor. Client-side search over one loaded page would silently miss runs; loading all pages defeats the bounded-list contract. The spec must either remove global search or flag a contract change.
8. **Nice-to-have — the otherwise excellent lay language still foregrounds specialist package terms (§§4.7, 5.18).** “age X25519,” “recipient public key,” and “SHA-256 digest” need inline action-oriented definitions on first encounter, not only glossary availability, so the owner understands what to provide and what verification proves.

## Concrete fixes

1. Redraw setup against the legal lifecycle: create a server-backed `DRAFT` after the minimum source/provider fields; collect and save all ten discovery records and all approval decisions in `DRAFT`; show the complete setup review; then invoke target resolution; show immutable target identity and remaining limits in `READY`; finally allow “Begin assessment.” Specify reload, stale-row, failure, and back-edit behavior at every boundary.
2. Add a first-run provider-readiness flow with authenticated, unauthenticated, expired, provider unavailable, and launcher/provider mismatch states. Give exact safe remediation through the relevant launcher, explain environment credentials as an alternative, and preserve/restore setup state after authentication.
3. Add a dedicated Runtime capability screen/state sequence backed by `getCapabilities`: declared support, attestation, approval, effective result, attempted safe steps, effective network policy, reason and evidence, coverage effect, corrective action, rerun eligibility, and explicit “Continue with static assessment” behavior.
4. Produce a screen-to-OpenAPI dependency matrix. Either add frozen read models/operations for target snapshots, event history, reviews, recovery plans/attempts, validation issues, and package stages/certificates, or simplify the affected screens to data the contract actually provides. Resolve project search in the same pass.
5. Define failed-review correction as one exact state/revision sequence: editable versus immutable material, copied discovery, accepted corrections, superseded outputs, invalidated gates, rerun phases, retained objections, replacement reviews, and return to package eligibility.
6. Replace four blank unknown fields with a short reason plus optional follow-up owner; have the system propose topic-specific confidence and coverage effects for explicit confirmation/editing so the canonical contract remains complete without forcing users to invent assessment language.
7. Bind provider selection to `launcherProvider`: show the current provider as available and the other as a relaunch path, or formally revise architecture to support switching. Do not let an unavailable provider appear as a normal enabled radio choice.
8. Add inline plain-language explanations for X25519/public keys and SHA-256 verification at the package decision points.

## Verdict

**Revise.** The contender clears the quality bar for lay comprehension, evidence honesty, report craft, accessibility, and responsive rigor. It misses the ship bar because its main intake flow violates the frozen lifecycle, first-run authentication and runtime-gate journeys are incomplete, and release-critical screens depend on absent API data.
