## Scores

- **Requirements coverage — 4/10.** Sections 4–9 cover evidence admission, redaction, rendering, packaging, retention, and incident handling deeply, but P2-required container/nested-runtime controls, target-egress states, runtime-test safety classes, prompt-injection defenses, and the frozen VM secret-envelope review are not specified.
- **Assets, attacker model, and trust boundaries — 6/10.** Section 2.1 names the important data assets and Section 2.2 correctly treats repository, provider, scanner, browser, and imported-package content as untrusted, but it merely declares the host helper, pinned worker image, and runtime broker trusted without decomposing the outer-sandbox → helper → Lima VM → rootless Docker → target/probe boundaries frozen in architecture §§3 and 10.
- **Prohibited actions and authorization — 3/10.** “No provider, scanner, target process, browser probe, or report text can directly create” authoritative state is useful, but the spec never supplies the required explicit deny set for host Docker socket access, privileged/container escape features, production endpoints/credentials, destructive external actions, DoS, arbitrary commands, or target-selected runtime capabilities.
- **Container, nested-runtime, and source-isolation controls — 1/10.** Apart from references to a “runtime gate” and the residual Docker/Lima attack surface, no section operationalizes architecture ADR-006/ADR-007 or §10.2: there is no compiled-Compose rejection matrix, no rootless/cgroup/firewall/mount/namespace/resource invariants, no immutable snapshot transfer check, no cleanup-residue rule, and no statement that an incompatible target becomes blocked rather than receiving weaker controls.
- **Credential lifecycle and secret handling — 4/10.** Sections 5.1 and 8.5 are strong for non-persistence, one-use handles, redaction canaries, and age passphrases, but they do not define the SSH key/socket, provider-home, provider-token, sandbox-secret, and VM-envelope lifecycles end to end, including exact recipients, approval binding, expiry, replay/wrong-recipient rejection, cancellation/restart cleanup, and engagement-home disposal.
- **Network egress and hosted-service controls — 3/10.** Sections 3.2 and 10.5 require disclosure and react to uncertain egress, yet there is no finite target-egress state machine, default-deny IPv4/IPv6/DNS rule, metadata/LAN denial, build-acquisition/runtime separation, destination/byte audit receipt, approval revocation behavior, or no-silent-fallback test matching architecture §§3.4 and 10.3.
- **Safe dynamic testing and emergency control — 2/10.** Section 5.5 safely constrains screenshot capture, but the spec defines no runtime-test safety classes, non-destructive probe allowlist, authorization boundary, production-like endpoint/credential sentinel, destructive-method prohibition, resource-abuse limits, heartbeat escalation, emergency-stop semantics, orphan cleanup, or test result mapping after forced termination.
- **Prompt injection and untrusted-content defense — 5/10.** Sections 2.2, 6, and 11.3 provide excellent active-content and report-rendering defenses, but repository/model prompt injection into Codex or Claude Code is not analyzed: there is no instruction-precedence rule, provider tool/capability allowlist, approval non-delegation invariant, malicious-task fixture, or proof that model prose cannot induce egress, execution, secret access, or a permissive fallback.
- **Evidence integrity, privacy, redaction, and packaging — 9/10.** Sections 4–8 precisely separate blobs from occurrences, bind fences and snapshots, fail closed on truncation, specify layered secret detection and irreversible derivations, constrain untrusted rendering, and define a staged fresh-process package validator with adversarial fixtures; this is the contender’s strongest and nearly implementation-ready area.
- **Failure, incident response, and auditability — 6/10.** Sections 9–10 handle ENOSPC, deletion, pre/post-delivery leaks, tamper, parser failure, and uncertain egress well, but there is no emergency-stop behavior for hostile runtime execution and no complete normative audit-event inventory for capability decisions, approvals, secret redemption/revocation, egress, helper/broker lifecycle, policy rejection, and cleanup residue.
- **Finding governance and compliance-language safety — 5/10.** Sections 3.3 and 7 block unsupported compliance claims and require independent review, but High/Critical labels are used without severity assignment rules, confidence/validation transitions, separation of technical severity from business priority, CVSS sufficiency criteria, or deterministic handling of disputed/imported findings.
- **Verification, ownership, and parallel buildability — 6/10.** Sections 11, 12, and 14 provide excellent negative fixtures and lane ownership for evidence/report/package concerns, but the acceptance suite omits the highest-risk runtime, egress, prompt-injection, production-sentinel, broker-envelope, host-socket, and escape paths; “fresh-context” and lay-review pass criteria also lack a mechanically testable independence and acceptance contract.

## Overall

**4.5/10.** The evidence-integrity/redaction/package slice is excellent, but this is not a complete P2 safety specification. Most controls around hostile execution—the highest-consequence part of the product—would still have to be invented during P4/P5, violating P2’s freeze-before-build gate.

## Strongest objection

**Must-fix:** Section 2.2 declares the host helper, pinned worker image, and runtime broker trusted, while Sections 11–12 contain no control or release test for the frozen hostile-runtime architecture. Architecture §§10.2–10.4 and ADR-006/ADR-007 require compiled Compose policy, mount-free disposable Lima/rootless Docker isolation, default-deny target egress, an explicitly reviewed VM secret-envelope profile, and blocked coverage when controls cannot be preserved. Contender 3 never specifies those invariants, their owners, failure transitions, audit receipts, or adversarial proofs. Consequently, an implementation could satisfy every listed release gate while still mounting a dangerous resource, weakening runtime isolation, leaking a sandbox secret to the wrong recipient, or allowing external target traffic.

## Other findings

1. **Must-fix — Credential and network rules are descriptive, not enforceable.** Section 5.1 says secrets “MUST be inaccessible” except to a “narrowly scoped component,” and §3.2 asks for hosted-service disclosure, but neither defines the exact recipient/capability matrix or lifecycle for SSH, provider credentials/homes, sandbox credentials, optional-service credentials, and VM envelopes. This leaves the most important “who can receive what, when” decision to implementation.
2. **Must-fix — No target-egress contract exists.** Section 10.5 only describes response after egress uncertainty. It does not define default-deny runtime, separately approved build acquisition, DNS/IPv6/metadata/LAN controls, exact-endpoint approval, or the behavior when enforcement cannot be attested. This misses both the brief’s production-access prohibition and architecture §3.4.
3. **Must-fix — Dynamic-test authorization is absent.** Section 5.5 gates screenshots, not runtime actions. There is no safe-technique taxonomy, HTTP-method/action allowlist, sandbox-only credential and endpoint binding, destructive-action/DoS denial, or sentinel test required by AC-4.
4. **Must-fix — Prompt injection is conflated with active-content safety.** Sections 6 and 11.3 stop HTML/Markdown execution in the UI/report, but do not constrain provider behavior when hostile repository instructions ask the agent to run commands, contact a service, expose credentials, alter policy, or fabricate evidence. The two attack classes require different controls and tests.
5. **Must-fix — The frozen VM secret-envelope profile is not reviewed.** Architecture §10.3 explicitly requires safety review of ephemeral X25519/HKDF/AES-GCM delivery and replay, wrong-recipient, expiry, and cleanup fixtures. Contender 3 only specifies a generic one-use broker handle in §5.1; it neither accepts nor rejects the architecture profile.
6. **Must-fix — The release suite proves the narrow slice, not the product boundary.** Section 11 extensively tests provenance, redaction, rendering, packages, and deletion, while omitting hostile Compose fields, host-socket absence, privilege/capabilities/devices/namespaces, immutable snapshot transfer, egress, secret-envelope replay, emergency stop, orphan cleanup, production sentinels, and malicious provider instructions.
7. **Must-fix — Severity/confidence rules remain undefined.** Sections 1 and 7 treat High/Critical findings as release-significant but do not state how severity is assigned, what evidence permits CVSS, how technical severity differs from business priority, or which transitions are legal for corroborated/disputed/invalidated/not-assessed findings. Different lanes can therefore produce inconsistent blockers.
8. **Must-fix — Audit coverage is incomplete.** Stage certificates, tombstones, and sanitized incident records are specified, but P2’s required audit events need a complete inventory and required fields for capability resolution, approvals/denials, provider/optional-service disclosure, secret handle redemption/revocation, egress attempts, runtime compile/start/stop/emergency-stop, cleanup residue, and override attempts.
9. **Should-fix — Human-review gates are not objectively testable.** Section 7.2 requires a “fresh-context reviewer” and says a lay reviewer “can identify” key information, but it does not define reviewer identity/separation, prohibited self-review relationships, required questions, scoring, evidence capture, or a deterministic pass/fail threshold.
10. **Should-fix — Safety invariant 3 is literally overbroad.** Section 2.4 says “Every customer-visible byte is admitted,” but `manifest.json`, `SHA256SUMS`, the ZIP container, and detached digests are generated after evidence admission. The spec needs separate invariants for admitted source-derived content and packaging-generated metadata so the release gate is implementable without semantic exceptions.

## Concrete fixes

1. Add a normative control matrix for every P2 trust boundary with asset, attacker, allowed operation, prohibited operation, enforcement component, immutable input/approval, fail state, audit event, owning lane, and required negative test.
2. Add a hostile-runtime section that adopts the frozen helper/Lima/broker architecture: enumerate every rejected Compose/Docker field, enforce rootless Docker, read-only verified snapshot, no host socket or bind mount, dropped capabilities, `no-new-privileges`, non-root execution, cgroup/PID/CPU/memory/time/output limits, internal-only networking, and cleanup-residue handling. State explicitly that no policy failure may fall back to a weaker runtime; dynamic coverage becomes `blocked`.
3. Review architecture §10.3’s VM secret-envelope design explicitly. Freeze recipient/purpose/approval binding, one-use redemption, expiry, replay and wrong-recipient rejection, tmpfs handling, zeroization, cancellation/restart reconciliation, and negative fixtures. Prohibit provider and SSH credentials as envelope purposes.
4. Define credential lifecycles separately for SSH input, provider authentication/home, sandbox credentials, optional-service credentials, and age secrets—from intake and storage compartment through exact recipient, use count, expiry/revocation, cancellation, crash, run completion, and engagement cleanup.
5. Define target egress as finite states such as denied, build-acquisition-approved, and exact-runtime-exception-approved, with separate network identities, IPv4/IPv6/DNS/metadata/LAN enforcement, approval digest, destination and byte audit receipts, timeout/revocation, and failure-to-attest → blocked behavior. Forbid silent fallback to provider or hosted services.
6. Add runtime-test safety classes and authorization rules: passive/read-only checks, sandbox-authenticated non-destructive checks, explicitly unsupported/destructive checks, method/action allowlists, production-like credential and endpoint sentinel denials, rate/resource bounds, and exact status/coverage consequences for cancellation or emergency stop.
7. Add a prompt-injection section covering hostile repository instructions, model output, tool proposals, and provider compartments. Freeze instruction precedence, capability non-delegation, no provider access to helper/secret broker/package state, typed tool allowlists, approval non-inference, output-as-proposal semantics, and malicious prompt fixtures for command, egress, secret, policy-override, and evidence-fabrication attempts.
8. Add a complete audit-event catalogue and the minimum safe fields for approval, capability, credential, egress, runtime, policy, emergency-stop, cleanup, evidence, review, incident, and package events; explicitly prohibit secret/source bodies in those events.
9. Freeze severity, technical impact, business priority, confidence, and validation as separate fields with legal transitions and evidence requirements; define CVSS use, imported-finding behavior, disagreement handling, and which unresolved states block release.
10. Extend Sections 11–12 with adversarial runtime, network, provider, and envelope tests, and make all four promised host/architecture variants release blockers. Define human-review independence and lay-review pass criteria as stored, repeatable acceptance records.

## Verdict

**Reject.** The contender clears the bar for an evidence-integrity/redaction/packaging subsystem specification, but misses the P2 bar that every trust boundary and prohibited action have enforceable controls and verification. Its missing hostile-runtime, egress, authorization, credential-envelope, and prompt-injection contracts would force security-critical invention during implementation.
