## Scores

- **Requirements coverage — 8/10.** The contender covers nearly every P2 domain in substantial depth: assets and hostile actors (§§2–3), prompt injection and provider authority (§§4–5), approvals and egress disclosure (§§6–7), privacy (§8), finding and recommendation safety (§§9–10), audit/incident handling (§§11–12), ownership (§13), and release tests (§§14–15). The explicit P2 requirement for runtime-test safety classes is absent, and source acquisition plus the frozen VM-secret profile are referenced rather than actually safety-reviewed.
- **Assets, attacker model, and trust boundaries — 9/10.** Sections 2–3 name provider homes, SSH, source, sandbox credentials, workflow authority, decision quality, local attackers, malicious repositories, plugins, optional services, runtimes, and recipient harms, and §2.4 honestly bounds the TCB. The model is less complete for malicious Git transport/object parsing and for the authenticated loopback UI/session path than it is for provider manipulation.
- **Prohibited actions and authorization — 8/10.** Sections 4.1, 5.2, and 6.2 strongly establish structural authority, a five-command provider surface, human-only approvals, and non-waivable production/destructive/socket/mount/upload prohibitions. However, “destructive or state-changing security tests” is only a negative rule; there is no per-control authorization object that distinguishes an allowed login POST or reversible sandbox mutation from a forbidden state change.
- **Container, nested-runtime, and source-isolation controls — 7/10.** Sections 3, 5.1, 13.4–13.5, and release gate 5 preserve separate provider/analyzer/runtime compartments, the closed helper surface, compiled Compose, Lima/rootless Docker, resource controls, and no weaker fallback. But the safety spec does not enumerate or test architecture §§9–10’s acquisition, Compose, broker, mount, namespace, build-context, image, MAC/fence, and cleanup rejection paths; “preserve the architecture” leaves the safety-owned conformance matrix to implementation.
- **Credential lifecycle and secret handling — 7/10.** The data map (§8), provider compartment (§5.1), approval rules (§6), stop order (§12.2), canaries (§14.1), and gate 6 cover provider, SSH, sandbox, optional-service, and package secrets with strong separation and cleanup intent. Architecture §10.3 explicitly requires P2 to review X25519/HKDF/AES-GCM envelope construction, but §§13.5 and 15.11 mention only purpose-bound one-use delivery and replay/recipient/expiry tests; nonce generation, KDF context, canonical associated data, key zeroization, crash residue, and failure semantics remain unreviewed.
- **Network egress and hosted-service controls — 8/10.** Sections 6–7 provide exact destination/data/purpose/byte approvals, no redirects, DNS-rebinding defense, hostile-response quarantine, no fallback, and distinct provider versus optional-service disclosures; §14.3 also tests network-identity separation. Git acquisition, build acquisition, and target-runtime flows do not receive equivalent normative proxy/firewall lifecycle detail, and there is no attack test for malicious build/source content attempting to encode repository bytes through an otherwise approved Git or registry destination.
- **Safe dynamic testing and emergency control — 5/10.** Sections 6.2, 12, 13.5, 14.4, and gate 5 give excellent production denial, security-stop ordering, bounded emergency teardown, restart reconciliation, and residue blocking. But the spec never defines the required `passive-observation`, `read-only-authenticated`, `reversible-sandbox-mutation`, and `prohibited` classes—or any equivalent—and never binds a planned runtime control to origin, method/action, account, synthetic data, credential handle, side-effect budget, rollback proof, rate, and abort trigger.
- **Prompt injection and untrusted-content defense — 9/10.** Sections 4–5 are the contender’s standout: they freeze instruction precedence, make repository instruction files inert evidence, remove the snapshot from the provider working directory, expose only typed evidence-ID commands, constrain context and bytes, treat outputs as proposals, and semantically validate them. Section 14.1 exercises both agents across filenames, instructions, code, SARIF, runtime content, encodings, fake tool results, credential theft, scope manipulation, approval, suppression, and forged evidence; the remaining irreducible provider-CLI credential risk is correctly disclosed.
- **Evidence integrity, privacy, redaction, and packaging — 9/10.** Sections 5.3, 8–10, 13.4/13.6, 14.2/14.5/14.6, and gates 8–10 combine bounded parsing, allowlisted references, provenance/confidence gates, staged redaction, screenshot re-encoding, typed rendering, independent review, reopened-ZIP validation, retention, and deletion. A residual covert channel remains when a hostile target that received a sandbox secret can transform it into an otherwise declared artifact or screenshot; exact-value scanners and re-encoding cannot prove non-exfiltration.
- **Failure, incident response, and auditability — 9/10.** Sections 11–12 define a broad safe-field audit inventory, concrete stop triggers, deterministic containment order, severity/disposition, no automatic resume, fresh provider context, crash reconciliation, resource-nonce ownership, and release blocking on uncertainty. The spec does not map every listed audit action to a frozen event enum/producer schema, but it is substantially more operational than a prose-only incident policy.
- **Finding governance and compliance-language safety — 9/10.** Sections 9–10 correctly separate technical severity, business priority, confidence, validation, applicability, and coverage; constrain CVSS; require evidence and independent review; prohibit repository grades and unsupported absolutes; and prevent security alone from forcing rebuild. Dispute/supersession authority and the exact release effect of unresolved Medium/Low findings could be made more explicit.
- **Verification, ownership, and parallel buildability — 7/10.** Sections 13–15 assign controls to the frozen packages and provide unusually adversarial dual-provider, authority-laundering, egress, incident, evidence, privacy, and package tests. An implementation could nevertheless pass the written suite without proving dynamic-action authorization, source-acquisition parser/hook/filter defenses, the complete helper/Compose rejection matrix, VM-envelope cryptographic correctness, or local bootstrap/session abuse resistance.

## Overall

**7.9/10.** This is the strongest product-wide safety direction in the reviewed material and is close to the P2 bar, but the average stays below ship because the explicitly required dynamic-test authorization model is missing and several high-consequence architecture boundaries are adopted by reference rather than independently reviewed and verified.

## Strongest objection

**Must-fix — the spec has no positive authorization contract for runtime actions.** PLAN P2 explicitly requires “runtime-test safety classes,” and the brief requires automatic safe runtime/browser checks while forbidding production and destructive actions. Contender 5 identifies accidental mutating browser actions as a High threat (§3), prohibits “destructive or state-changing security tests” (§6.2), and delegates probing to a `controlPlanId` through architecture-compatible runtime components (§13.5), but nowhere defines what makes a concrete probe safe to execute.

That omission leaves the decisive attack edge open:

`hostile target page/redirect/form/API description or model-proposed control → trusted Playwright/ZAP/probe planner → authenticated POST/PUT/DELETE or cross-origin request → sandbox state mutation, credential misuse, or unintended external effect`.

The provider’s inability to grant authority does not solve this: a deterministic probe still needs a frozen allow/deny decision based on exact origin, route, method/action, account, credential purpose, data, side-effect and rate budgets, cleanup/rollback, and stop conditions. Sections 14–15 contain no fixture for login versus mutation, redirects, forms, JavaScript-triggered requests, WebSockets, uploads/downloads, CSRF-like actions, or reversible-mutation cleanup. P5 would therefore have to invent a security-critical policy and contract after P2, directly missing the “every trust boundary and prohibited action” completion gate.

## Other findings

1. **Must-fix — the VM secret-envelope profile is not actually reviewed (§13.5; §15.11).** Architecture §10.3 explicitly assigns P2 review of ephemeral X25519, HKDF-SHA-256, AES-256-GCM, JCS-associated-data binding, replay, recipient, expiry, tmpfs, and cleanup. The contender merely says “purpose/recipient-bound one-use sandbox secrets” and requires replay/recipient/expiry tests. It does not accept or reject exact key generation, nonce uniqueness, HKDF salt/info, associated-data encoding, key/plaintext zeroization, crash recovery, or malformed-ciphertext behavior, so a cryptographic boundary remains for P5 to invent.

2. **Must-fix — source acquisition is an unreviewed attack path (entire spec; §§8, 12.1, and 13 do not assign it).** The frozen architecture has extensive defenses for hostile Git URLs/servers, hooks, filters, LFS, submodules, symlinks, special files, Unicode/path collisions, mutation races, decompression, and immutable export. Contender 5 records SSH lifecycle and source mutation incidents but assigns no acquisition component requirements and tests none of those paths. A malicious Git object stream or local working tree can attack before the provider/analyzer controls begin.

3. **Must-fix — adopting the hostile-runtime architecture by reference is not a safety conformance specification (§13.5; gate 5).** “Compile Compose before pull/build/create; reject unsafe references” does not enumerate remote/escaping contexts, include/extends, privileged/device/namespace/sysctl/runtime/provider/hook fields, bind/external volumes, mutable images, host ports, platform mismatch, cgroup failure, forged helper MACs, stale fences, or cleanup ownership. Gate 5 says the architecture matrix must pass, but §14 supplies no negative fixtures for these individual controls or their fail-to-coverage transitions.

4. **Must-fix — build/Git allowlists do not close approved-destination exfiltration (§§6.1, 7.2, 14.3, 16).** The spec correctly admits that an approved Git or registry endpoint remains an exfiltration channel, but it does not state whether untrusted build steps ever receive acquisition egress or prove that only a trusted broker—not a Dockerfile/package hook—can originate allowed fetches. Test the path where malicious source encodes repository bytes in requests to an otherwise approved registry/dependency host, including DNS labels, URLs, headers, and request bodies.

5. **Must-fix — target-controlled artifact collection after secret exposure has an unbounded covert channel (§8 and §14.6).** A hostile target deliberately receives a sandbox credential, then may encode or split it into logs, HTTP output, images, filenames, timings, or declared artifacts that move through `vm.collect`. Secret scanners and screenshot re-encoding detect known representations, not arbitrary encryption or steganography. Restrict collection after secret delivery to trusted-probe-generated structured results and explicitly bounded derivatives, or record and customer-disclose this residual path.

6. **Should-fix — local UI/session threats are named but not verified (§3 last row; §13.2/13.7).** The threat model cites LAN/local theft of the bootstrap token/session and abuse of download/deletion, but §14 has no tests for loopback-only binding, one-use fragment removal, SameSite session behavior, exact-origin rejection, stale row versions, token replay/expiry, CSRF-like requests, or package/download authorization. The architecture supplies these mechanics; P2 should own their abuse cases.

7. **Should-fix — the audit catalogue is broad but not contract-complete (§11; §13.1).** “Define strict schemas/enums” plus a prose event list does not freeze event names, producer, required/safe optional fields, transaction ordering, deduplication, retention, and correlation for each event. Architecture `RunEvent` lacks most approval, secret, egress, incident, and deletion events, so either versioned audit DTOs or an explicit separate audit record are needed.

8. **Should-fix — provider refusal behavior is ambiguous (§7.1).** Dispatch is blocked until the operator explicitly continues, but the spec does not state whether refusal ends the run, permits a deterministic scanner-only package, or creates a specific blocked/unsupported coverage state. Because both provider paths are MVP requirements, the UI and workflow need a single safe outcome rather than an implementation choice.

9. **Should-fix — reviewer governance is only partially frozen (§9.2; gates 8 and 10).** Fresh context, no author transcript, input evidence, and same-provider labeling are good controls, but reviewer eligibility, human role independence, disagreement resolution, re-review after evidence/report/package changes, and unavailability behavior are not explicit. All unavailable mandatory reviews should deterministically block packaging.

## Concrete fixes

1. Add a versioned runtime-control authorization schema and matrix. Define at least passive observation, read-only unauthenticated, read-only authenticated, narrowly reversible sandbox mutation, and prohibited classes. Bind every planned control to exact internal origin, route/action, HTTP methods/protocols, redirect policy, account/tenant, credential handle/purpose, synthetic data, request/rate/byte budget, allowed side effects, cleanup proof, evidence outputs, abort triggers, and coverage result on denial or interruption.
2. Add adversarial dynamic fixtures for cross-origin redirects, forms, JavaScript/navigation requests, WebSockets, downloads/uploads, login POST versus destructive POST, CSRF-like controls, account/tenant crossing, reversible-mutation rollback failure, emergency revocation mid-request, and production-like endpoint/credential sentinels. Enforce the policy in a trusted broker/proxy outside the target and browser process.
3. Add an explicit P2 adoption/rejection table for architecture §§9–10. For every source-acquisition, host-helper, Compose compiler, Lima/rootless/cgroup/firewall, broker, snapshot-transfer, build-acquisition, cleanup, and emergency-stop control, name the enforcer, immutable inputs, fail state, audit event, negative fixture, and residual risk.
4. Complete the VM-envelope review: freeze X25519 key validation/generation, HKDF salt/info, AES-GCM nonce generation, canonical JCS associated data, recipient identity, replay cache, expiry skew, one-use redemption ordering, key/plaintext zeroization limits, crash residue, malformed input, and cancellation/reconciliation behavior.
5. Add acquisition and approved-destination exfiltration tests: malicious Git server/object graphs, hooks/config/filters, LFS/submodules, symlink/path/Unicode/special-file/mutation/decompression bombs, hostile Dockerfile/package steps, and encoded uploads to approved Git/registry/dependency endpoints. Require build to be offline after trusted broker acquisition and forbid target-controlled network clients.
6. Restrict evidence export after sandbox-secret delivery to trusted-probe structured results and predeclared safely transformed derivatives. Test split/encoded/compressed/encrypted/steganographic canaries across multiple artifacts, and disclose the detection limit rather than claiming scanners close it.
7. Add loopback UI/session abuse tests and freeze a versioned audit-event contract plus reviewer workflow. Specify provider-refusal outcome, mandatory-review unavailability, disagreement, re-review triggers, and deterministic packaging effects.

## Verdict

**Revise.** Contender 5 clears a very high bar for prompt-injection containment, provider authority, consent, evidence honesty, privacy, incident response, and release gating. It misses P2’s ship bar because dynamic probes have no positive action-authorization model, and source acquisition, the full hostile-runtime rejection matrix, and the VM-secret cryptographic boundary remain reviewed only by reference rather than with safety-owned controls and adversarial proofs.
