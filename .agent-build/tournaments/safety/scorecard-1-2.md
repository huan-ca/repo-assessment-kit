## Scores

- **Requirements coverage — 8.0/10.** Sections 2–16 cover nearly every P2 topic in unusual depth, including hostile source, nested runtime, credentials, prompt injection, evidence, incident response, compliance wording, and release tests; however, P2's runtime-test safety classes, audit-event contract, and severity/confidence/validation rules are absent rather than merely terse.
- **Assets, attacker model, and trust boundaries — 9.0/10.** Sections 2–3 explicitly model malicious Git/package/image endpoints, compromised parsers/browser/daemon, prompt-following providers, cross-run confusion, and the host/helper/VM/broker boundaries; the main weakness is that trusted control-plane compromise is largely relegated to residual risk without an enforcement-owner matrix for each invariant.
- **Prohibited actions and authorization — 7.0/10.** Sections 1, 3, 7, 9, and 10 provide a strong default-deny set and prevent provider proposals from becoming authority, but dynamic-control authorization is reduced to “separately approved” mutating methods without a versioned action class, side-effect budget, rollback rule, or independently enforced request policy.
- **Container, nested-runtime, and source-isolation controls — 8.5/10.** Sections 5, 6, and 8–11 specify no-follow acquisition, disposable static workers, mount-free Lima, broker-only rootless Docker, compiled Compose, cgroups, firewalls, resource ceilings, and hostile fixtures; “default seccomp” for host-side analyzer containers is not a pinned policy, and broker/probe/target east-west ACLs are not fully frozen.
- **Credential lifecycle and secret handling — 7.0/10.** SSH acquisition and VM envelopes have precise recipient, use, expiry, replay, tmpfs, cancellation, and cleanup controls (§§5.1, 8.3), while provider homes are separated (§7); but SI-04's claim that provider auth exists “only” in a provider home conflicts with DECISIONS' environment-credential and `.env` launch modes, and age-wrapper key/passphrase ingress, lifetime, recovery, and deletion are not specified.
- **Network egress and hosted-service controls — 5.5/10.** Section 10 correctly separates build from runtime, denies IPv4/IPv6/DNS bypass, blocks LAN/metadata paths, and records approvals, but §10.1 cannot enforce or log approved HTTPS path prefixes, HTTP methods, or data categories through an ordinary CONNECT proxy, and the spec simultaneously concedes that malicious build code can send repository bytes to an approved destination. Optional hosted-service transport and revocation receive no equally concrete mechanism or acceptance suite.
- **Safe dynamic testing and emergency control — 6.0/10.** Sections 10.2, 11, and 13 give strong isolation, budgets, forced stop, secret revocation, and residue handling, but there is no required runtime-test taxonomy for passive, read-only, authenticated-read, reversible sandbox mutation, exploit validation, and prohibited actions. Because the compromised-browser threat is explicit, an in-browser prohibition on mutating methods is not an independent enforcement point.
- **Prompt injection and untrusted-content defense — 8.5/10.** Section 7 treats target text as data, limits provider operations to five typed verbs, isolates homes/views/outboxes, makes output non-authoritative, and tests command, credential, policy, evidence, and package attacks; it does not specify how a provider engagement home is protected from persistent configuration/session poisoning by a compromised CLI or when such a home must be discarded.
- **Evidence integrity, privacy, redaction, and packaging — 8.0/10.** Sections 6, 12, and 14 bind receipts to current fences, parse under limits, quarantine malformed output, serialize reports from typed ASTs, re-encode safe previews, rescan every package boundary, and reopen the ZIP; raw active evidence is safe in the authenticated UI via attachment headers but its handling after ZIP extraction is unspecified, where those headers no longer protect the customer.
- **Failure, incident response, and auditability — 6.0/10.** Sections 11 and 13 provide concrete stop ordering, deadlines, quarantine, credential rotation, cleanup, and honest blocked coverage, but §13 invents `SECURITY_HOLD`, which does not exist in architecture §6.1's frozen run-state machine, and there is no versioned audit-event catalogue for approval, egress, secret redemption, policy denial, attestation drift, incident, or cleanup events.
- **Finding governance and compliance-language safety — 5.5/10.** Section 4 appropriately restricts applicability and compliance claims, and §§14–15 make High/Critical states release-significant, but the spec never defines technical-severity assignment, confidence meaning, validation-state transitions, CVSS sufficiency, imported findings, disputes, supersession, reviewer independence, or what “unaccepted” means.
- **Verification, ownership, and parallel buildability — 7.0/10.** Section 14 is an excellent hostile fixture inventory across acquisition, analyzers, providers, VM, Compose, egress, secrets, evidence, and packages, but several promised tests lack a realizable oracle or frozen contract—especially HTTPS method/path/data enforcement, continuous invariant attestation, runtime action authorization, security hold, and audit/finding governance—so P4/P5 would still have to make security-critical design choices.

## Overall

**7.2/10 (equal-weight average).** This is a strong hostile-repository containment design and likely a valuable synthesis source, but it does not clear P2's implementation-freeze bar because some of its most important consent and authorization claims cannot be enforced or objectively verified with the mechanisms specified.

## Strongest objection

**Must-fix — Section 10.1 promises an egress policy the stated proxy cannot enforce.** Every build exception includes `path prefix`, `methods`, and `data categories`, and the proxy is required to log the method, yet target-controlled package managers and build scripts normally use end-to-end HTTPS through CONNECT. Without trusted TLS termination or a release-owned application-layer fetch gateway, the proxy can observe destination/port and connection bytes but not the HTTP method, URL path, or whether the encrypted body contains an approved data category. The same section admits that the destination remains a repository-exfiltration channel, directly undercutting §1.5's claim that every exception is data- and purpose-scoped. This is not a documentation nicety: the operator consent, architecture `Approval` DTO, egress audit receipt, and release tests all depend on properties the enforcement point cannot observe. P4/P5 would have to add a CA/MITM design, build an application gateway, or silently weaken the promised scope.

## Other findings

1. **Must-fix — Runtime-test authorization is not a contract (§10.2).** “Mutating HTTP methods are denied unless the exact non-production flow is separately approved” does not define safety classes, permitted methods/actions, origin and route scope, credential purpose, request/body limits, expected side effects, cleanup, or coverage behavior after partial mutation. Architecture exposes only an opaque `controlPlanId`; implementations cannot make equivalent Codex/Claude decisions or prove AC-4's destructive-action prohibition.
2. **Must-fix — The stated threat model defeats the probe's apparent request guard (§§2.2, 10.2).** The spec assumes browser compromise but places the method/origin restrictions on the “trusted Playwright/passive probe” without identifying an out-of-process network policy between that probe and target services. Once compromised, the browser can issue arbitrary internal requests unless a broker-owned L7 enforcement point validates a frozen control plan.
3. **Must-fix — Incident containment is incompatible with the frozen lifecycle (§13.2).** `SECURITY_HOLD` is absent from architecture §6.1, the canonical RunEvent enum, SQLite transitions, OpenAPI, and SSE. There is no legal transition into the state and no defined terminal/new-run relationship, even though package eligibility depends on it. Either the canonical profile must be versioned or the hold must be represented by an existing run state plus a typed blocking disposition.
4. **Must-fix — Auditability is asserted, not contracted (§§8, 10, 13).** The spec repeatedly says records are journaled or audited, but it does not enumerate event names, trusted producers, required correlation fields, ordering/transaction guarantees, redacted payloads, retention, or export status for approvals, revocations, proxy decisions, envelope redemption, attestation drift, policy rejection, emergency stop, and residue. Architecture §8.8's RunEvent union cannot represent most of these events.
5. **Must-fix — Finding gates have undefined inputs (§§14.3, 15.1).** “Any bypass is Critical,” “unaccepted Critical/High vulnerability,” and independent reviewer approval are not enough to define the general security-finding lifecycle required by P2. Without severity, confidence, validation, dispute, supersession, CVSS, and reviewer-independence rules, equivalent agent outputs can produce different release decisions.
6. **Must-fix — Provider authentication contradicts an approved launch mode (§§3 SI-04, 7).** The invariant says provider auth exists only in its provider/engagement home, while DECISIONS explicitly requires environment credentials and gitignored `.env` support as alternatives. The spec does not define a launcher-only import into the home, process-environment scrubbing, `/proc` protection, crash handling, or whether imported tokens persist, so the invariant is neither implementable across all required modes nor testable as written.
7. **Must-fix — Build acquisition does not enforce its claimed data boundary (§10.1).** Destination approval plus disclosure limits the recipient but cannot prevent hostile repository-controlled build code from uploading source to that recipient. Prefer trusted lockfile/image resolution and out-of-process fetching followed by a physically networkless build; otherwise make repository-byte disclosure an explicit high-risk approval category and stop describing the channel as data-scoped.
8. **Must-fix — Optional hosted services are present in the data map but absent from the execution contract (§§4, 10).** There is no compartment, typed request/receipt, TLS/auth design, payload-subset proof, response normalizer, revocation behavior, or dedicated adversarial test comparable to build/provider egress. A generic “exact disclosed recipient” leaves P5 to invent a high-risk boundary.
9. **Should-fix — Exported active evidence loses UI attachment protections (§12).** `Content-Disposition`, CSP, and `nosniff` protect browser delivery from the local server, not files extracted from a ZIP. If raw HTML/SVG/XML/PDF or scanner output is customer-deliverable, package it in an inert encoded envelope or safe textual derivative with warnings and neutralized filenames; otherwise exclude it and expose only admitted safe derivatives.
10. **Should-fix — “Continuously attested” overstates what is specified (§3).** The VM has phase-boundary drift checks, but provider mounts/network, static analyzer confinement, helper key state, and package staging do not have comparable cadence, sensor, failure transition, or durable evidence. Distinguish release-test invariants from runtime-monitored invariants and name the attestation owner and receipt for each.
11. **Should-fix — Reviewer independence is not mechanically defined (§7, §15).** A “fresh-session independent reviewer” could still be the same provider, model, instruction bundle, or author identity. Define prohibited self-review relationships, exact input digest, stored verdict, disagreement path, re-review triggers, and safe behavior when an eligible reviewer is unavailable.

## Concrete fixes

1. Replace the ambiguous build proxy with one enforceable design: a release-owned dependency/image fetch gateway that constructs requests from typed lock/digest inputs, or explicitly specified TLS termination with CA lifecycle and real package-manager compatibility tests. Align approval UI and audit receipts to only observable/enforceable properties.
2. Add a versioned runtime-action matrix. Every control plan must declare safety class, origin, method, route, input/data category, credential purpose, maximum requests/bytes/rate, permitted side effect, cleanup proof, evidence type, abort triggers, and exact coverage result on denial or interruption.
3. Put probe authorization outside the browser process. Route probe-to-target traffic through a broker-owned enforcing proxy or equivalent ACL boundary that consumes the signed control plan and remains effective after browser compromise; add raw-socket, redirect, WebSocket, upload/download, service-worker, and malicious-page bypass fixtures.
4. Reconcile `SECURITY_HOLD` with `rak-contract/1.0.0`: version the run state, persistence, OpenAPI, reducers, SSE, recovery, retention, and package gates, or define a typed security disposition mapped to legal existing states.
5. Add a schema-versioned audit catalogue with event, producer, trigger, run/attempt/fence, actor/workload, approval/policy/input digests, safe fields, transactional ordering, retention, and package visibility for every security-relevant authority change and denial.
6. Freeze security-finding governance: technical severity, business priority, confidence, validation state, CVSS/CWE rules, imported-finding behavior, independent-review eligibility, dispute/supersession transitions, acceptance authority, and release effect for every state.
7. Reconcile provider credential modes by defining an exact launcher import channel, allowed process boundary, environment/proc scrubbing, home permissions, engagement disposal, rotation/revocation, crash recovery, and conformance tests for both real pinned CLIs.
8. Split dependency fetching from target-controlled build execution where possible; otherwise elevate the actual source-exfiltration possibility into the approval's disclosed data category and per-run residual-risk record rather than claiming semantic data enforcement.
9. Specify the optional-service gateway and age-wrapper secret lifecycle with the same rigor as VM envelopes: recipient/purpose/run binding, payload digest and category proof, one-use credentials, expiry/revocation, response quarantine, audit receipt, cleanup, and negative tests.
10. Define ZIP-safe handling for active raw evidence and publish an invariant/attestation matrix that distinguishes compile-time tests, per-dispatch checks, continuous monitors, and package gates with named owners and evidence receipts.

## Verdict

**Revise.** The contender clears the bar for hostile-source modeling, container/VM confinement, prompt-injection containment, safe failure, and an unusually strong adversarial test corpus. It misses the P2 ship bar because its method/path/data-scoped egress promise is not realizable with the specified proxy, runtime action safety is not a versioned independently enforced contract, and incident/audit/finding controls drift from or fail to complete the frozen architecture.
