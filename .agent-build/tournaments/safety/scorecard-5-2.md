## Scores

- **Requirements coverage — 8/10.** The contender covers nearly every P2 subject with concrete requirements, especially provider prompt injection, optional-service disclosure, evidence safety, incidents, and release gates; however, PLAN P2 explicitly requires “runtime-test safety classes,” and §§13.5, 14, and 15 provide containment tests but no normative safe/prohibited probe classes, browser-action policy, method/route limits, or per-control authorization contract.
- **Assets, attacker model, and trust boundaries — 9/10.** §§2–3 identify provider homes, SSH, source, credentials, evidence, packages, host/VM components, local attackers, malicious dependencies, compromised tools, and decision-quality harm, while §2.4 honestly retains approved recipients as exfiltration risks; a data-flow matrix tying each boundary to its enforcing process and test would make this complete.
- **Prohibited actions and authorization — 8/10.** §6.2 gives a strong non-waivable prohibition list and §6.1 binds approvals to destination, methods, data, credential handle, expiry, and policy, but it says only “a human operating the authenticated loopback UI” may approve and does not freeze which roles can approve each capability or reconcile its added `purpose`, `maximum bytes`, `policy digest`, and residual-risk fields with architecture §8.7’s frozen `Approval` DTO.
- **Container, nested-runtime, and source-isolation controls — 7/10.** §§5.1, 13.4, and 13.5 preserve minimal provider/analyzer compartments and the architecture’s VM/rootless/firewall boundary, but the most important provider credential separation is delegated to unspecified “Managed Codex and Claude policy,” and the spec mostly references rather than reviews the architecture’s source-acquisition, Compose compilation, build, and nested-runtime controls.
- **Credential lifecycle and secret handling — 7/10.** §§5, 8, 12, and 14 define separate homes, ephemeral SSH use, one-use handles, canaries, revocation, cleanup, and package exclusions; nevertheless, architecture §10.3 explicitly says `safety.md` “must review” the X25519/HKDF/AES-GCM VM envelope, while contender §15.11 merely repeats replay/recipient/expiry/cleanup as an open gate and never reviews key generation, nonce uniqueness, AAD encoding, key zeroization, or cryptographic failure behavior.
- **Network egress and hosted-service controls — 8/10.** §§6–7 and 14.3 give optional services exact destinations, data categories, approvals, TLS/path/size/time enforcement, redirect and DNS-rebinding denial, revocation, and no fallback; provider inference and build/Git acquisition do not receive the same payload-method/path policy, so §2.4’s acknowledged allowed-destination exfiltration path is disclosed but not bounded enough to be testably minimized.
- **Safe dynamic testing and emergency control — 6/10.** §§12 and 13.5 provide a strong stop order, fenced recovery, VM teardown, and containment release gate, but there is no safety-class taxonomy for probes, no automatic-versus-human-authorized action matrix, no role/tenant/test-data boundaries, no request/response budget contract, and no adversarial fixture showing browser/HTTP tooling cannot mutate application state; this is a direct P2 requirement gap.
- **Prompt injection and untrusted-content defense — 7/10.** §§4–5 contain excellent instruction precedence, typed evidence envelopes, five-command capability restriction, proposal-only output, and laundering tests, but §5.1 requires the same provider compartment to expose authentication to the CLI while somehow denying it to CLI-invoked tools without specifying a separable OS enforcement boundary; §14.1’s “repeat enough times” is not a reproducible acceptance criterion and cannot prove this control.
- **Evidence integrity, privacy, redaction, and packaging — 9/10.** §§5.3, 8, 9, 13.6, 14.5–14.6, and gate 10 cover bounded admission, typed rendering, derivatives, screenshot re-encoding, staged redaction, secret/path scans, review, manifest/checksum validation, and ZIP reopening; the statement “Gitleaks matching values are never retained” in §8 conflicts with retaining the immutable source snapshot and needs a storage-class-qualified meaning.
- **Failure, incident response, and auditability — 9/10.** §§11–12 define broad typed audit content, security-stop triggers, an ordered containment sequence, incident classes, human disposition, stale-fence rejection, crash reconciliation, and residue release blocking; implementation is weakened by leaving the promised audit event catalogue as prose while architecture §8.8 freezes a much smaller `RunEvent` enum.
- **Finding governance and compliance-language safety — 9/10.** §§9–10 cleanly separate severity, business priority, confidence, validation, applicability, and coverage; constrain CVSS; require independent review; prevent security-only rebuild conclusions; and deterministically flag prohibited compliance/certification claims. The remaining ambiguity is the unversioned “named RAK rubric” for non-CVSS findings.
- **Verification, ownership, and parallel buildability — 7/10.** §§13–15 map controls to package owners and unusually rich abuse cases across both providers, but critical tests lack executable profiles: no defined network-capture/MITM mechanism for comparing the digest of an encrypted provider request, no exact repetition/sample rule for nondeterministic injection tests, no runtime probe safety suite, and no schema migration plan for requirements that extend frozen architecture DTOs.

## Overall

**8.0/10.** This is a strong, product-wide safety contender with excellent hostile-content, evidence, incident, and governance coverage. It reaches the numerical review threshold, but a critical provider-boundary control is presently asserted rather than implementably separated, and the P2-required dynamic-test safety classes are absent.

## Strongest objection

**Must-fix — the provider credential/tool boundary in §5.1 (lines 198–216) is not an enforceable architecture.** The provider CLI runs in one compartment, its authentication is “mounted only where the CLI requires it,” and “Managed Codex and Claude policy” is then expected to deny reads of those same authentication/session/config paths to filesystem tools and shell subprocesses. The spec does not identify a distinct credential broker, privilege boundary, syscall broker, tool-runner UID, mandatory-access-control profile, or provider capability proven to make a file readable to the CLI but unreadable to code that the same CLI can spawn. The architecture’s launch modes (`codex exec --sandbox workspace-write` and `claude -p --permission-mode dontAsk`) do not themselves establish that separation.

This matters because prompt injection is the contender’s Critical threat and release gate 1. A model-driven test that happens not to leak a canary cannot prove the isolation property, especially under §14.1’s undefined “repeat enough times.” P4/P5 would have to invent the actual security boundary, or discover that a required provider cannot satisfy it, after the spec is frozen.

## Other findings

1. **Must-fix — required dynamic-test safety policy is missing (§§13.5, 14, and 15.5).** The contender tests VM containment and emergency behavior but never defines the PLAN-required runtime safety classes: which HTTP/browser actions are automatically safe, which require scoped approval, which are always prohibited, how methods/origins/routes/roles/tenants/test identities are bound, and how request, response, mutation, and time budgets are enforced. A contained browser can still perform destructive application actions.

2. **Must-fix — the safety spec extends frozen architecture contracts without a versioned reconciliation (§6.1 lines 278–289; §11 lines 522–538; §13.1).** Its approval requires purpose, maximum bytes, policy digest, expected coverage benefit, and residual risk, none of which exist in architecture §8.7’s `Approval`. Its detailed audit events also exceed architecture §8.8’s closed `RunEvent.type` union. Implementers cannot honor both “strict unknown-field rejection” and these safety requirements without an explicit DTO revision or separate linked records.

3. **Must-fix — architecture’s mandatory VM-envelope security review is not performed (§15.11).** The contender names replay, wrong-recipient, expiry, and cleanup testing but does not assess X25519 key validation, HKDF salt/info/domain separation, AES-GCM nonce construction and uniqueness, canonical AAD representation, crash residue, broker private-key lifetime, or zeroization limits. Architecture §10.3 explicitly delegates that review to `safety.md`.

4. **Must-fix — prompt-injection acceptance is partly statistical and partly unobservable (§14.1 lines 717–736).** “Repeat enough times” supplies no pinned model list, trial count, stopping rule, fixture corpus version, or flake policy. “No canary appears in provider request payloads” has no specified observation point for TLS-encrypted provider traffic. The deterministic command/filesystem/network boundary should be tested independently of model behavior, and model trials should be a defense-in-depth conformance test with a fixed profile.

5. **Must-fix — approved acquisition/provider endpoints remain weakly constrained (§2.4, §7.1, §14.3).** Optional services receive proxy-enforced method/path/size controls, but Git, registry, dependency, build, and provider flows are mostly identity-separated and audited. A malicious build or source path can still upload bytes to an approved registry or package host unless each class has fixed client operations, upload denial, destination/path rules, byte budgets, and egress receipts.

6. **Must-fix — §8’s “Gitleaks matching values are never retained” (line 406) contradicts the immutable source snapshot retained for the run (line 382).** A target may already contain a matching secret. The rule must distinguish immutable quarantined source from extracted values, logs, evidence derivatives, prompts, previews, and packages; otherwise it is impossible to satisfy and impossible to test consistently.

7. **Should-fix — approval authority is under-specified (§6.1).** “A human operating the authenticated loopback UI” does not say whether an operator, engagement security reviewer, customer owner, or package recipient may approve provider disclosure, optional-service egress, sandbox credentials, or incident resumption. Freeze a capability-by-role matrix and non-self-approval rules for sensitive actions.

8. **Should-fix — provider resume safety cannot be proven from digests alone (§12.4).** Matching session, target, evidence, instruction, policy, approval, capability, schema, and fence digests is necessary, but the spec should also require adapter evidence that no unsupported CLI-side context, project index, connector state, or cached tool result survived; otherwise “fresh session” and “matching session” remain provider-specific assertions.

## Concrete fixes

1. Replace §5.1’s managed-policy assertion with a concrete provider execution profile. Prefer a separate authenticated inference proxy or ephemeral workload identity so the task process has no readable credential file; run model-callable tools in a distinct brokered process with no provider home, generic exec, or provider network. Freeze the supported Codex/Claude versions and the exact OS controls, mounts, UIDs, seccomp/MAC rules, IPC protocol, and negative syscall/filesystem/network tests. If either CLI cannot satisfy the profile, declare it unsupported at architecture time rather than leaving P4/P5 to discover that.
2. Add a normative runtime-test chapter: safety classes, allowed method/action matrix, origin/route/redirect rules, role/tenant/test-account binding, credential purpose, data and mutation budgets, request/response capture limits, passive versus active techniques, stop conditions, and exact coverage outcomes. Add fixtures that attempt POST/PUT/PATCH/DELETE, logout/password changes, emails/webhooks, purchases, cross-tenant access, and navigation to production-like endpoints.
3. Publish a `rak-contract` revision or explicit extension DTOs for approval disclosure scope, transmission records, security-stop/incident records, and the full audit event catalogue. Provide architecture-to-safety field mappings, reason-code enums, state-transition ownership, JSON Schema golden fixtures, and migration rules.
4. Complete the VM secret-envelope review with exact KDF salt/info and domain separation, public-key validation, nonce generation/uniqueness, canonical AAD fields/encoding, private-key and plaintext lifetime, crash/replay behavior, error normalization, and test vectors for wrong run/runtime/recipient/purpose/approval/fence/time.
5. Split prompt-injection verification into deterministic isolation tests and model-behavior tests. The former must prove denied mounts/syscalls/tools/routes without invoking a model. The latter must pin provider/CLI/model versions, corpus digest, trial count, timeout, capture point, and zero-tolerance failure rule; use an explicit trusted proxy or adapter hook to hash the exact sanitized request before TLS.
6. Define fixed egress profiles for provider, Git, tool update, build acquisition, target runtime, and optional services, each with its own identity, client operation set, destinations, methods/path prefixes, upload policy, data categories, byte/time budgets, certificate/DNS behavior, revocation, and receipts. Add exfiltration attempts to allowed hosts, not just denied-host tests.
7. Qualify §8’s Gitleaks requirement by storage class: source-secret occurrences may remain only in the immutable access-controlled snapshot/quarantine required for assessment, while extracted raw values must never enter SQLite, audit, provider prompts, previews, reports, packages, or logs. Test every named class.
8. Freeze capability-to-role approval and incident-disposition matrices, including dual-control/non-self-approval where warranted, then add authorization tests for every role and capability.

## Verdict

**Revise.** The contender clears the breadth and rigor bar and should be a leading synthesis source, but it does not yet clear P2’s “every trust boundary and prohibited action with enforceable controls and verification methods” bar. Shipping requires a realizable provider credential/tool boundary, normative runtime-test safety classes, frozen contract reconciliation, and the delegated VM-envelope review.
