## Scores

- **Requirements coverage — 5/10.** Sections 4–15 are a deep safe-dynamic-testing specification, but PLAN P2 requires the whole product boundary: malicious-source acquisition, provider/SSH credential handling, static analyzer execution, prompt injection, optional hosted services, package release safety, typed audit events, and finding governance are absent or only mentioned.
- **Assets, attacker model, and trust boundaries — 6/10.** Section 3 correctly treats the repository, build inputs, target, browser, ZAP, provider task, and operator mistakes as hostile, but it does not decompose attacker capabilities or trace the outer sandbox → provider/static analyzer → host helper → VM broker → target/probe → evidence/package boundaries; the only complete paths are dynamic-probe paths.
- **Prohibited actions and authorization — 7/10.** Sections 4 and 6 provide excellent runtime authorization binding and an unusually explicit `PX-PROHIBITED` list, but there is no equivalent authority matrix for source acquisition, provider tools, static analyzers, build instructions, optional scanners, evidence admission, or package release.
- **Container, nested-runtime, and source-isolation controls — 7/10.** Section 5 requires the frozen Lima/rootless/cgroup/firewall/compiler controls and DYN-01/08/11/16 test them, but the spec delegates the rejection policy to architecture §10.2 rather than reviewing every rule and does not close malicious Dockerfile/build-step exfiltration through approved acquisition destinations.
- **Credential lifecycle and secret handling — 6/10.** Sections 4, 7, 11, 13, and DYN-05/06/13 are strong for target credentials, one-use handles, context isolation, and VM cleanup, but the P2-required SSH keys/agent sockets, provider homes/tokens, optional-service secrets, engagement-home disposal, and full envelope cryptographic profile are not specified end to end.
- **Network egress and hosted-service controls — 5/10.** Sections 5.4–5.6 and DYN-02/11 strongly deny runtime/public/LAN/metadata traffic, but provider inference, Git acquisition, build acquisition, target runtime, and optional-service egress never receive distinct state machines, revocation/failure behavior, DNS/IP rebinding controls, or per-flow data/method enforcement; §11.1 merely says hosted flows need separate approval.
- **Safe dynamic testing and emergency control — 8/10.** Safety classes, role/tenant matrices, locked adapters, budgets, stop conditions, cleanup, coverage semantics, and sixteen adversarial fixtures are excellent; the score is capped because §6 places the “final enforcement point” in the request interceptor despite §3.2 treating the browser as compromised, and the authorization order is internally circular.
- **Prompt injection and untrusted-content defense — 4/10.** Sections 1, 3.2, and 8.1 say provider recommendations have no authority and DOM text is not instruction, but there is no instruction-precedence contract, provider tool allowlist, context partition, canary handling, approval non-delegation protocol, audit event, or Codex/Claude fixture proving hostile repository/scanner/page text cannot induce execution, egress, secret access, or policy weakening.
- **Evidence integrity, privacy, redaction, and packaging — 6/10.** Sections 10–12 precisely constrain dynamic occurrences, screenshots, response data, lineage, and coverage claims, but they do not specify the architecture’s general admission boundary, active-content rendering, redaction derivations, package-stage certificates, ZIP reopen/tamper checks, or handling of hostile static/provider outputs.
- **Failure, incident response, and auditability — 7/10.** Section 13 gives a strong dynamic incident sequence with non-resumable attempts and cleanup re-attestation, but there is no normative product-wide audit-event catalogue or incident handling for source acquisition, prompt injection, provider compromise, static tools, optional hosted flows, evidence admission, review, or package delivery.
- **Finding governance and compliance-language safety — 5/10.** Sections 2 and 12 correctly restrict compliance claims and dishonest coverage, yet the spec never freezes technical severity, business priority, confidence, validation state, CVSS prerequisites, imported-finding treatment, dispute/supersession rules, or release effects beyond separately reviewing Critical/High dynamic findings.
- **Verification, ownership, and parallel buildability — 7/10.** Sections 14–15 map dynamic controls to strong native-platform fixtures and owning packages, but an implementation could pass all sixteen groups without testing provider prompt injection, SSH/provider secret isolation, malicious static analyzers, approved-destination exfiltration, optional hosted-service behavior, general audit events, or the final package boundary.

## Overall

**6.1/10.** This is a strong, nearly buildable safe-dynamic-testing subsystem, but it is not the complete safety specification required by P2. The average reflects excellent runtime detail offset by major unmodeled product attack paths.

## Strongest objection

**Must-fix — the specification scopes away the highest-leverage pre-runtime attack path.** Section 2 (lines 40–49) limits governance to runtime candidacy, runtime credentials, Playwright/ZAP, dynamic evidence, and runtime incidents, even though Section 3.2 explicitly identifies repository instructions, dependencies, build steps, scanner output, and a compromised provider task as untrusted (lines 76–87). No later section closes:

`malicious repository/instruction or scanner output → Codex/Claude/provider decision or static/build proposal → approved provider/build/optional-service channel or host-helper operation → source/credential disclosure, unsafe execution, or authoritative evidence/package state`.

The only prompt-injection controls are “no policy authority” (§1) and “DOM text is untrusted evidence” (§8.1); there is no provider capability boundary, typed tool policy, instruction precedence, context separation, approval-creation denial, injection audit event, or dual-provider adversarial test. DYN-01 through DYN-16 can therefore all pass while a hostile repository manipulates a provider or pre-runtime build/static path into leaking source through an approved destination or proposing unsafe authoritative state. That directly misses PLAN P2’s requirement to cover **every trust boundary and prohibited action** and would force foundational safety design into P4/P5.

## Other findings

1. **Must-fix — the “final enforcement point” shares a failure domain with an explicit adversary (§3.2 lines 84–85; §6 lines 257–261).** The spec treats a compromised browser process as an attacker, then relies on the Playwright/browser request interceptor as the final method/origin/path control. A browser escape or adapter compromise can bypass that interceptor and reach other internal services. Method, origin, route, redirect, byte, and request-budget enforcement must also occur in a broker-owned, out-of-process proxy/network boundary that the browser and target cannot modify.

2. **Must-fix — runtime authorization has a circular lifecycle (§4 lines 157–161; §5 lines 182–185).** The gate and authorization must complete before image pull/build/container creation, but authorization is bound to actual image digest, internal origin/service map, and route changes; architecture `vm.build` and `vm.start` produce image digests and internal origins only afterward. The spec lacks separate pre-build acquisition consent and post-build probe authorization, so a conforming implementation either deadlocks or authorizes values not yet proven.

3. **Must-fix — approved destinations remain an executable exfiltration path (§4 lines 131, 170–171; §5 lines 203–206; §16 lines 627–629).** Exact host allowlisting does not prevent a malicious Dockerfile, target dependency, or optional adapter from sending source/evidence to an allowed registry or sandbox endpoint. The spec needs phase-specific proxy identities, allowed methods/path prefixes, upload denial or strict data-category budgets, DNS resolution pinning/revalidation, destination certificate policy, byte receipts, and fail-closed revocation.

4. **Must-fix — prompt-injection treatment is declarative, not enforceable (§1 lines 34–36; §3.2 line 80; §8.1 line 334).** There is no fixed provider task envelope, safe read-only evidence API, denial of helper/secret-broker/approval/package access, output-as-proposal rule, injection-marker propagation, or malicious instruction fixtures across repository files, filenames, comments, analyzer output, and runtime pages.

5. **Must-fix — secret coverage is limited to target runtime credentials (§7 and §11).** The brief and architecture also protect SSH material, provider authentication/homes, optional-service credentials, package passphrases/recipient keys, and secrets retained across retries. Their capture, recipient, storage, redemption, cancellation, rotation, cleanup, and canary tests are not governed here.

6. **Must-fix — the frozen VM envelope is tested but not actually reviewed (§7.1; DYN-05).** Architecture §10.3 requires safety review of X25519/HKDF/AES-GCM associated-data binding. The contender says “encrypted VM envelope” and tests wrong recipient/replay/expiry, but does not validate key generation/zeroization, nonce uniqueness, HKDF salt/info, AEAD associated-data canonicalization, service recipient identity, crash residue, or cryptographic failure behavior.

7. **Must-fix — source acquisition, static analyzer, and build execution policies are incomplete (entire spec).** There is no prohibition/test for Git hooks, LFS/submodule/filter execution, repository package managers and install scripts, target scanner configs/plugins/reporters, remote build contexts, mutable registry responses, or supply-chain substitution. Referring to architecture §10.2 covers Compose fields, not all source-to-execution paths.

8. **Must-fix — product-wide auditability is missing (§13 and DYN-15).** Define typed, safe-payload audit events for capability/approval changes, credential issue/redeem/revoke, prompt-injection encounters, source/helper/broker commands, egress decisions/bytes, policy denials, runtime stop/cleanup residue, evidence admission/rejection, finding review, incident declaration, and package release, with actor/correlation/fence IDs and retention.

9. **Must-fix — finding governance is insufficient (§10, §12, §15.7).** “Critical/High” is release-significant but has no assignment algorithm. Separate severity, business priority, exploitability, confidence, validation, provenance, and reviewer outcome; define CVSS requirements, imported/tool finding normalization, disagreement, supersession, false-positive handling, and package/release consequences.

10. **Should-fix — the dynamic evidence controls do not protect the complete package boundary (§11 lines 460–463).** A final secret scan is not enough for hostile active files, Unicode/path collisions, archive bombs, manifest omissions, checksum tampering, unsafe HTML/SVG/PDF rendering, or redaction derivation failures. Explicitly adopt the architecture’s admission and staged package-validation contracts and add negative fixtures.

11. **Should-fix — role/tenant negative reads can collect the very data whose isolation failure they detect (§7.2 lines 296–310).** Require fixture responses to carry non-sensitive canaries, cap and quarantine denied-edge bodies before admission, stop after an unexpected authorized response, and forbid screenshots/DOM excerpts on cross-boundary failures unless a reviewed redacted derivative is safe.

12. **Should-fix — incident severity is not normalized (§13 lines 552–555).** “Critical product incident” and “High-signal safety event” are prose categories without event schema, triage owner, notification deadline, credential-rotation decision, release waiver rule, or closure criteria.

## Concrete fixes

1. Expand the spec from dynamic testing to the full architecture trust-boundary table. For each provider, acquisition, static analyzer, helper, VM/broker, target/probe, evidence, UI, optional-service, and package boundary, add attacker capability, forbidden authority, enforcing component, fail state, audit event, and adversarial fixture.
2. Add a normative Codex/Claude prompt-injection contract: repository/provider-visible content is data only; fixed task envelopes and tool allowlists; no model access to approvals, secrets, helper/broker, network policy, canonical evidence, or package state; all outputs are schema-checked proposals; fixed-context/fresh-review rules; and equivalent malicious fixtures for both agents.
3. Move request enforcement out of the browser’s trust domain. Require a broker-owned transparent/explicit proxy with a signed control-plan digest, exact method/origin/path/content-type/account budgets, DNS/IP pinning, redirect validation, request accounting, and atomic revocation; keep Playwright interception as defense in depth.
4. Split authorization into at least two explicit contracts: pre-build acquisition approval bound to candidate/compiled plan/destinations/data/methods, and post-build probe authorization bound to produced image digests, service/origin map, route/control plan, accounts, safety classes, and probe digests. Define invalidation and cleanup between stages.
5. Specify all network classes from architecture—provider inference, Git acquisition, build acquisition, target runtime, and optional service—with separate identities, approvals, data categories, method/path rules, expiry/revocation, DNS/IP/certificate checks, byte/destination receipts, and no silent fallback. Add allowed-destination exfiltration fixtures, not only denied-destination tests.
6. Add end-to-end lifecycle tables and canary tests for SSH, provider, target, optional-service, and package-protection secrets. Complete the VM-envelope review with exact KDF/AEAD parameters, nonce/key handling, associated-data encoding, recipient identity, crash/replay behavior, and zeroization limits.
7. Add source/static/build execution rules and fixtures for hooks, filters, submodules/LFS, package-manager scripts, scanner configs/plugins, Dockerfile commands, remote contexts, registry substitution, mutable images, and approved build destinations.
8. Adopt the architecture’s general evidence admission, active-content rendering, redaction-derivation, and staged package-validation controls, then extend the release suite with hostile static/provider outputs and ZIP/HTML/SVG/PDF/path/Unicode/tamper/bomb fixtures.
9. Freeze typed audit events and finding-governance schemas, including actor/correlation/fence identity, safe field allowlists, severity/confidence/validation transitions, CVSS criteria, independent-review outcomes, disagreement/supersession, and release effects.
10. Retain Sections 4–17 as the dynamic-testing chapter; their safety classes, role/tenant accounting, budgets, coverage semantics, incident flow, and native-platform fixtures are strong material once embedded in the complete product safety specification.

## Verdict

**Reject.** Contender 4 clears a high bar for the dynamic-assessment subsystem, but misses P2’s bar for a product-wide safety specification. It cannot ship as `safety.md` until provider prompt injection, source/static/build execution, full secret and egress lifecycles, out-of-process request enforcement, product-wide audit/finding governance, and the evidence/package boundary are covered with enforceable controls and adversarial proofs.
