## Scores

- **Requirements coverage — 9.0/10.** The specification covers every P2 topic and almost every brief safety constraint with normative controls and tests: hostile acquisition/parsing (§§5–6), nested runtime and Compose (§10), credentials (§8), egress (§11), P0–PX dynamic safety classes (§12), provider prompt injection (§7), covert credential output (§8.3), evidence/package handling (§14), finding governance (§14.4), frozen incident mapping (§16), audit (§17), release gates (§§18–19), and residual risks (§20). The principal coverage gap is not a missing topic but the absent durable provider-disclosure acknowledgement and residual-risk acceptance record required by the spec's own prose.
- **Threat and attack-path completeness — 9.2/10.** Sections 2.3–2.4 explicitly trace malicious repositories/endpoints through parser exploitation, Compose smuggling, prompt injection, VM/daemon/browser compromise, replay/confused-deputy attacks, resource exhaustion, and transformed/split/encrypted/steganographic credential output. Section 8.3 closes the winning draft's strongest missed path by classifying all reachable post-credential output as O2 and excluding raw O2 from providers and packages even after a clean scan. The remaining blind spot is the concrete same-container path from a model-launched child process through `/proc`, filesystem, IPC, or inherited descriptors to the provider CLI's credential-bearing process/home; §7.3 acknowledges a compromised CLI but does not decompose or control those child-tool paths.
- **Enforceable and testable controls — 8.1/10.** The source, analyzer, Compose, VM, egress, request-guard, receipt, O2/O3, packaging, and incident controls are unusually specific and backed by the adversarial matrix in §18. HTTPS claims are now correctly bounded: §11.1 permits method/path claims only for a trusted fetch adapter and labels opaque TLS as destination-level enforcement. The score is capped because §12's signed `controlPlanId` has no frozen creation, admission, or transport operation into the broker, and §7.2 asserts that only five provider commands are available without specifying the OS-level mechanism that makes arbitrary Codex shell/filesystem tools unavailable.
- **Architecture, state, and API alignment — 7.0/10.** Section 16.2 correctly removes `SECURITY_HOLD`/`SECURITY_STOP` and maps incidents only to the frozen `cancelRun`, legal `CANCELLING -> CANCELLED`, existing events, evidence, provenance, and successor revisions. Other material conflicts remain: safety §11.2 prohibits every target-runtime egress exception while frozen architecture §3.4 and design §§5.2/5.5 explicitly support exact approved exceptions; safety §4 requires a durable provider acknowledgement separate from launcher login, while frozen `createRun`/`putApprovals` and design §5.2 provide no such record; and safety §12.1 alternately says P0–P3 need no `Approval` and that authorization is a subset of “that DRAFT approval.” Most importantly, architecture exposes only `vm.probe({controlPlanId,...})`/`broker.probe({controlPlanId,...})`; no operation registers the per-run plan that safety requires.
- **Credential, network, runtime, prompt-injection, evidence, and privacy controls — 8.6/10.** Credential purpose/recipient binding, one-use VM envelopes, late delivery, provider-home separation, exact acquisition inputs, trusted-fetch versus opaque egress, mount-free VM/rootless Docker, external request guard, proposal-only agents, evidence-ID views, O0–O4 output policy, safe rendering, retention, and package revalidation form a coherent defense in depth. The provider boundary is honest but incomplete: §7.2 says the provider gets its credential-bearing home and only five commands, while architecture launches Codex with `workspace-write`; without a named process/filesystem/procfs boundary or a credential-isolating inference gateway, the five-command property is a test aspiration rather than a frozen enforcement design. Section 7.3 appropriately discloses this residual and makes both real-provider canary suites release blockers, preventing a higher score rather than a failure.
- **Safe failure — 9.2/10.** Sections 13, 16, 18, and 19 consistently turn ambiguity, drift, exhaustion, stale fences, malformed receipts, cleanup residue, cancellation, and missing native-platform proof into blocked/partial/not-tested coverage or release blockers. Host-side emergency stop does not depend on the guest, terminal runs remain immutable, exact-resource cleanup prevents cross-run deletion, and SEV-0–2 recovery requires a successor revision. The one wording defect is §1's “prohibited without an override path,” which reads as though an override exists for host sockets, production credentials, destructive tests, or silent uploads and conflicts with §3's explicit statement that no such approval path exists.
- **Operational usability — 7.7/10.** The specification gives operators clear consent content, denial consequences, coverage effects, static-only continuation, cancellation semantics, incident facts, retention inventory, and release blockers. However, the required provider acknowledgement cannot be recorded through the frozen UI/API, target-runtime consent differs from the parallel design, and positive dynamic authorization does not identify which DRAFT object is authoritative when P0–P3 require no approval. These are not cosmetic discrepancies: P4/P6 would need to invent different setup and consent behavior from P5's policy engine.
- **Residual-risk honesty — 9.0/10.** Sections 7.3, 8.3, 11.1, 15, and 20 candidly disclose provider-side processing, credential-bearing CLI exposure, opaque-destination exfiltration, categorical covert-channel capacity, hypervisor/kernel escape, compromised trusted components, checksum limits, imperfect redaction, and static/passive coverage limits. The spec correctly makes disposable least-privilege sandbox credentials—not scanner confidence—the core defense. It still lacks a durable, scoped residual-risk acceptance model despite §19.1 referring to “unaccepted” Critical/High boundary issues, leaving the actor, scope, rationale, expiry, revocation, and non-waivable categories undefined.
- **Buildability — 7.3/10.** Most controls have an owner, protocol surface, failure state, and fixture, and the O2/O3 policy deliberately maps onto frozen evidence fields rather than inventing DTO enums. Buildability falls materially at the dynamic boundary: a control plan containing post-start internal origins, identities, fixture IDs, budgets, aborts, and a compiled-plan digest must be generated per run, but neither the host-helper nor broker protocol can accept, authenticate, or register it before `probe`. P4/P5 therefore must invent a security-critical protocol operation or silently treat an unregistered ID as authority, violating P1's contract freeze.

## Overall

**8.3/10.** Equal-weight average (8.34 unrounded). This clears the 8.0 tournament threshold and is a real improvement over the 7.9333 winner baseline: transformed-secret exfiltration, invented lifecycle state, opaque-HTTPS claims, dynamic safety classes, finding governance, and frozen-event incident handling are all substantially corrected. It does not clear the implementation-freeze bar because the central positive dynamic-authorization artifact cannot reach the enforcing broker under the frozen protocol.

## Strongest objection

**Must-fix — the request guard cannot enforce the signed positive authorization because the per-run control plan has no frozen admission or transport path.** Safety §12.1 says the broker's `controlPlanId` names a release-owned, digest-locked plan binding `compiledPlanDigest`, exact internal origin, method/route, principal/role/tenant, secret recipient, fixtures, budgets, output class, aborts, cleanup, and coverage outcome. Several values are known only after compile/start. Frozen architecture §10.1 exposes `vm.probe({runtimeId, controlPlanId, probeProfileId, secretEnvelopeIds})`, and §10.4 exposes `broker.probe({controlPlanId,...})`; neither protocol has `stageControlPlan`, an inline signed plan/digest, nor another operation that transfers and registers this per-run object. The architecture merely requires IDs to resolve to something “already registered” without defining how registration occurs.

That omission breaks the exact correction the synthesis claims in safety-report.md: the external request guard cannot verify the plan's content, signature, fence, compiled-plan binding, or non-expansiveness from an opaque ID it never received. The implementation lanes must either add an unreviewed security-critical protocol operation, trust server assertions, or weaken the guard to a static profile. Any choice causes P1/P2 rework and divergent backend/runtime implementations.

## Other findings

1. **Must-fix — dynamic approval semantics contradict themselves (§12.1).** Lines 615–619 make `createRun.selectedProfiles`, effective capability, and the signed plan sufficient for internal P0–P3 controls and expressly require no empty-destination `Approval`; lines 621–627 then authorize only when the plan is a subset of “that DRAFT approval,” record approval IDs in `RuntimeCapability`, and block changes that exceed DRAFT scope. There may be no approval ID for an internal control. The engine cannot deterministically decide whether profile selection is operator authorization, whether target-code execution needs a non-egress approval, or which object bounds origin/identity/action fields discovered later.
2. **Must-fix — provider disclosure has no durable contract (§4).** The safety spec requires the UI to record a separate run acknowledgement containing provider/model, categories, byte limits, purpose, processing terms, and transfer uncertainty before sending any source-derived content. Frozen `createRun` has no acknowledgement fields, `Approval` cannot represent model/terms/byte-limit details, and design §5.2 explicitly treats provider inference as explanation rather than an approval. P5 cannot gate provider phases on a record P6 cannot create.
3. **Must-fix — target-runtime egress policy conflicts with both frozen P1 and parallel P3.** Safety §11.2 says “No DRAFT approval type can relax target runtime egress in MVP,” while architecture §3.4 defines exact endpoint exceptions with approval and design §§5.2/5.5 expose consent and status for them. The stricter safety rule better matches the brief's allowed outbound categories, but it must be reconciled by a deliberate architecture/design revision rather than left as three incompatible sources of truth.
4. **Must-fix — the provider tool boundary is asserted more strongly than its mechanism (§7.2).** `AgentTask.allowedCommands` is a data field, not an OS command filter. Architecture launches Codex with `workspace-write`, which ordinarily permits sandboxed command execution, while safety says “Only” five commands are available and arbitrary shell is disabled. The spec does not name the wrapper, executable allowlist, filesystem layout, syscall/process policy, `/proc` isolation, or credential gateway that enforces this for both real CLIs. The §18 canary suite can detect some failures but cannot substitute for a buildable boundary.
5. **Should-fix — residual-risk acceptance remains undefined (§§19.1, 20).** Product release is blocked by “unaccepted” Critical/High issues affecting a boundary, but there is no acceptance record or authority. Without scope, evidence, rationale, compensating controls, expiry, revocation, disclosure, and non-waivable classes, “unaccepted” is not a deterministic gate and may become an ad hoc override.
6. **Should-fix — the opening prohibition is dangerously ambiguous (§1).** “Host Docker socket mounting ... and silent uploads are prohibited without an override path” normally means they are allowed through an override. Section 3 later says there is no approval path for most of them. A release/security policy must not leave non-waivability to grammar.
7. **Should-fix — O3 review semantics do not identify the reviewer record (§8.3).** O3 requires “technical-human review,” and §14.2 requires deterministic validation plus review, but the safety spec does not state which frozen `Review` kind/decision/input digest proves O3 eligibility or how a changed O3 derivation invalidates prior review. This is smaller than the raw-O2 fix, because O2 exclusion itself is unambiguous.
8. **Nice-to-have — retained provider homes need a concrete default.** Sections 4 and 8 keep homes until engagement cleanup and mention inactivity reminders, but do not freeze the default inactivity interval or the exact verified cleanup outcome. Given the admitted reusable-provider-credential residual, indefinite retention by omission deserves a deterministic default.

## Concrete fixes

1. Revise the frozen runtime protocol to define one authenticated, fenced way to admit a per-run control plan before probing—either a typed `stageControlPlan` operation or an inline plan plus digest/signature on `vm.probe`—and specify canonical bytes, signer/verification key, size limits, registration journal, creation nonce, compiled-plan/runtime/origin binding, replay handling, revocation, and reconciliation. Add ID swap, stale fence, altered-plan, post-start-origin, and missing-registration fixtures.
2. Make the dynamic authority chain singular and explicit. State whether DRAFT `selectedProfiles` itself authorizes non-egress P0–P3, whether target-code execution requires a separate non-egress capability decision, which approvals are optional/required, and how post-DRAFT discovered values are proven non-expansive without pretending every control has an approval ID.
3. Add a frozen provider-disclosure acknowledgement DTO and DRAFT mutation (or deliberately model it as a distinct typed approval) with all §4 fields, row-version/idempotency behavior, refusal outcome, audit event, and provider-dispatch gate; update design to render that exact contract.
4. Choose one MVP target-runtime egress rule and update architecture, safety, and design together. If runtime remains physically offline, remove endpoint-exception capability/UI language. If exceptions remain, safety must define their class and enforcement without weakening the brief's production prohibition.
5. Freeze the provider tool/credential enforcement mechanism for each real CLI: process and mount layout, child-tool command surface, filesystem/procfs/IPC boundaries, environment/FD scrubbing, network namespace/gateway, home permissions, credential canaries, and what exact failure destroys the engagement home. Do not use `allowedCommands` alone as proof of enforcement.
6. Define a durable residual-risk decision contract and make non-waivable categories explicit; fix §1 to say the prohibited actions have no override path where that is intended.
7. Bind O3 release eligibility to an existing frozen review kind, current derivation/input digest, reviewer role, and invalidation rule, and freeze the provider-home inactivity cleanup default.

## Verdict

**revise.** The synthesized specification clears the numeric tournament bar and fixes all three mandatory winner defects plus the invented-state problem. It misses the freeze/ship bar because positive dynamic authorization still depends on an untransportable control plan, and the provider acknowledgement, target-runtime egress rule, and provider command boundary conflict with or exceed the frozen architecture/API. P4/P5/P6 would otherwise have to invent security-critical behavior independently.
