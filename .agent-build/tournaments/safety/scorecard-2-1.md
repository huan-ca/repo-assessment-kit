## Scores

- **Requirements coverage — 6.5/10.** The spec covers credentials, egress, production prohibition, redaction, incident response, compliance language, and release tests in depth, but P2-required container/nested-runtime controls, runtime-test safety classes, an audit-event contract, and finding severity/confidence/validation rules are absent or materially incomplete.
- **Assets, adversaries, and trust boundaries — 8.0/10.** Sections 2 and 3 identify sensitive data, external recipients, hostile source, compromised dependencies/parsers, operators, providers, and failure/replay adversaries, but do not turn every named boundary—especially static analyzer containers and the local UI session—into a corresponding control and verification matrix.
- **Attack-path completeness — 6.5/10.** The harm scenarios in §3.2 are concrete and the egress/replay paths are probed aggressively, yet the primary chain `malicious source -> vulnerable static scanner/parser -> code execution in a host-side analyzer container -> host/helper compromise` is named only as an adversary and never closed.
- **Hostile-source and nested-runtime isolation — 5.5/10.** Sections 5.3, 6, and 10 specify VM firewall, one-use secrets, and resource bounds, but no normative static-analyzer container profile or test covers user/capability/seccomp/AppArmor/no-new-privileges/mount/output/control-socket isolation; inside-VM separation among build, target, probe, broker, and evidence collector is also unspecified.
- **Credential lifecycle and authentication isolation — 9.0/10.** Sections 4 and 6 provide unusually strong purpose/recipient/run scoping, opaque handles, single-use semantics, provider-home separation, exact SSH resources, revocation, envelope binding, cleanup failure behavior, and adversarial fixtures.
- **Network egress, consent, and production prohibition — 8.5/10.** Sections 5 and 8 bind approvals to exact workload/destination/data dimensions, address DNS rebinding, redirects, IPv6, tunneling, metadata/LAN access, and prohibit target-runtime egress; the remaining weakness is that §5.3 knowingly permits a hostile build to use an approved dependency endpoint as a source-exfiltration channel without requiring an out-of-process fetch/offline-build boundary.
- **Prompt injection and external-service safety — 8.0/10.** Section 4.4 gives providers a redacted read-only task view, treats target text as data, quarantines output, and removes policy/credential/package authority; §§5.3 and 12.3 make hosted tools explicit and non-fallback, though provider-dispatch admission is not expressed as a per-task proof that actual paths/categories are a subset of the acknowledged disclosure.
- **Evidence integrity, privacy, logs, screenshots, and packaging — 9.0/10.** Section 7 uses quarantine, immutable redaction derivations, allowlisted logs, trusted image decoding, mandatory human review for credentialed screenshots, fail-closed scanning, and fresh-process ZIP reopening; §§9 and 14 are candid about external retention and redaction limits.
- **Safe failure, incident response, auditability, and finding governance — 5.5/10.** Section 11 defines useful triggers, containment, recovery, and non-recall language, but its new `SECURITY_HOLD` state is absent from the frozen run-state machine, audit events lack normative event types/emission points, and the spec never defines security-finding severity, confidence, or validation states despite P2 requiring them.
- **Verification, enforceability, and architecture fit — 6.5/10.** Section 12 is an excellent adversarial fixture catalog for credentials, egress, packages, and incidents, but it omits local-source and static-analyzer escape fixtures and relies on contracts the architecture does not expose, most visibly `SECURITY_HOLD`; downstream lanes would have to invent schema, transition, API, and persistence behavior.

## Overall

**7.3/10.** Equal-weight average. This is a strong credential/egress/redaction specification, but not yet a complete safety specification for a hostile-repository assessor.

## Strongest objection

The spec names “a compromised dependency, image, scanner parser” as an adversary in §3.1, but never specifies or tests the containment boundary for static analyzers. Section 5.3 defines network classes for provider, Git, build, target runtime, optional services, and updates—but not static analyzer workers—and §12 contains no malicious-parser/container-escape suite. Under frozen architecture §5, the host helper runs fixed static analyzer containers directly, so malicious repository bytes are intentionally fed to parsers on a host-side execution boundary. Without a normative analyzer profile and escape/lateral-access tests, a scanner vulnerability can become arbitrary code in that container with undefined access to the host, helper resources, snapshot/output paths, or other runs. This is the most direct hostile-repository attack path and P2 explicitly requires container and nested-runtime controls; it is a must-fix release gap.

## Other findings

1. **Must-fix — finding severity/confidence/validation is missing.** P2 requires “severity/confidence/validation rules.” The only taxonomy is the Critical/High/Medium priority in §3.2 and the release statement “no unresolved Critical or High finding” in §13.1. There is no definition for actual finding severity, confidence, validation status, independent-review disposition, conflict handling, or gate calculation, so two agent paths can classify and release the same security evidence differently.
2. **Must-fix — incident state is incompatible with the frozen architecture.** Section 11.2 requires an atomic transition to `SECURITY_HOLD`, and §§12.2, 12.6, and 13.1 depend on it. Frozen architecture §6.1 has no such `RunState` or transition, and the OpenAPI/state/persistence contracts have no security-hold operation or recovery transition. The containment procedure therefore cannot be implemented without an unplanned contract migration.
3. **Must-fix — runtime-test safety classes are not defined.** Sections 8 and 10 list prohibited actions and broad resource controls, but never classify passive observation, safe authenticated workflow exercise, state-changing sandbox action, exploit validation, or prohibited testing, nor bind each class to allowed methods, data, credentials, rate limits, cleanup, and approval. “Non-destructive” remains a judgment call at the exact point hostile prompts and provider proposals can influence test selection.
4. **Must-fix — inside-VM lateral boundaries are underspecified.** Section 5.3 says the trusted probe uses internal service names and §6 gives target services recipient-specific secrets, but it never states whether target, build, probe/browser, broker control, and evidence collection share routes or identities. A malicious target can attack the browser/probe or broker-facing surfaces; compromise should still have no control-channel, artifact-admission, secret-broker, or cross-service reach.
5. **Must-fix — local-repository intake is absent from the safety verification matrix.** Section 4.5 and §12.2 cover SSH only. The brief requires existing local paths, and frozen architecture §9 relies on registered roots, no-follow reads, symlink/special-file rejection, TOCTOU checks, collision handling, and before/after source integrity. None of those hostile local-source paths is promoted into P2 release gates.
6. **Must-fix — auditability is described but not contracted.** Sections 2.3, 5.2, and 11.2 list receipt/incident fields, but there is no required event taxonomy for secret creation/redemption/revocation, approval grant/deny/change, provider dispatch, egress decision, runtime lifecycle, evidence admission/rejection, package release, incident hold, or cleanup. Missing IDs, ordering, integrity linkage, and retention rules make forensic reconstruction and automated acceptance ambiguous.
7. **Must-fix or explicitly narrow the claim — build egress is called both a Critical harm and an accepted channel.** §3.2 labels build/service endpoint exfiltration Critical and says “Required prevention,” while §5.3 permits malicious build payloads to reach approved package endpoints and concedes source can be exfiltrated. Disclosure and byte caps do not prevent the harm. Require release-owned dependency resolution/fetch outside repository-controlled execution followed by a networkless build wherever supported, and make any exception a separately accepted limitation rather than a normal safe path.
8. **Nice-to-have — test the complete local UI authorization boundary.** Section 4.1 gives secret upload origin/host/CSRF controls, but the safety suite does not exercise bootstrap-token replay, localhost DNS rebinding, cross-origin mutation attempts, SameSite behavior, session shutdown, or approval/deletion/package actions. Frozen architecture §12.1 defines these controls; P2 should make their adversarial verification explicit because approvals confer external-transfer authority.

## Concrete fixes

1. Add a normative workload-isolation matrix for acquisition, every static analyzer, build workers, target services, probes/browser, provider adapters, helper, broker, admission, and packager. For each, freeze UID, rootfs, mounts, Linux capabilities, seccomp/LSM, namespaces, network class, sockets, secrets, writable paths, quotas, outputs, and reachable peers.
2. Add hostile static-analyzer fixtures that exploit parser inputs, attempt shell/process creation, socket and host-path access, cross-run reads, namespace escape, output flooding, malformed archives, and cleanup persistence; make any host/helper/control-socket reach a release blocker.
3. Define a versioned runtime-test safety taxonomy with allowed/prohibited action types, HTTP methods, credential classes, rate/side-effect budgets, evidence rules, approval requirements, and cleanup behavior. Require every planned dynamic control to declare and validate one class before dispatch.
4. Reconcile incident handling with frozen contracts: either add and version `SECURITY_HOLD` across `RunState`, legal transitions, DB schema, OpenAPI/SSE, reducers, recovery, deletion, and package eligibility, or express the hold through an existing state plus a separately frozen blocking security disposition. Do not leave downstream lanes to choose.
5. Define security-finding `severity`, `confidence`, `validationState`, reviewer independence, conflict/supersession, and release-gate rules, including how threat harm, exploitability, evidence strength, and blocked validation are kept distinct.
6. Add an enumerated, schema-versioned audit-event table with trigger, actor/workload, required fields, correlation IDs, integrity link, sensitivity exclusions, retention, and package/export status for every authority-changing or security-relevant action.
7. Add the local-source attack suite from architecture §9 to P2 gates, including root/relative-path escape, symlink/hardlink/special file, Unicode/case collision, concurrent mutation, oversized input, dirty working tree, and final before/after integrity mismatch.
8. Split build dependency acquisition from repository-controlled build execution: validate lock/digest requests, fetch through a secret-free trusted worker, then physically remove network before any Dockerfile/build script runs. If an ecosystem cannot support that boundary, mark depth partial/blocked or require an explicit high-risk exception outside the default release profile.
9. Freeze VM-internal network identities and ACLs so target/build containers cannot reach broker control, helper relay, probe control, artifact admission, or another service except declared app dependencies; prove this with malicious target and browser-compromise fixtures.

## Verdict

**revise.** The contender clears the bar for credential isolation, exact egress consent, production denial, redaction, and adversarial secret testing. It misses the P2 ship bar because the principal static hostile-parser execution boundary is unspecified, several required safety contracts are absent, and incident containment depends on a run state that does not exist in the frozen architecture.
