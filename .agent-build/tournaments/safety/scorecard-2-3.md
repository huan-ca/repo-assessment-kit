## Scores

- **Requirements coverage — 8/10.** The spec covers nearly every P2 domain in depth: assets and adversaries (§§2–3), credentials (§4), egress and consent (§5), the VM envelope (§6), redaction/package handling (§7), production denial (§8), incident response (§11), release tests (§§12–13), and residual risk (§14). It does not, however, freeze the required runtime-test safety classes or a complete finding severity/confidence/validation policy.
- **Assets, attacker model, and trust boundaries — 9/10.** Sections 2.2–3.2 identify customer, operator, provider, repository, runtime, evidence, credential, and package assets and trace credible attackers through provider, dependency, scanner, operator, DNS, retry, and cleanup failures. The local browser/session and a malicious same-host user are not developed to the same depth despite the persistent provider homes and loopback credential-entry surface.
- **Prohibited actions and authorization — 8/10.** The hard invariants (§1), production prohibition (§8), and abuse rules (§10) clearly deny production access, destructive actions, broad mounts, ambient credentials, arbitrary destinations, and permission-bypass modes. Authorization remains incomplete for dynamic controls because “No scanner or probe may perform destructive testing” (§10) is a negative list, not a control-by-control authorization contract for allowed origins, methods, actions, accounts, state changes, and reversibility.
- **Container, nested-runtime, and source-isolation controls — 8/10.** Sections 3.1, 5.2–5.3, 6, and 12 require disposable VMs, separate identities, root-owned egress enforcement, no target ports, internal probe traffic, envelope binding, cleanup, and four-platform negative tests. The spec relies heavily on the architecture for the host-helper and Compose compiler rather than explicitly reviewing their command/mount/namespace/image rejection matrices, so P4/P5 still lack a safety-owned conformance table for those critical boundaries.
- **Credential lifecycle and secret handling — 7/10.** Sections 4 and 6 give unusually strong lifecycle rules for provider homes, SSH, sandbox credentials, package secrets, revocation, one-use delivery, replay prevention, tmpfs, and cleanup. Buildability drops because the frozen architecture's `SecretHandle.purpose` permits only `target-service`, `probe`, and `age-passphrase`, while this spec also requires optional-service and dedicated provider invocation credentials; §4.2/§4.3 additionally permit API tokens to “exist only for the single provider process” without freezing a non-environment delivery mechanism compatible with the CLIs.
- **Network egress and hosted-service controls — 9/10.** Sections 5.1–5.4 bind consent to exact destinations and data categories, separate network identities, deny redirects/tunnels/private ranges, cap bytes and duration, prohibit target runtime egress, and prevent hosted-service fallback. The main defect is contractual: §5.1 requires `workloadIdentity`, `purpose`, and `maximumBytes`, but the frozen `Approval` DTO has none of those fields, so the normative policy cannot be persisted, replayed, or validated as written.
- **Safe dynamic testing and emergency control — 6/10.** Production sentinels, sandbox-only credentials, resource caps, external egress denial, host-side emergency stop, and forced-teardown fixtures are strong. P2 specifically requires runtime-test safety classes, yet the spec never defines passive versus authenticated/read-only versus reversible mutation controls, allowable HTTP methods/actions, per-control origin and credential binding, or what evidence authorizes any state-changing probe; “non-destructive” is left for implementers to interpret.
- **Prompt injection and untrusted-content defense — 8/10.** Section 4.4 gives providers bounded redacted task views, marks target text as untrusted, removes policy/credential/helper authority, quarantines output, and §12.1 tests direct and encoded secret-exfiltration instructions across both providers. It should additionally freeze instruction precedence and explicitly treat repository `AGENTS.md`/`CLAUDE.md`, filenames, scanner output, target pages, and model-generated approval language as data-only injection carriers rather than relying on the generic “untrusted” label.
- **Evidence integrity, privacy, redaction, and packaging — 9/10.** Sections 7–9 use allowlist logs, quarantined and re-encoded screenshots, mandatory visual review, immutable redaction derivations, fail-closed format scanning, fresh-process ZIP reopening, conditional privacy language, and no-recall disclosure. The remaining weakness is operational: screenshot review has no reviewer eligibility, queue, decision record, delta invalidation, or unavailable-review transition, although screenshots may safely be omitted.
- **Failure, incident response, and auditability — 6/10.** Sections 5.4 and 11 define strong revocation ordering, containment, minimal incident records, external revocation honesty, recovery prerequisites, and notification limits. However, §11.2 requires an atomic `SECURITY_HOLD` and §12.6 tests it, while the frozen architecture's canonical `RunState` enum and transition table contain no such state; the frozen `RunEvent` union also has no incident, approval-revoked, egress-denied, or secret-redeemed event types. The incident path therefore cannot be implemented or audited without reopening P1 contracts.
- **Finding governance and compliance-language safety — 6/10.** Section 9 carefully avoids applicability and compliance claims, and §13 blocks unresolved Critical/High findings. It never defines what “unresolved” means, how technical severity differs from business priority, which evidence permits CVSS, how confidence and validation states transition, or how disputed/imported findings affect release; merely inheriting the DTO from architecture does not satisfy P2's requirement to specify safety rules for those fields.
- **Verification, ownership, and parallel buildability — 7/10.** Section 12 is one of the strongest adversarial suites among the contenders, covering provider homes, SSH, egress bypass, envelope cryptography, secret leakage, package attacks, deletion, incidents, and production sentinels. Parallel buildability is materially weakened by the incompatible run state, event vocabulary, approval fields, and credential purposes, plus the absence of an explicit schema/API owner and migration step to reconcile them before P4.
- **Operational usability — 6/10.** Consent copy, deny/revoke effects, no-recall language, blocked-runtime outcomes, and issuer-side incident actions are operator-friendly. Normal operation can still deadlock or become approval-heavy: provider denial has no defined reduced workflow; exact provider/build destinations and representative paths may require repeated approvals with no grouping/diff model; any “unexpected egress” or host-key mismatch can trigger a global hold; recovery requires “documented triage” and “independent security review” (§11.3) without defining the authorized reviewer, UI/API workflow, evidence record, or safe abandon/clone-run path.
- **Residual-risk treatment — 8/10.** Section 14 honestly identifies the provider process as the largest residual risk and also discloses approved-destination exfiltration, generic SSH-agent breadth, external retention, image-redaction misses, and VM/hypervisor limits. It understates the operational residuals of indefinite provider-home/package retention, stale operator-maintained production sentinels, unverified provider retention/region terms that may still be accepted, local-session compromise, and the possibility that an intentionally malicious repository remains outside the claimed safe envelope until short-lived provider identity or a credential broker exists.

## Overall

**7.5/10 (equal-weight average).** This is a serious, unusually complete safety contender, but it misses the 8/10 freeze bar because several central controls are not representable by the frozen architecture and the operator-facing incident/dynamic-test workflows remain underspecified.

## Strongest objection

**Must-fix — the safety control plane contradicts the frozen P1 contract at the exact point where an incident must fail closed.** Contender §11.2 says the engine must “atomically move the run to `SECURITY_HOLD`,” prevent resume, and later resume only after triage, rotation confirmation, cleanup, new approvals, and independent review (§11.3); §§12.6 and 13.1 make that state a release gate. Architecture §6.1 declares the canonical run-state enum and legal transitions, rejects every illegal transition with `409 RUN_STATE_CONFLICT`, and contains no `SECURITY_HOLD`. Architecture §8.8's closed `RunEvent.type` union likewise cannot record the required incident, approval-revocation, credential, or egress events. Related drift appears in contender §5.1, whose approval binding adds `workloadIdentity`, `purpose`, and `maximumBytes` absent from architecture §8.7's frozen `Approval`, and in optional-service/provider credentials absent from architecture §10.3's `SecretHandle` purposes.

This is not editorial drift: P4 must generate root contracts and P5/P6 must independently implement the workflow, persistence, API, SSE, credential, approval, and UI state. As written, each lane must either violate the safety spec or silently invent incompatible extensions, making incident containment and recovery least reliable precisely when the system is under attack.

## Other findings

1. **Must-fix — no runtime-test safety classes (§§8, 10, 12.4).** The spec strongly bans production, egress, and destructive testing, but does not classify permitted probes or bind each planned control to origin, method, action, account, credential, expected state change, reversibility, and rate. A probe can be called “non-destructive” by one implementer and state-changing by another, defeating cross-agent equivalence and safe runtime authorization.
2. **Must-fix — incident recovery is not operable (§§11.1–11.3).** A known secret match, credential-path read attempt, unexpected egress, host-key mismatch, or cleanup residue all trigger the same global containment, yet there is no distinction between a safely denied attempt and confirmed exposure, no incident severity, no response deadlines, no reviewer eligibility/independence, no triage record schema, no state transition/API, and no abandon-or-create-successor-run procedure. The likely outcome is either excessive permanent holds or unsafe manual overrides.
3. **Must-fix — approval policy cannot be enforced by the frozen DTO (§5.1).** `workloadIdentity`, `purpose`, `maximumBytes`, and the full destination-policy digest are security-significant inputs, not optional UI metadata. Without contract fields they cannot participate in attempt `inputDigest`, consent replay, revocation, audit receipts, or equivalence validation.
4. **Must-fix — credential channels do not fit the frozen secret contract (§§2.2, 4.2–4.3, 4.6, 5.3).** Optional-service credentials require a service-specific client and approval handle, while architecture supports no matching secret purpose/upload path. Provider token modes promise a “dedicated protected input” but do not choose stdin, inherited FD, mounted one-shot file, or a brokered invocation and do not reconcile that promise with CLIs that commonly consume environment variables. This leaves P4/P5 to improvise the highest-value secret boundary.
5. **Must-fix — security finding policy is incomplete (§13.1).** “No unresolved Critical or High finding” is not deterministic without legal validation-state transitions, dispute rules, CVSS sufficiency, confidence requirements, imported-finding treatment, and who may accept residual Medium/Low risk. Two providers can produce different release decisions from the same evidence while both claiming compliance with this spec.
6. **Should-fix — provider denial has no usable path (§§1.3, 5.3, 13.2).** Provider inference requires affirmative acknowledgement, but the spec explains reduced completion only when optional services/build/runtime are denied. It must state whether denying the mandatory provider transfer blocks the run, permits a deterministic scanner-only package, or requires a different offline mode, with precise coverage/confidence consequences.
7. **Should-fix — consent can become an unbounded operator task (§§2.3, 5.1, 5.3).** Exact host/path/method/category/byte approval is defensible, but provider and package registries may use multiple endpoints and redirects. The spec supplies no signed release-owned destination bundle, approval grouping, change diff, destination discovery mechanism, or “approve none and continue static-only” summary; repeated opaque prompts will encourage careless consent.
8. **Should-fix — screenshot review is a release workflow without a contract (§7.2).** Every admitted screenshot requires human visual review, but the spec does not define reviewer role, independent/self-review rules, review input digest, accept/reject reasons, delta invalidation after remasking, queue progress, or how P6 displays a safe failure. Screenshot omission is allowed, which limits impact, but admitted-image release remains underspecified.
9. **Should-fix — retention defaults rely too much on operator memory (§§2.2, 7.1, 9, 14).** Provider homes and validated packages persist until explicit cleanup, and provider homes contain sessions/logs/config beyond authentication. Add engagement-close cleanup, inactivity reminders, retained-data inventory, and a deliberate renewal choice; isolation reduces cross-customer access but does not reduce at-rest exposure.
10. **Should-fix — residual-risk acceptance has no accountable decision record (§14).** The spec names important residuals but does not bind acceptance to a role, scope, expiry, rationale, compensating controls, customer-visible limitation, or re-review trigger. “Accepted only with disclosure” is not enough to prove who accepted an intentionally malicious repository, generic SSH-agent use, unverified processor terms, or an admitted screenshot risk.

## Concrete fixes

1. Reconcile P1 before freezing P2: add a canonical incident/hold model and legal transitions, typed incident/recovery APIs, event types, persistence tables, SSE/UI states, and successor-run behavior; or map containment onto existing states with equally strict semantics. Do not leave `SECURITY_HOLD` as an out-of-contract string.
2. Version the approval schema to include workload identity, purpose, request/response/total byte ceilings, policy digest, and any attempt scope required by enforcement. Include the complete approved object in capability resolution and attempt input digests, and define explicit revoke/expire operations.
3. Extend the secret contract with purpose-specific optional-service/provider invocation channels, or explicitly exclude those auth modes from MVP. Freeze the actual delivery primitive for each supported CLI and prove child tools, `/proc`, logs, crash paths, and retries cannot observe it.
4. Add a runtime-control authorization matrix: `passive-observation`, `read-only-authenticated`, `reversible-sandbox-mutation`, and `prohibited`. For every control bind origin, methods/actions, recipient credential, synthetic data, state-change budget, cleanup proof, rates, evidence, cancellation result, and exact coverage status.
5. Define a two-tier safety response: safely denied policy violations become typed blocked controls and reviewable warnings; suspected/confirmed exposure becomes durable incident hold. Specify severity, detection owner, deadline, containment acknowledgement, triage evidence, qualified reviewer, recovery/abandon/successor-run choices, and immutable audit events.
6. Freeze finding governance: technical severity, business priority, confidence, validation state, CVSS prerequisites, imported data, dispute/invalidation/supersession transitions, reviewer authority, and release effects for every state.
7. Add an operator workflow contract for provider refusal, destination bundles and diffs, grouped consent, revocation progress, screenshot review, incident triage, external-issuer actions, and residual-risk acceptance. Each blocked state needs plain-language cause, what ran, what did not, what remains at risk, and the safe next actions.
8. Expand residual-risk records to include approver, scope, affected run/control, rationale, compensating controls, customer-visible disclosure, expiry, and re-review triggers. Add explicit risks for stale production sentinels, unverified provider terms, local-session/same-host compromise, and indefinite provider-home retention.
9. Add release fixtures for the repaired contracts: incident transition/restart/recovery, approval digest and field mutation, optional/provider credential delivery, safely denied versus confirmed-exposure classification, dynamic safety classes, consent-bundle diffing, screenshot review invalidation, provider refusal, and engagement-home retention/cleanup.

## Verdict

**Revise.** The contender clears the bar for threat modeling, egress isolation, credential intent, VM-secret review, redaction, and adversarial verification, but misses the P2 freeze bar for architecture-compatible contracts and operationally complete incident, dynamic-test, finding-governance, and residual-risk acceptance workflows.
