## Scores

- **Requirements coverage — 7/10.** The contender substantively covers attacker models, credentials, destination consent, target egress, prompt injection, data-flow disclosure, redaction, incident response, compliance wording, release tests, and residual risk, but PLAN P2's runtime-test safety classes, security severity/confidence/validation rules, audit-event contract, and complete container/nested-runtime review are missing or only implied.
- **Control enforceability and testability — 7/10.** The approval binding (§5.1), one-use envelope (§6), revocation (§5.4), and adversarial fixture matrix (§12) are unusually concrete, but mandatory provider traffic cannot simultaneously use ordinary end-to-end TLS and satisfy §5.2's ban on CONNECT while an external proxy enforces HTTPS path, method, and byte policy; several incident triggers and credential channels likewise lack an implementable observation or transport mechanism.
- **Evidence integrity and validation — 7/10.** Provider output is quarantined and non-authoritative (§4.4), raw screenshots have a trusted derivation and human gate (§7.2), and package reopening/secret scanning fail closed (§7.3, §12.5), but the spec does not define security-finding severity/confidence/validation semantics, evidence-admission authority, reviewer independence, or how transformed/encoded target output is prevented from laundering a sandbox secret into admitted evidence.
- **Operational usability — 6/10.** Consent copy, equal-weight deny controls, blocked static continuation, revocation effects, and incident summaries are operator-oriented, but the spec gives no realizable workflow for `SECURITY_HOLD`, no reviewer eligibility/disagreement path, no bounded handling of “not verified” service terms, and no recovery mapping to the frozen run state machine.
- **Residual-risk treatment — 8/10.** §§3.3 and 14 candidly identify provider-process credential exposure, approved-destination exfiltration, SSH-agent breadth, external retention, imperfect image redaction, and hypervisor risk; the main omission is target-to-artifact covert exfiltration after a deliberately supplied sandbox secret and the feasibility risk of the proposed L7 proxy.
- **Buildability and architecture fit — 5/10.** The spec frequently names the frozen architecture and gives strong fixture targets, but it invents a non-canonical `SECURITY_HOLD` run state (§11.2), materially extends the frozen `Approval` contract without a profile/version change (§5.1), adds durable records/events without schemas, and leaves the host-helper and Compose-compiler safety review largely to P1 rather than freezing P2 implementation contracts.

## Overall

**6.7/10.** This is a strong credentials-and-egress design with an excellent adversarial test inventory, but it does not yet meet P2's implementation-ready, every-boundary bar. The equal-weight average reflects that its best controls are precise while its mandatory provider path, state/event integration, and dynamic-test authorization remain unresolved.

## Strongest objection

The mandatory provider-egress control is internally inconsistent at §5.2 and therefore cannot be verified as written. The spec requires the external proxy to enforce `"path prefix, method, request/response/total byte ceilings"` while also denying `"CONNECT tunneling"` and allowing only validated TLS. Codex and Claude provider traffic is HTTPS generated by pinned third-party CLIs. With ordinary end-to-end TLS, a network-external proxy can enforce destination/IP/port and coarse connection bytes, but it cannot see HTTP paths or methods; with CONNECT denied, the usual forward-proxy transport does not work; with trusted TLS termination, RAK must install and protect a trusted CA, define certificate generation and hostname validation, account for CLI pinning/streaming behavior, and test both real clients—none of which is specified. This is not an edge case: §1 makes provider inference a normal external transfer and §13.1 makes exact destination enforcement a release gate. P4/P5 would have to invent a materially different provider gateway or weaken the approval promise, invalidating the consent contract and several §12.3 tests.

## Other findings

1. **Must-fix — The incident lifecycle contradicts the frozen run contract (§11.2).** The contender requires the engine to `"atomically move the run to SECURITY_HOLD"`, but architecture §6.1 has no `SECURITY_HOLD` state or transition; canonical state values cannot drift without a profile change. The spec also says resume requires triage (§11.3) without identifying a legal transition. Backend, UI, SSE, and recovery tests cannot implement one shared lifecycle.

2. **Must-fix — Approval and audit requirements are not represented in canonical DTOs (§§2.3, 5.1, 5.4, 11).** The effective approval adds workload identity, purpose, maximum bytes, credential binding, and other dimensions beyond architecture §8.7's frozen `Approval`; the data-flow register and revocation/incident records add more durable fields. Yet the contender provides no revised schema/version, migration, persistence constraints, API shape, or typed events. Architecture §8.8's `RunEvent` has no approval, revocation, policy-denial, secret-redemption, egress-receipt, incident, or cleanup event types. Calling revocation a `"durable event"` does not make it auditable or buildable.

3. **Must-fix — PLAN P2's runtime-test safety classes are absent (§§8, 10, 12.6).** The spec prohibits destructive actions and high-rate behavior, but never classifies allowed probes (passive observation, read-only HTTP, authenticated read, reversible sandbox mutation), binds a planned control to methods/routes/origin/data/credential, defines mutation cleanup, or distinguishes an allowed login POST from a forbidden state-changing POST. A provider cannot choose extra authority, but the deterministic probe engine still has no authorization contract from which to decide what it may execute.

4. **Must-fix — The credential transport invariants conflict with supported CLI authentication (§§1, 4.1–4.3).** §4.1 categorically forbids secrets in environment variables, while §§4.2–4.3 conditionally support `CODEX_API_KEY`, `ANTHROPIC_API_KEY`, and `CLAUDE_CODE_OAUTH_TOKEN` through an unspecified `"dedicated protected input"` and promise to unset them only before child commands. P0 establishes those modes as environment-based. No file-descriptor wrapper, provider-native secret API, or broker protocol is defined, so API/token mode is either nonfunctional or violates the invariant and the `/proc/*/environ` fixture.

5. **Must-fix — Container and nested-runtime safety is asserted, not reviewed (§§1, 10, 12).** The contender says it `"strengthen[s], and do[es] not replace, the frozen architecture"` and mentions VM/resource limits, no socket, and egress. It does not explicitly adopt/reject architecture §10.2's Compose compiler rules or §10.1's authenticated host-helper protocol, nor add negative fixtures for privileged mode, devices, namespace sharing, unsafe sysctls, bind/external volumes, escaping build contexts, mutable images, disabled labels, custom runtimes, forged helper MACs, stale fences, idempotency conflicts, or orphan resources. P2's required review of these trust boundaries is therefore deferred to implementation.

6. **Must-fix — Several incident triggers have no detector or evidence contract (§11.1).** `"access/read attempt against a credential path"`, `"package released before all gates"`, cross-engagement sentinel access, and `"evidence that an external service received an unapproved category"` are useful conditions, but the spec does not name the sensor, event producer, trusted observation point, correlation fields, false-positive policy, or atomic link to containment. §12.6 tests the state effect after a trigger, not whether real components can reliably detect and emit it.

7. **Must-fix — Security-finding semantics required by P2 are omitted (entire spec; §13.1 only).** The release gate blocks unresolved Critical/High findings, but the contender never defines who assigns technical severity, how business priority remains separate, when CVSS is allowed, confidence meanings, imported-finding treatment, `corroborated` versus `independently reproduced`, disputes, supersession, or what unresolved Medium/Low findings do to release. The gate cannot be applied consistently to the architecture's `Finding` contract.

8. **Must-fix — Provider prompt-injection control tests only the credential-theft subset (§4.4, §12.1).** The task-view boundary and rule that output cannot approve or call privileged components are strong. However, fixtures ask providers to read/transmit auth and exercise denied tools; they do not test hostile instructions that manipulate evidence citations, omit controls, falsely mark coverage, request unsafe candidate selection, smuggle prohibited content through filenames/encodings, or exploit model output consumed by report generation. “The deterministic engine revalidates all output” needs named schemas, semantic invariants, and fixtures for every downstream authority.

9. **Must-fix — A target deliberately given a sandbox secret still has an unmodeled export channel (§6, §12.4).** Runtime network denial prevents direct egress, but `vm.collect` intentionally exports declared target artifacts. Exact-value and known-encoding scans cannot prove that a hostile target did not transform, split, encrypt, or steganographically encode the secret in logs, screenshots, or evidence. The spec should either prohibit collection of target-controlled artifacts after secret exposure, constrain collection to trusted-probe-derived structured results, or explicitly accept and disclose this residual risk.

10. **Should-fix — Human review controls are not operationally bounded (§§7.2, 13.1).** Every admitted screenshot requires human visual review and release requires independent security review, but there is no reviewer eligibility/independence rule, immutable input digest, verdict schema, disagreement resolution, re-review trigger after redaction/package changes, or behavior when a second qualified reviewer is unavailable. The safe outcome is blocking release, but the product still needs a deterministic review state and recovery path.

11. **Should-fix — Production classification depends on unspecified mutable operator data (§8).** `"operator-maintained production sentinel hosts, account/tenant IDs, database names, certificate names"` can be absent, stale, or incomplete. The spec blocks on uncertainty, which is sound, but does not define installation/run scope, trusted update authority, normalization, version/digest binding to the runtime attempt, conflicts with operator credential metadata, or test coverage across IDNs, aliases, resolved IPs, and certificate SANs.

## Concrete fixes

1. Choose and specify an enforceable provider-network design. Either limit approval enforcement to externally observable host/IP/port/connection-byte facts; add a release-owned application gateway/adaptor that constructs provider API calls from typed requests while keeping credentials outside the CLI; or fully specify trusted TLS termination, CA lifecycle, client compatibility, and real Codex/Claude conformance. Align the consent UI and §12.3 assertions with facts the chosen boundary can actually observe.
2. Reconcile safety states and records with `rak-contract/1.0.0`: map incidents onto legal canonical states or version the run state machine; publish strict DTOs/migrations/API/SSE events for security hold, approvals, revocations, credential redemption, egress decisions, policy denials, incidents, and cleanup; define transactional ordering and redacted payload allowlists.
3. Add a runtime-action authorization matrix. For every dynamic control, freeze class, origin, methods, routes, data scope, credential purpose, allowed side effect, cleanup/rollback, rate budget, evidence type, abort trigger, and coverage result on denial. Include malicious redirect, form, JavaScript, WebSocket, download/upload, login, and mutation fixtures.
4. Resolve provider token transport honestly: either remove environment-token modes from MVP, explicitly permit a provider-process-only environment with process/proc isolation and adjust the invariant, or prove a provider-supported non-environment channel. Test the real pinned CLIs, not a wrapper stub.
5. Add a normative P2 review table for every host-helper, Compose compiler, VM/rootless/cgroup/firewall, broker, secret-envelope, collect, cleanup, and emergency-stop control in architecture §10. For each, identify enforcement owner, failure state, audit event, negative fixture, and residual risk.
6. Define incident detectors and a typed audit catalog: event name, producer, trusted observation, actor/workload, run/attempt/fence correlation, policy/approval digest, safe fields, retention, severity, deduplication, and containment transition. Test both trigger detection and containment, including dropped/duplicated/out-of-order events.
7. Adopt the architecture's security-finding model with normative rules for technical severity, business priority, confidence, validation state, CVSS/CWE use, imported findings, independent reproduction, disputes, supersession, and release effects for every unresolved state.
8. Expand prompt-injection tests to indirect semantic attacks on coverage, evidence, runtime plans, report content, optional-service selection, and limitation suppression. Name the deterministic schemas and semantic validators that reject each proposed authority escalation or unsupported claim.
9. Restrict post-secret runtime collection to trusted-probe-generated structured outcomes and predetermined screenshot regions, or treat arbitrary target-controlled exports as secret-suspected and block them. Add transformations, chunking, compression, encryption, image steganography, and cross-artifact reconstruction fixtures, and document what remains impossible to detect.
10. Freeze human-review and production-sentinel workflows: role eligibility and independence, input digest, verdict/disagreement/re-review rules, fail-closed unavailability state, sentinel ownership/versioning/normalization, and binding of the exact sentinel digest to capability and runtime attempts.

## Verdict

**Revise.** The contender clears the bar for a high-quality credential, consent, egress, privacy, and incident-control direction, and much of its test corpus should survive synthesis. It misses P2's ship bar because the mandatory provider-egress mechanism is not implementable as described, the incident/approval/audit contracts drift from frozen architecture, and runtime authorization, nested-runtime review, and security-finding rules remain incomplete.
