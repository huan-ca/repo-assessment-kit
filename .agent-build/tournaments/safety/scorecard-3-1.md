## Scores

- **Requirements coverage — 4/10.** Contender 3 thoroughly covers evidence admission, redaction, active-content rendering, packaging, retention, and post-delivery leaks, but P2 explicitly requires malicious-source attacker models, prohibited actions, container/nested-runtime controls, target-egress states, runtime-test safety classes, prompt-injection defenses, and audit/severity rules; most of those are absent or only named as assets.
- **Control enforceability and testability — 6/10.** Covered controls are often excellent, deterministic, and fixture-backed—for example the admission algorithm (§4.3), package state certificates (§8.2), and hostile package tests (§11.5)—but high-risk statements such as secret “inaccessibility” (§5.1), hosted-service disclosure (§3.2), and stopping runtime/provider activity (§10.1) have no authorization, network-policy, broker-protocol, or audit-event enforcement contract.
- **Evidence integrity and validation — 9/10.** The blob/occurrence split (§4.1), fenced admission (§4.3), truncation semantics (§4.4), typed report boundary (§6.2), staged package validation (§8), and negative fixtures (§11) are precise and substantially satisfy the brief’s traceability, honesty, redaction, and package-integrity requirements.
- **Operational usability — 5/10.** Retention, incident, review, and no-recall language is useful, but four mandatory reviews plus inspection of every packaged customer-confidential derivative (§7.2) lack role eligibility, delegation, queue/batching, timeout, disagreement, replacement-reviewer, or solo-operator handling; the result can deadlock normal delivery without telling the operator how to recover.
- **Residual-risk treatment — 6/10.** §13 is candid about detector misses, approved-destination exfiltration, unsigned digests, recipient redistribution, parser/host compromise, and delayed deletion, but it cannot adequately characterize residual prompt-injection, build/runtime escape, production-contact, or dependency-supply-chain risk because those source-to-impact paths were never modeled or controlled.
- **Buildability and architecture fit — 5/10.** §14 gives useful lane ownership and many covered controls map to frozen architecture, but the spec does not review or operationalize the architecture’s security-critical host-helper protocol, Compose compiler, Lima/rootless runtime, VM secret-envelope profile, network classes, or emergency-stop lifecycle; backend and foundation lanes would still have to invent the safety policy P2 exists to freeze.

## Overall

**5.8/10.** The score reflects a high-quality evidence-integrity sub-spec embedded in an incomplete product safety spec. Its strongest material is reusable, but it does not clear P2’s “every trust boundary and prohibited action” bar.

## Strongest objection

The threat model stops before the most dangerous source-to-impact chain. The spec labels repository instructions, Docker/Compose files, provider output, the host helper, and runtime broker as trust-boundary participants (§2.2, lines 50–69), but never traces or constrains:

`hostile repository/instruction → provider/model decision or tool request → approved dependency/optional-service egress or typed host-helper call → build/runtime target → sandbox credential, customer source, network, VM, or host impact`.

That omission is visible in the complete absence of a prompt-injection section and the lack of substantive Docker/Lima/Compose/runtime-network policy: “instructions” appears only in the untrusted-input list, while Docker/Compose and the runtime broker are only named. This fails PLAN P2’s explicit prompt-injection, nested-runtime, target-egress, runtime-test-class, safe-failure, and emergency-stop requirements (PLAN lines 80–93) and leaves the frozen architecture’s most security-critical contracts unreviewed: provider prompt-injection fixtures (architecture line 2290), Compose rejection corpus (2295), runtime egress/privilege/isolation/emergency-stop tests (2296–2297), and the VM secret-envelope profile that “must” receive safety review (1551–1557). A malicious repository can therefore be perfectly redacted after the system has already performed an unsafe action.

## Other findings

1. **Must-fix — No attacker/actor model or authority matrix (§2).** “Product-specific threat model” lists assets, trusted components, untrusted bytes, and artifact-centric abuse stories, but not malicious repository author, compromised dependency/registry, compromised target service, prompt-injected provider, malicious operator, local user/browser origin, or optional-service/provider adversary. Without actor capabilities and prohibited authority, “No provider…can directly create” customer state (§2.2) does not address indirect influence over workflow proposals, coverage, egress requests, runtime selection, or operator approvals.

2. **Must-fix — Runtime isolation is effectively unspecified (§2.2, §10, §11).** The frozen architecture requires a disposable Lima VM, rootless Docker, default-deny IPv4/IPv6/DNS, internal-only probes, no host ports/socket, dropped capabilities, read-only roots, cgroup limits, a strict Compose compiler, and residue-aware emergency stop (architecture §§10.1–10.4). Contender 3 offers no normative review of these controls and no repository fixtures for privileged containers, devices, namespace sharing, unsafe sysctls, bind mounts, remote build contexts, Dockerfile exfiltration, metadata/LAN routes, DNS, mutable images, or orphan cleanup.

3. **Must-fix — Prompt injection has no prevention or verification contract (entire spec).** Repository instructions are merely declared untrusted (line 59), and provider output is prevented from directly admitting evidence (lines 67–69). The spec never limits provider tools/context, prevents repository-owned `AGENTS.md`/MCP/plugin instructions from expanding authority, separates system policy from repository text, validates proposed calls, denies approval creation, records injection encounters, or defines canary tests across both Codex and Claude. PLAN P7 specifically requires seeded prompt-injection fixtures.

4. **Must-fix — Egress and optional-service controls stop at disclosure (§3.2, §10.5, §13).** The spec requires naming destination/data categories before approval (lines 137–140) and admits allowlist limits (lines 744–746), but does not define the architecture’s separate `provider-inference`, `git-acquisition`, `build-acquisition`, `target-runtime`, and `optional-service` states, approval binding/expiry/revocation, DNS/IP enforcement, byte/destination audit receipts, no-silent-fallback behavior, or how an operator emergency-stops uncertain egress. It therefore cannot prove the brief’s no-production/no-silent-upload boundary.

5. **Must-fix — Credential lifecycle does not review the frozen VM protocol (§5.1).** Opaque one-use handles and revocation are good, but the spec does not examine the architecture’s X25519/HKDF/AES-GCM envelope, associated-data binding, recipient/service isolation, tmpfs exposure, provider/SSH-purpose prohibition, replay/wrong-recipient/expiry behavior, or cleanup residue. The required production-like sentinel endpoint/credential acceptance test from AC-4 is also absent.

6. **Must-fix — Package/dependency execution attack path is missing.** Pinned Gitleaks/Trivy and age versions are specified, but there is no rule that static assessment must not run target package managers, install scripts, hooks, builds, test plugins, custom reporters, or repository scanner configuration; no worker-image/toolchain signature/lock verification; and no policy for dependency acquisition beyond generic disclosure. This leaves hostile `package.json`, lockfiles, Maven/Gradle plugins, Dockerfiles, and registry substitutions outside the threat model despite the architecture’s explicit non-execution baseline (architecture lines 2043–2055).

7. **Must-fix — Runtime-test authorization and prohibited actions are absent.** The brief prohibits destructive external actions and production access, while P2 requires runtime-test safety classes. The contender defines screenshot hygiene but not allowed HTTP methods/actions, destructive route suppression, passive-vs-active probe classes, scope/origin enforcement, production endpoint sentinels, operator elevation rules, or a control-to-authorization matrix. Screenshot capture being safe does not make the preceding browser action safe.

8. **Must-fix — Security finding semantics are incomplete (§7).** Independent review outcomes are defined, but technical severity, business priority, confidence, validation state, CVSS sufficiency, imported-finding treatment, disputes, supersession, and release policy for unresolved lower-severity findings are not. The opening blocks “unreviewed High/Critical” only (lines 24–28), leaving ambiguous whether disputed or unvalidated medium findings can silently affect coverage or decision confidence.

9. **Should-fix — Human review policy is not operationally bounded (§7.2).** “Every artifact classified customer-confidential or derived from secret-suspected input” (lines 412–415) can encompass most source-derived evidence. Define reviewer eligibility and independence, review input digest, workload presentation, re-review triggers, conflicting verdict resolution, and what happens when a qualified second human is unavailable; otherwise the state machine is enforceable only by permanently blocking release.

10. **Should-fix — Audit-event vocabulary is missing.** The spec records provenance and some tombstone/incident metadata, but P2 calls for audit events across approvals, credential issue/redeem/revoke, egress, policy denial, prompt injection, helper/runtime commands, emergency stop, cleanup residue, evidence admission, review, and release. Without event names, safe payload allowlists, retention, actor IDs, and correlation IDs, enforcement cannot be independently demonstrated.

## Concrete fixes

1. Add an actor/capability matrix and at least six complete source-to-impact attack trees: prompt-injected provider; malicious source acquisition; target package/build execution; Compose/runtime escape; credential-to-target-to-egress; and optional-service/provider exfiltration. For every edge, name the enforcing component, immutable input/approval binding, audit event, failure state, and adversarial fixture.
2. Add a normative prompt-injection section: repository instructions and MCP/plugin/config are data only; provider tasks use fixed tool allowlists and bounded safe evidence APIs; models cannot approve capabilities, alter policies, select arbitrary destinations/commands, access secrets, or call helper/runtime directly; every proposal is schema/policy validated; test both agents with instruction, filename, code-comment, scanner-output, and web-response injections.
3. Review the frozen runtime architecture explicitly. Adopt or reject each Compose compiler rule, VM/rootless/cgroup/firewall control, host-helper authentication/fencing rule, cleanup-residue behavior, and emergency-stop sequence. Add negative fixtures for every rejected mount, capability, namespace, route, image, build context, and external network path.
4. Define the egress state machine per architecture network class, including exact destination and data-category approvals, expiry/revocation, proxy/firewall/DNS enforcement, byte/destination receipts, default-deny runtime DNS, no fallback, production/LAN/metadata endpoint denial, and uncertainty handling.
5. Review the VM secret-envelope construction and write lifecycle requirements from capture through one-use redemption, target/probe exposure, expiry, cancellation, crash reconciliation, and residue. Add replay, wrong runtime/run/purpose/recipient, stale approval, malformed ciphertext, target exfiltration, and production-sentinel tests.
6. Freeze runtime-test safety classes and prohibited actions: passive observation, read-only authenticated checks, narrowly approved reversible mutations, and prohibited destructive/production/network actions. Bind each planned control to allowed methods, origin, credential handle, data scope, egress policy, and emergency stop.
7. Add target dependency/package controls: static analyzers never execute repository package managers, hooks, plugins, builds, tests, config, or reporters; any build acquisition occurs only in the VM under explicit approval and locked destinations; pin and verify worker images/tools/rules/licenses per architecture toolchain lock.
8. Add security-finding and audit contracts: separate severity, business priority, confidence, validation, and review status; define CVSS prerequisites, dispute/supersession behavior, package effects, and a typed safe audit-event catalog. Operationalize human reviews with eligibility, digest binding, disagreement and re-review rules, and bounded UI workflow.

## Verdict

**Reject.** It clears a high bar as an evidence-integrity, redaction, rendering, and packaging specification, but misses the P2 gate for complete product safety. The required revision is architectural in scope: it must model and constrain hostile source, provider prompt injection, dependency execution, host-helper/runtime/VM escape, credential delivery, egress, runtime authorization, and emergency stop before implementation can safely proceed.
