## Scores

- **Requirements coverage — 8.5/10.** The §1.3 ownership map, §4 native-document catalog, §7 API inventory, §8 release gates, and §10/§12 blocker matrix cover almost every Must and make degraded runtime explicit; source before/after verification and signal-driven deeper-profile recommendations are named but not frozen as executable contracts.
- **Hostile-repository isolation — 6.5/10.** The mount-free VM, no-host-socket rule, compiled Compose policy, no-network analyzers, and quarantine boundary are strong, but §§2/3.6/7.6 require fixed worker services to receive a per-attempt read-only snapshot and “only” the current writable outbox without any mechanism that can change mounts or transfer those objects, while §3.7 merely asserts that a provider model can invoke only `rakctl`.
- **Source immutability — 7.5/10.** §3.4 correctly distinguishes commit-only from frozen-working-tree identity, rejects unsafe filesystem entries, and hashes exported content, but it says only that the exported snapshot is checked before/after each assessment class; it does not freeze the required before/after algorithm for the operator's original tracked and untracked tree or its concurrent-mutation behavior.
- **Cross-agent equivalence — 7/10.** §§3.7 and 9.5 establish shared schemas, artifact classes, coverage vocabulary, independent review, and package gates while correctly rejecting byte identity; they do not define a frozen mandatory control-plan digest, minimum evidence-sufficiency rules, or an escalation rule when both providers produce valid but materially different findings or recommendations.
- **Evidence integrity — 7.5/10.** §§3.5 and 8 provide content addressing, immutable derivation, semantic validation, redaction, collision-safe packaging, and fresh-process ZIP verification; however, hostile scanner/log/screenshot normalization runs in trusted Node worker threads (§2), the ledger lacks a trusted terminal anchor during recovery, and privacy deletion across quarantine/backups is absent.
- **Resumability — 7.5/10.** §§5.5–6 define leases, checkpoints, append-only attempts, cancellation, database checks, and orphan cleanup, but state diagrams omit complete guards/transactional side effects and external broker effects lack a durable effect/reconciliation protocol for crashes between VM/Docker action and SQLite response commit.
- **Portability — 7/10.** The architecture honestly makes the four-host Lima path, Node 24/`better-sqlite3`, Claude, ARM64 browser, and ZAP support release blockers rather than silently downgrading them; nevertheless, all of those are still unproven and the fixed-worker volume model is not portable as specified because normal Compose cannot remount services per attempt.
- **Build-lane contracts — 6/10.** Endpoint inventories and protocol envelopes are useful, but undefined response types, prose-only native schemas, incomplete database constraints, an analyzer request that contains only `snapshotId`, an undefined one-use credential channel, and an uninstantiated egress proxy still force P4–P6 to invent security-critical behavior.
- **Operability — 7.5/10.** Explicit budgets, health/readiness, structured failures, checkpoints, backups, signal/orphan tests, observability, and release blockers are substantial; recovery runbooks, secure purge/retention, host/container bind semantics, and privileged-effect reconciliation are not operationally closed.
- **Simplicity — 6/10.** A single control-plane writer and fixed analyzer set avoid distributed scheduling and arbitrary plugins, but the MVP still combines SQLite, CAS, a hash-chain ledger, checkpoints, engagement provider homes, multiple fixed workers, a host launcher, Lima, a broker, rootless Docker, an egress proxy implied but not modeled, numerous projections, and optional encryption; several boundaries duplicate state without one compact reconciliation invariant.

## Overall

**7.2/10 (equal-weighted average, rounded).** This is a notably rigorous architecture in intent and it has strong failure, evidence, and release-gate thinking. It does not clear the P1 freeze bar because several non-functional guarantees are descriptions that the selected deployment topology cannot yet enforce.

## Strongest objection

**Must fix — the static-worker isolation contract is not implementable with the declared topology.** Section 2 says static workers are “predeclared hardened services” so the server needs no Docker API; §3.6 simultaneously says each worker “mounts snapshots read-only and only its current outbox writable”; and §7.6 sends only a `snapshotId` and later refers to an `outboxName`, with no object transfer, descriptor passing, or supervisor protocol. Docker/Compose mounts are fixed when a service container is created. A long-lived fixed worker therefore cannot be given a different per-attempt snapshot and writable outbox without either (a) mounting broad parent directories, which lets a compromised analyzer read other snapshots and write/read other attempts, or (b) dynamically recreating containers, which contradicts the no-container-API design. This breaks the central hostile-repository and cross-engagement isolation claim and forces the implementation lane to redesign a trust boundary.

## Other findings

1. **Must fix — provider command confinement is asserted rather than enforced (§3.7, §7.5, ADR-003).** “The model can invoke only `rakctl`” is not produced by Codex `workspace-write` plus approval `never`; those settings are not a command allowlist. The provider process also owns its engagement home and credential. The spec needs an enforceable process/tool mediation boundary, not only a narrower application socket, or hostile repository instructions can drive shell/file reads and submit sensitive content through otherwise valid commands.
2. **Must fix — egress controls have no enforceable network design (§§3.9, 7.3 approvals, 7.7, 9.1, ADR-007).** The architecture promises destination/byte/time-scoped, proxied build egress and offline runtime, but the diagram and repository layout contain no proxy/firewall component or protocol. It does not freeze DNS pinning/rebinding behavior, redirects, direct IP/IPv6 and UDP denial, private/link-local/metadata ranges, TLS tunneling, Docker pull/build traffic, or whether method restrictions are observable. “Internal” Docker networking alone does not prove a hostile container cannot reach the VM gateway or broker.
3. **Must fix — hostile output is parsed inside the highest-trust process (§2, §§3.5/3.11, §8).** Normalization, hashing, redaction, report rendering, archive validation, and screenshot/log metadata handling run in Node worker threads behind the sole SQLite writer. Worker threads provide concurrency, not fault or security isolation. A malformed scanner result or target-produced evidence can crash or compromise the process that owns SQLite, the vault, admitted evidence, and packaging. The threat model explicitly names poisoned tool data but assigns it no parsing sandbox.
4. **Must fix — source integrity evidence does not implement AC-2 (§3.4, §5.2).** The `targets` table has `before/after digest`, but the algorithm checks the exported snapshot, not the original local repository's tracked and untracked state after the assessment. It also omits a stable-copy/race rule if the operator or another process changes the local tree during capture. Read-only mounting reduces assessor writes but is not the required evidenced before/after integrity check.
5. **Must fix — broker external effects are not transactionally resumable (§§6.3–6.4, 7.7).** Idempotency keys and expected digests do not specify where the broker durably stores accepted/effect-created/completed results, how stable Docker/VM resource names derive from a command, or what happens after a crash following creation but before response persistence. Retrying can duplicate resources or misclassify coverage; restoring SQLite can lose the only orchestration record.
6. **Must fix — the secret boundary overclaims its mechanism (§5.3, §§7.3/7.7).** “Server-owned locked-memory/tmpfs vault” is not a defined Node 24 implementation: JSON body parsing creates ordinary heap copies, no `mlock`/zeroization/fallback contract is selected, and crash-dump/swap behavior is omitted. The broker receives credentials through an undefined “one-use channel,” with no authenticated key exchange, use count, acknowledgement, expiry, or revocation semantics.
7. **Should fix — Docker loopback wording is internally inconsistent (§2, §7.1, §9.1).** Publishing the host port as `127.0.0.1:host:container` is correct, but a server bound to loopback inside its container is normally unreachable through Docker port publishing, while requests arrive from a bridge/proxy address rather than a physical-host loopback address. Freeze separate physical-host publish, container listen, trusted-proxy, forwarded-header, Host, and Origin rules.
8. **Should fix — sensitive-data retention and purge are missing (§§3.5, 5.4–5.5, 9.1/9.4).** Raw quarantine may contain repository secrets; state backups, provider homes, CAS objects, VM disks, failed staging trees, packages, and logs can persist. An engagement retention field without defaults, a purge graph, deletion outcomes, and disclosure of non-guaranteed secure erasure is not adequate privacy lifecycle design.
9. **Should fix — the ledger deletion claim is too strong (§3.5).** A previous-hash chain detects interior modification only relative to a trusted terminal commitment. A valid-looking suffix truncation can survive SQLite reconstruction unless every checkpoint/final state anchors the expected sequence and terminal hash somewhere an attacker cannot truncate in tandem.
10. **Should fix — deeper-profile recommendation is not contracted (§§3.10, 4.2, 7.3).** AC-7 requires observed signals, a named recommended profile, cited triggers, and customer-confirmation labeling. The control planner and profile registry are named, but no native document, signal/rule registry, API shape, or validation gate makes this behavior testable.
11. **Nice to have — performance targets need a reproducible reference (§9.2).** “Reference hardware” is undefined, and the 100,000-row p95 target does not specify concurrency, cache state, query mix, measurement window, or minimum disk characteristics. These numbers cannot currently serve as acceptance gates.

## Concrete fixes

1. Choose and freeze one implementable analyzer isolation model. Prefer content-addressed snapshot transfer into a worker-private tmpfs plus length/digest-checked output streaming back to admission, or define a narrow trusted worker supervisor that launches one ephemeral container per attempt without exposing its lifecycle capability to the server/provider. Add mount/object ownership, UID, socket authentication, quotas, cleanup, and cross-run denial tests.
2. Add a provider-tool enforcement design for each CLI: exact available tools/commands, filesystem namespace, network namespace, provider-home visibility, source/context projection, scratch/outbox ownership, command mediation, credential canaries, and a test proving repository prompt injection cannot run `cat`, shell, HTTP, or arbitrary `rakctl` submissions.
3. Specify the network data plane: proxy/firewall placement, separate acquisition/build/runtime namespaces, Docker daemon pull/build routing, DNS resolution and pinning, redirect/TLS policy, private/link-local/metadata and IPv6/UDP denial, broker/gateway reachability tests, byte/time accounting, and exact audit evidence. Distinguish enforceable network properties from operator-declared data purpose.
4. Move normalization and risky evidence parsing into resource-bounded, no-secret, no-DB worker processes/containers. Define canonical input/output schemas and make the trusted server admit only validated, bounded results.
5. Freeze the original-source integrity protocol, including pre-capture and post-assessment manifests for tracked and untracked content, Git object identity, concurrent-mutation detection/retry, submodule/LFS/filter/config behavior, and explicit failure/limitation outcomes.
6. Add a durable broker effect ledger and reconciliation state machine with stable resource names derived from command IDs, fsynced terminal responses, duplicate semantics, observe/compensate operations, crash injection at every boundary, and behavior when SQLite is restored.
7. Replace the “locked-memory” claim with a proven supported implementation or narrow it to an ephemeral process-isolated vault with explicit heap-memory residual risk. Freeze streaming secret ingestion where possible and the broker credential channel's encryption, authentication, TTL, one-use acknowledgement, revocation, and zeroization rules.
8. Freeze host/container binding and proxy-header behavior with runnable negative fixtures for LAN binding, DNS rebinding, hostile Origin/Host, CSRF, and bootstrap replay.
9. Add a retention/purge state machine spanning quarantine, CAS, staging, packages, SQLite/WAL/backups, provider homes, VM disks, caches, and logs; define safe defaults and recorded deletion failures.
10. Anchor ledger sequence and terminal hash in each immutable checkpoint and final detached metadata, and require reconstruction to reject missing tails or conflicting heads.
11. Add a `profile-recommendation` contract with trigger evidence, rule/profile version, applicability state, customer-confirmation requirement, API/report projection, and final validation rules.

## Verdict

**revise.** The contender clears the bar for threat awareness, explicit degraded behavior, evidence/package rigor, release blockers, and operational ambition. It misses the ship bar because its fixed-worker topology cannot enforce the per-attempt isolation it promises, and provider command confinement, egress mediation, hostile-output parsing, secret transfer, and crash-safe privileged effects remain non-functional claims rather than frozen mechanisms.
