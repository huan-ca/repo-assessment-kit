## Scores

- **Requirements coverage — 8.3/10.** The spec covers nearly every Must with explicit lifecycle, package, runtime, review, and portability gates, but it does not freeze the required discovery-topic identifiers or the common modernization criterion set, and line 369 permits a `pass` control without supporting evidence despite AC-4.
- **Hostile-repository isolation — 8.6/10.** The no-network analyzer containers, mount-free disposable VM, compiled Compose subset, broker-only Docker access, and one-way admission path are unusually rigorous; however, the source-acquisition/host-executor boundary and UDS authentication protocol are missing precisely where hostile paths and SSH access enter.
- **Source immutability — 8.1/10.** Lines 322–332 correctly distinguish commit-only from frozen dirty-tree snapshots and define a deterministic manifest, symlink handling, and before/after checks, but no executable acquisition/export protocol explains how a containerized server safely reads an arbitrary host local path or asks the host helper to export it.
- **Cross-agent equivalence — 8.8/10.** Lines 189–217 define common tasks/outcomes and a shared conformance harness, while lines 852–853 make provider-specific omissions fail; the exact required domain/artifact matrix and task-kind acceptance payloads remain named rather than specified, and both adapters are required to claim resume/schema-output support before the Claude path has proved it.
- **Evidence integrity — 7.5/10.** One-way admission, immutable derivations, strict schemas, semantic validation, raw-output retention, projections, and ZIP re-verification are strong, but lines 369–370 fail to require evidence for `pass`, and lines 431, 473–476 conflict with the API at line 527 over whether `unverified`/`conflicting` are provenance values or assertion states.
- **Resumability — 7.1/10.** CAS transitions, leases, idempotency records, preserved attempts, recovery reconciliation, and context-digest checks are solid; the revision identity is internally ambiguous because `runs` has one `revision`, no lineage/engagement key, a weak uniqueness constraint, and no FK to the prior immutable revision, while `failed -> ready` is allowed even after packaging freezes the revision.
- **Portability — 7.7/10.** Multi-architecture image digests, native-host release gates, driver validation, and blocked-runtime behavior honor the platform promise honestly; Lima/rootless Docker, ARM64 Chromium/ZAP, Claude, and `better-sqlite3` are still empirical blockers, and host-helper installation/upgrade/version negotiation is not operationally specified.
- **Build-lane contracts — 6.8/10.** The package ownership map, HTTP table, fixtures, state vocabulary, and plugin manifest are useful seams, but several critical interfaces are only names: `TargetResolution`, `RuntimeCommand`, `RuntimeOutcome`, `EvidenceBundle`, and executor responses have no schemas, and `ExecutorCommand` lacks source acquisition plus analyzer status/stop/cancel operations.
- **Operability — 7.8/10.** The spec has concrete budgets, readiness behavior, metrics, structured logs, failure modes, emergency stop, backups, and package recovery; operators still lack a defined mechanism for supplying sandbox credentials, selecting/authorizing local host paths, diagnosing host-helper protocol incompatibility, or recovering a frozen packaging failure without lifecycle ambiguity.
- **Simplicity — 7.2/10.** Most complexity follows from the hostile-runtime and evidence requirements, and the spec explicitly rejects a marketplace and arbitrary extensions; nevertheless, a provider SPI, analyzer SPI, capability registry, host executor, VM broker, native schema family, projections, and revision machinery form a very large MVP, while foundational source and executor contracts remain unfinished.

## Overall

**7.8/10.** This is a strong security architecture and a good systems design, but not yet a contract freeze. Its weakest points occur at the exact cross-process seams that backend, DevOps, and persistence lanes must implement independently.

## Strongest objection

**Must-fix: the trusted source-acquisition boundary is contradictory and unbuildable as written.** `POST /api/v1/runs` accepts an arbitrary local host path or SSH Git URL (line 524), `Source intake` is said to export the immutable snapshot (line 144), and the credential matrix assigns an “acquisition action” to the host executor (line 591). Yet the exhaustive `ExecutorCommand` union at lines 243–250 contains only analyzer and runtime commands, explicitly accepts no host path, and defines neither acquisition status/result nor snapshot-transfer semantics. A server inside Docker cannot safely open an arbitrary host path without a prearranged mount, and it cannot use host SSH material through the described narrow helper without a protocol. Implementers must therefore invent either a broad host mount, a new privileged command surface, or launcher-specific copying—each changes the trust boundary and risks source mutation or SSH leakage. This should block freezing the architecture.

## Other findings

1. **Must-fix — successful controls can be unevidenced.** Lines 369–370 require evidence or a limitation for every state *except* `pass`. AC-4 requires supporting evidence for every planned runtime control, and the product’s central integrity claim cannot allow an unsupported pass. `control_results` at line 445 also does not state non-null/cardinality rules for activity/evidence links.
2. **Must-fix — assertion provenance has two incompatible models.** Lines 473–475 say `unverified` and `conflicting` are states, not sources; `product_assertions` at line 431 has both a provenance enum and status, but the discovery API at line 527 exposes only `provenance` and appears to put all seven labels in that field. This prevents lossless capture of combinations such as documented-but-conflicting and makes the cross-agent schema non-equivalent.
3. **Must-fix — revision lineage cannot enforce the promised audit history.** The `runs` relation at line 429 has no engagement/lineage key or prior-revision FK, and uniqueness on `(project_slug, revision, created_at)` permits duplicate revision numbers trivially. It is unclear whether `/revisions` creates a new run row/ID or mutates a run. That ambiguity undermines “never overwrites,” package-to-revision identity, and reliable resume.
4. **Must-fix — executor and runtime contracts are declarations, not buildable interfaces.** The executor union has no response envelope, protocol version negotiation, error vocabulary, analyzer status/cancel, or reconciliation/list operation. `RuntimeCommand v1` and `RuntimeOutcome v1` are mentioned at line 147 but never defined. UDS “authentication” at line 254 does not define peer credential checks, framing, permissions, replay protection, or compatibility handling.
5. **Must-fix — modernization comparisons are not constrained to the same criteria.** `decision_options` at line 447 merely stores “criterion results”; neither the schema summary nor API contract enumerates required criteria or enforces the same set for remediation, incremental replacement, and rebuild. The brief specifically requires recoverability, boundaries, security/engineering risk, critical parity, scale, and rebuild feasibility to be compared consistently.
6. **Must-fix — packaging-failure recovery conflicts with freezing.** Lines 336–347 allow `packaging -> failed -> ready` while packaging freezes admitted data permanently. The API’s generic resume route does not distinguish retrying a pure packaging operation from correcting redaction/evidence/report failures that require a new revision.
7. **Should-fix — discovery completeness is asserted but not contracted.** Line 527 says all topics are validated but never defines stable topic IDs, required multiplicity, unknown impact, or how unknowns affect confidence/coverage. Frontend and backend can independently invent incompatible topic models despite “frozen” schemas.
8. **Should-fix — credential delivery is a placeholder boundary.** `credentialHandle` and a “purpose-specific ephemeral channel” are referenced, but no launcher/API/broker lifecycle specifies creation, binding to a run/service, one-time consumption, revocation, restart behavior, or redacted audit. Safe runtime depends on this.
9. **Should-fix — `CapabilitySnapshot` can encode incoherent combinations.** The example permits independent `support`, `attestation`, `approval`, and `effective` strings but provides no truth table or precedence rules. Providers/plugins cannot grant access, but two implementations could calculate different `effective` results from the same inputs.
10. **Nice-to-have — package self-description is needlessly subtle.** Lines 750–753 put both `manifest.json` and `SHA256SUMS` in the manifest without their self-referential metadata, then hash only the manifest in `SHA256SUMS`. This can be valid, but the exact special-entry schema and verification order should be fixture-defined to prevent packager/verifier disagreement.

## Concrete fixes

1. Add a versioned `SourceCommand`/`SourceOutcome` protocol to the host boundary for Git and local inputs, including canonical-path authorization, immutable export destination, SSH credential-token handling, progress/status/cancel, before/after manifests, error codes, limits, and explicit mount/copy semantics. Show the process and network path in the trust diagram and credential matrix.
2. Fully specify executor request/response envelopes: protocol version, request authentication and peer authorization, framing, replay/idempotency behavior, analyzer status/cancel/reconcile, runtime lifecycle responses, typed errors, timeout semantics, and compatibility failure behavior.
3. Make every `pass` control require at least one admitted evidence/activity reference. Define exact evidence cardinality and reason requirements per each of the six states, then enforce them in JSON Schema plus semantic fixtures.
4. Split assertions into `provenanceSource` and `epistemicState` (or provide an equally lossless mapping), define legal combinations, and make SQLite, API, agent outcome, native JSON, and report projections use the same vocabulary.
5. Introduce an immutable assessment-lineage/engagement ID and model each revision as a distinct row with unique `(lineage_id, revision)`, an FK to its predecessor, immutable-input/profile digests, and an unambiguous run-directory/package identity. Define whether retry is a new attempt or revision.
6. Split failure recovery transitions by failure class: packaging retries may reuse a frozen revision only when no admitted/report content changes; validation/redaction/content corrections must create a new revision. Encode this in the state table and endpoint preconditions.
7. Freeze stable discovery topic IDs and a required decision-criterion registry. Require all three options to contain the identical criterion set, with per-criterion evidence/state/confidence, and add semantic validation for that equality.
8. Define the ephemeral credential channel and capability reduction truth table as normative contracts, with lifecycle, restart, expiry/revocation, audit, and conformance fixtures.

## Verdict

**Revise.** The contender clears the bar for architectural direction and hostile-runtime strategy, but misses the contract-freeze bar: source intake, privileged execution, revision lineage, successful-control evidence, and assertion semantics still require cross-lane invention that would cause security and data-model rework.
