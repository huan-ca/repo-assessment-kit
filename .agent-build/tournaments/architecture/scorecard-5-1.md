## Scores

- **Requirements coverage — 9/10.** The requirements-to-components map in §1.3, canonical document inventory in §4.2, API inventory in §7.3, and release blockers in §10 cover nearly every Must and explicitly preserve static assessment when runtime is blocked; the missing implementation-level schemas prevent full credit.
- **Hostile-repository isolation — 9/10.** §§1.2, 3.6, and 3.9 consistently treat source, Compose, Dockerfiles, scanner input, and web content as hostile, deny the host Docker socket, isolate runtime in a mount-free VM, and prohibit arbitrary command forwarding; the provider outbox/write boundary and one-use credential channel remain underspecified.
- **Source immutability — 9/10.** §3.4 correctly distinguishes `commit-only` from `frozen-working-tree`, binds dirty content to a deterministic manifest digest, rejects special files/path escape, and verifies the snapshot before and after assessment classes; “assessment class” and the exact integrity-check scheduling are not formally defined.
- **Cross-agent equivalence — 7/10.** §§3.7 and 9.5 correctly require separate homes, a common `rakctl` protocol, common schemas, six-state coverage, artifacts, and package validation without byte identity, but the promised “deterministic acceptance harness” has no comparison algorithm, fixture contract, minimum domain/control set, or rule for materially divergent but individually schema-valid conclusions.
- **Evidence integrity — 8/10.** §§3.5, 4, and 8 provide strong admission, immutable derivation, semantic validation, redaction, and ZIP-reopen controls; however, the claim that the hash chain “detects deletion/reordering within the run ledger” overstates what is guaranteed because no externally anchored terminal hash or explicit tail-truncation check is frozen.
- **Resumability — 7.5/10.** §§5.5 and 6 define checkpoints, leases, append-only retries, SQLite recovery, cancellation, and orphan cleanup, but the state diagrams do not freeze guards and side effects, merge phase and check lifecycle semantics, leave “active state” undefined, and do not specify how skipped/terminal-failed checks acquire the mandatory coverage result.
- **Portability — 8/10.** The Lima/rootless-Docker design and §10/§12 native release gates honestly preserve macOS/Linux and ARM64/x86-64 as blockers rather than claiming unproven support; the architecture remains dependent on unresolved native SQLite, Claude, Chromium/ZAP, and four-host validation, appropriately preventing a higher score.
- **Build-lane contracts — 5.5/10.** §7 supplies useful endpoint inventories and envelopes, but §4.2 is only a prose field list, §5.2 omits SQL types/nullability/cascades/index details, discovery uses `value: ...`, public responses rely on undefined `RunDetail`, `Operation`, `Claim`, and other types, and broker/worker/provider bodies are only partially specified. This does not meet P1’s requirement that schemas, data model, APIs, analyzer interface, report/export contracts, and transition tables be implementation-ready before parallel lanes begin.
- **Operability — 8/10.** The design has explicit preflight, health, failure envelopes, budgets, backup/recovery, observability, cleanup, and release-test gates; operator-visible recovery procedures and the exact reconciliation algorithm remain referenced rather than contracted.
- **Simplicity — 6.5/10.** The single writer and fixed workers are sensible reductions, but CAS plus a filesystem ledger plus canonical checkpoints plus SQLite indexes, a host launcher, VM broker, multiple approval classes, and many packages create substantial consistency surface. Much is justified by the threat model, yet the spec does not prove that both ledger and checkpoint layers are independently necessary or define one authoritative reconciliation invariant.

## Overall

**7.8/10.** The architecture is security-conscious, comprehensive, and directionally correct, but it misses the P1 threshold because the contracts that parallel implementation depends on are catalogued rather than actually frozen.

## Strongest objection

**Must fix — P1 defers its central deliverable to Milestone 0 instead of containing it.** Section 4 says “Schemas live at `packages/contracts/schemas/rak/1.0/`,” §7 repeatedly refers to unnamed or undefined shapes such as `RunDetail`, `Operation`, “full product assertion shape,” and provider submissions that “match the public native schemas,” while §10 lists “RAK 1 schemas,” “state-transition tables,” and broker/worker request schemas as future Milestone 0 deliverables. The PLAN says P1 itself must freeze those schemas, the data model, lifecycle, APIs, agent/analyzer interfaces, and export contracts so downstream lanes do not improvise. As written, backend, frontend, provider, reporting, and QA can all implement incompatible meanings while remaining faithful to this document; that is the highest-probability source of expensive rework.

## Other findings

1. **Must fix — lifecycle and coverage invariants are not mechanically closed (§§6.1–6.3, 8.1).** “Any active state → failed” does not define `active`; the arrow diagrams do not state guards, commands, emitted events, or transactional side effects; phase and check share one state graph even though a phase aggregates checks; and `skipped`/`terminal-failed` is not mapped to the required `blocked|not applicable|not tested|partial|fail` control result. A run can therefore reach validation with ambiguous coverage semantics.
2. **Must fix — cross-agent equivalence can pass two materially different assessments (§9.5).** Requiring each output to have valid schemas, artifact classes, and six-state coverage says nothing about whether both providers used the same mandatory controls, evidence sufficiency rules, decision criteria, or divergence review threshold. The phrase “deterministic acceptance harness” is an assertion, not a contract.
3. **Must fix — the database model is not migration-ready (§5.2).** The table lists omit concrete SQLite types, nullability, defaults, FK actions, check constraints, JSON schema identifiers, and most indexes. Several integrity-critical references are stored as JSON and deferred to “semantic validators before checkpoint/finalization,” allowing invalid live operational state and leaving repository implementations to choose incompatible behavior.
4. **Must fix — provider evidence production has an unresolved capability edge (§§3.7, 7.5).** The provider “can invoke only `rakctl`,” but `evidence.submit` may reference a “current attempt outbox”; the spec never states what directory the provider can write, how that path is mounted, how filenames are bound to the attempt, or how model-generated files reach quarantine without giving broader filesystem authority.
5. **Must fix — the analyzer normalization contract is too generic (§§3.6, 7.6).** The worker envelope identifies objects and one coverage result, but it does not freeze per-adapter native-version acceptance, finding normalization, location/fingerprint rules, partial-coverage aggregation, or how multiple controls map to one invocation. “The adapter owns” those decisions pushes correctness into the build lane.
6. **Should fix — the ledger tamper claim is stronger than the mechanism (§3.5).** A previous-hash chain detects interior mutation when a trusted head/tail is known, but deletion of an unanchored suffix can look like a shorter valid chain, especially during SQLite reconstruction. Package/checkpoint anchoring may solve this, but the trusted terminal commitment and reconciliation rule are not stated.
7. **Should fix — the package manifest special case is not represented as a validator contract (§8.3).** `manifest.json` declares itself and `SHA256SUMS` while omitting their digest/size, then later validation rejects size/path mismatches. The exception is plausible but needs an exact schema and validation rule so independent validators agree.
8. **Should fix — “locked-memory/tmpfs vault” is not a concrete Node contract (§5.3).** The spec does not choose a locking mechanism, platform fallback, zeroization behavior, maximum secret size, or crash semantics. Calling it locked memory without a proven implementation risks a false security claim.
9. **Nice to have — editorial duplication weakens freeze confidence (§5.4 heading and §9.2 streaming bullet).** Duplicate text is not architectural, but in a contract freeze it suggests insufficient consistency review.

## Concrete fixes

1. Embed or normatively attach the complete RAK 1 JSON Schemas now: required/optional fields, enums, discriminators, ID/reference rules, extension policy, examples, and negative fixtures for every document named in §4.2.
2. Replace the lifecycle diagrams with transition tables for run, phase, check, attempt, operation, package, and capability records. For every transition specify command, source states, guard, transactional writes, emitted event, idempotent replay result, failure behavior, and the required control-result effect.
3. Freeze an OpenAPI contract for every public route and JSON Schema contracts for SSE events, `rakctl`, worker, and broker protocols; eliminate placeholder types and ellipses.
4. Provide an actual Drizzle/SQLite logical schema contract with column types, nullability/defaults, checks, unique/index definitions, FK actions, transaction boundaries, and rules preventing invalid current references before finalization.
5. Define the cross-agent conformance algorithm: identical frozen control-plan digest, mandatory domain/control IDs, evidence-sufficiency validators, artifact/profile assertions, divergence categories, and when disagreement forces independent review or blocks packaging.
6. Define provider scratch/outbox ownership and admission flow, including mount permissions, attempt binding, quotas, path validation, closure, and cleanup.
7. Add per-analyzer adapter contracts covering accepted native versions, exit interpretation, normalization/fingerprints, one-invocation-to-many-control mapping, reduced-coverage rules, and unsupported-version failures.
8. Anchor the ledger’s terminal digest in each checkpoint and final detached package metadata, and specify reconstruction/tail-truncation detection before claiming deletion detection.
9. Publish the exact manifest/checksum schemas and self-reference validation algorithm, plus golden/tamper fixtures consumable by an independent verifier.
10. Either specify and prove the locked-memory mechanism on supported platforms or narrow the claim to a tmpfs-backed, process-isolated ephemeral vault with explicit residual memory risk.

## Verdict

**Revise.** It clears the bar for architectural direction, threat-boundary quality, requirements coverage, and evidence-first thinking, but it misses the P1 contract-freeze bar: security-critical concepts are well described while the exact schemas, state semantics, database constraints, and equivalence algorithm are still future work.
