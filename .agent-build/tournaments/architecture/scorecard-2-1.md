# Architecture Contender 2 — Scorecard

## Scores

- **Requirements coverage — 8.4/10.** The phase graph, security baseline, runtime gate, decision model, review gates, and package inventory cover nearly every Must, but the required discovery topics and common decision criteria are only described rather than frozen as registries, and the public API has no way to retrieve discovery assertions or limitation details.
- **Hostile-repository isolation — 8.6/10.** Fixed no-network analyzer workers, a disposable mount-free VM, broker-only Docker access, restricted Compose compilation, and one-way evidence admission form a strong boundary. The score is capped because the broker/helper protocols lack complete typed results and reconciliation semantics, while provider `allowedKitCommands` are named without an authorization or transport contract.
- **Source immutability — 7.8/10.** The commit-versus-working-tree distinction, read-only copied snapshots, full commit identity, and before/after checks are correct in principle. However, `TargetSnapshot` at lines 233 and 313–315 never freezes the manifest/digest algorithm, Git object-format handling, submodule/LFS/symlink treatment, concurrent live-tree mutation behavior, or the exact failure rule when the before/after digests differ.
- **Cross-agent equivalence — 7.6/10.** Provider-neutral tasks, shared schemas, fresh independent reviews, and one acceptance harness correctly avoid demanding byte-identical prose. Section 6.1 defines only one example task, not the task-kind registry, per-task required inputs/outputs/domains, provider exit normalization, permission-failure mapping, or equivalence matrix needed to keep Codex and Claude implementations behaviorally aligned.
- **Evidence integrity — 6.6/10.** Two-phase admission, fencing, immutable attempts, semantic validation, content-addressed storage, derivations, and reopened-ZIP verification are strong ideas. The relational constraint at line 269 fatally conflates byte deduplication with evidence identity: `unique (run, digest, evidence type)` allows only one `activityId`, so identical bytes produced by two attempts cannot preserve both generation activities and fences.
- **Resumability — 7.3/10.** Input digests, attempt fencing, idempotency keys, supersession, recovery checks, and completion certificates are substantial. But retrying identical output collides with the evidence identity model, the helper cannot demonstrably verify the API's current fence without a synchronization/reconciliation contract, and the run transition diagram omits the `PAUSED → RUNNING` transition that the API explicitly performs at line 523.
- **Portability — 7.5/10.** Exact pins, multi-architecture images, native four-host release tests, explicit blocked behavior, and honest reversal conditions align well with the research. Lima/rootless Docker, Claude, ARM64 browser/ZAP support, and `better-sqlite3` remain unproved release blockers, and host-helper installation, signing, protocol compatibility, upgrade, and rollback are not specified.
- **Build-lane contracts — 6.4/10.** The ownership map, HTTP views, relational entities, provider example, event format, sequencing, and fixtures provide useful structure. Yet sections 6.2–6.4 give prose field lists or command names rather than strict request/result/error schemas, the product-intake schema lacks stable topic IDs, and several public read paths are absent; backend, host, runtime, adapter, and UI lanes would still have to invent shared behavior.
- **Operability — 7.5/10.** Resource budgets, metrics, structured logs, cancellation, emergency stop, backups, crash tests, scoped approvals, and static-only continuation are practical. Operator recovery remains ambiguous for helper/protocol mismatch, stale HMAC replay state, snapshot-integrity failure, and review/package correction, while mandatory human gates have no reviewer authorization model beyond self-declared names and roles.
- **Simplicity — 6.1/10.** A single API writer, REST plus SSE, fixed workers, and static-only fallback are sensible choices. Still, the MVP commits to fourteen phases, numerous canonical schemas, two provider adapters, many analyzer services, a host helper, HMAC mailbox, Lima lifecycle, custom Compose compiler, VM broker, independent model reviews, two human gates, and optional encryption before the critical contracts are complete; the spec does not identify a smaller releasable static core.

## Overall

**7.4/10.** This is an impressively serious architecture with strong safety instincts, but it does not meet the P1 contract-freeze bar. Its canonical evidence model cannot faithfully represent repeated production of identical bytes, and multiple security-critical cross-process interfaces remain descriptive rather than implementation-ready.

## Strongest objection

**Must-fix: the evidence schema destroys attempt-level provenance whenever two activities produce identical content.** The central promise is that every retry has an immutable fenced attempt and admitted outputs (lines 177–195), while `evidence_entities` stores one `activityId` but enforces `unique (run, digest, evidence type)` (line 269). If attempt B emits the same normalized result or log bytes as attempt A, admission must either violate the uniqueness constraint, silently reuse A's evidence row and falsely attribute B's completion to A's activity/fence, or mutate the admitted row despite its immutability claim. The content-addressed filesystem may deduplicate bytes, but evidence occurrences and their `wasGeneratedBy` relationships may not be deduplicated. This breaks retry auditability, completion-certificate truth, independent reproduction, and the requirement that evidence provenance survive resume without drift.

## Other findings

1. **Must-fix — the most important internal contracts are not actually contracts.** Sections 6.2–6.4 specify analyzer fields in prose, list helper/broker operations, and describe policy, but define no strict request/result/error schemas, status-to-error mapping, size/framing limits, protocol negotiation, cancellation acknowledgements, or restart reconciliation. `BROKER_COMMAND {vmId, brokerRequest}` simply nests the entire undefined privileged protocol. Downstream lanes must invent security-critical behavior the PLAN says P1 must freeze.
2. **Must-fix — receipt authenticity and admission authority are contradictory.** Admission step 1 says the expected digest comes from a “signed receipt” (line 319), but the provider receipt at lines 660–675 has no signature/MAC and the analyzer mailbox at lines 681–687 defines none. Only the host-helper mailbox has HMAC. The spec therefore does not say which producer claims are authenticated, which are merely untrusted evidence, or how admission binds a receipt to a command, attempt, fence, and actual producer identity.
3. **Must-fix — product discovery is not an implementation-ready schema or API.** Lines 557–570 show one assertion example and say “all required topics” must be present, but never enumerate stable topic IDs, multiplicity, speaker semantics, unknown-impact rules, or conflict representation. `RunDetail` omits discovery, and there is no assertion read endpoint, so the UI cannot reliably review the captured business context that AC-1 makes foundational.
4. **Must-fix — lifecycle definitions disagree.** The canonical diagram at lines 121–133 does not include `PAUSED → RUNNING`, while the public resume endpoint performs exactly `PAUSED|RECOVERABLE_FAILURE → RUNNING` at line 523. More broadly, the relationship between a phase `RETRYABLE_FAILURE` and run `RECOVERABLE_FAILURE` is not stated, so workflow, API, and UI implementations can expose different legal actions.
5. **Must-fix — immutable snapshot identity is under-specified.** The snapshot schema summary and path allocation name tree/file-manifest digests but do not define canonical traversal, filename-byte handling, mode bits, symlinks, submodules, Git LFS, sparse checkouts, ignored/untracked files, object format, or the consequence of a source changing during capture. Two valid implementations can assign different identities to the same local source or package a snapshot after a failed integrity comparison.
6. **Must-fix — the public API is not complete enough for the promised UI.** There is no limitations endpoint despite `limitation.updated` events and limitation IDs, no discovery/assertion read contract, no approval/review listing, and no declared safe preview contract. `AttemptView.state` is merely `string` (line 420), `event_cursor_expired` is used at line 634 but absent from the stable error-code registry at line 358, and most endpoint response envelopes are informal. This will force frontend/backend contract churn.
7. **Should-fix — provider equivalence is schema-shaped but behaviorally open.** The task example does not enumerate `taskKind`, define the protocol behind `evidence.lookup`/`coverage.lookup`, constrain the minimum evidence bundle, classify CLI exits/timeouts/truncation, or require per-domain limitation output. Both adapters can pass JSON validation while assessing materially different scope.
8. **Should-fix — helper fencing and replay prevention lack durable state semantics.** Line 691 requires rejection of replays and invalid fences, and line 703 says the helper refuses an inactive fence, but the helper has no database access and no contract for durable nonce state, active-fence updates, API restart, or lost mailbox responses. A crash can make a legitimate command permanently ambiguous or allow helper/API views of the current fence to diverge.
9. **Should-fix — review identity is not independently trustworthy.** Human review accepts a free-form `{displayName, role}` (lines 604–620) and stores a reviewer identity, but the single local session has no reviewer authentication or role authorization. The package can therefore present “technical-human” and “lay-human” approval records without proving separation from the operator who ran the assessment.
10. **Nice-to-have — operational backup locations conflict.** The run tree lists `internal/db-backups/` at line 303, while line 290 says verified backups remain under `generated/.control/` and are excluded from every package. Pick one normative location and recovery policy so backup discovery and package exclusion cannot diverge.

## Concrete fixes

1. Split physical content from evidentiary occurrence: create a content-object table keyed by digest and an immutable evidence-entity/production table keyed by evidence ID with activity, attempt, fence, receipt, and validation data. Permit many evidence entities to reference one content object, and make completion certificates reference the occurrence IDs.
2. Publish strict versioned schemas and conformance fixtures for analyzer, provider-command, helper, and broker request/result/error envelopes. Include protocol negotiation, authentication, idempotency, progress, cancel/reconcile, timeout, output limits, typed failures, and every command payload.
3. Define receipt trust explicitly per producer. Bind receipt MAC/signature or trusted-channel attestation to command ID, attempt, fence, producer identity, content digest, size, schema, and timestamp; treat unauthenticated producer statements as untrusted input rather than calling them signed.
4. Freeze a discovery-topic registry and full assertion contract, then add read/write API endpoints for assertions, limitations, approvals, and reviews. Define stable IDs, multiplicity, unknowns, conflicts, confidence/coverage effects, and exact response schemas.
5. Replace the run diagram and phase prose with one machine-readable transition table shared by workflow, API, and generated UI types. Include source state, command, guards, side effects, destination, run/phase coupling, failure class, and recovery action.
6. Specify the snapshot algorithm completely, including Git SHA-1/SHA-256 identity, canonical file manifest bytes, path encoding/collision policy, mode/symlink/submodule/LFS behavior, dirty/ignored/untracked selection, concurrent mutation detection, and fail-closed rules for before/after mismatch.
7. Add a provider task registry mapping every task kind to exact input/output schemas, mandatory domains/artifacts, allowed lookup capabilities, exit/error normalization, truncation behavior, and cross-provider acceptance assertions.
8. Define durable helper replay/fence synchronization and host-helper lifecycle: key creation/rotation, nonce persistence, active-fence reconciliation, signed binary distribution, version negotiation, upgrade/rollback, and restart recovery.
9. Either authenticate distinct reviewer principals or label the records as unauthenticated local attestations and require an external signed review artifact for release-grade independence.
10. Explicitly separate a releasable static-assessment core from the additive dynamic-runtime subsystem, while retaining honest `blocked` runtime coverage, so the team can validate contracts before carrying the full VM stack.

## Verdict

**Revise.** The contender clears the bar for architectural direction, hostile-runtime isolation, and serious failure thinking, but misses the P1 freeze bar for correctness and contracts. Repair the evidence occurrence model and fully specify the analyzer/helper/broker/provider and discovery/API seams before parallel implementation begins.
