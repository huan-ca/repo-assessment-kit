## Scores

- **Requirements coverage — 8.4/10.** §§3–9 trace nearly every Must to a component, state, gate, or deliverable, but the brief’s required discovery topics and the shared assessment-domain/control/artifact matrices are not actually enumerated in the supposedly frozen contracts; §10 instead defers freezing them to Milestone 0.
- **Hostile-repository isolation — 8.2/10.** The fixed no-network workers (§6.2), VM broker policy (§6.4), and quarantine/admission boundary (§4.3) are strong, but the context diagram omits the `Snapshot service` and its SSH/network boundary entirely, and provider task bundles expose an undefined filesystem/command channel.
- **Source immutability — 8.0/10.** The contender distinguishes commit and dirty-working-tree identities, copies snapshots, and records before/after digests (§§2, 4.1), but never freezes the snapshot algorithm for symlinks, submodules, Git LFS, file modes, concurrent local-tree mutation, or acquisition failure; implementers still decide what bytes the identity covers.
- **Cross-agent equivalence — 7.4/10.** A provider-neutral task, common schemas, shared validators, and a single acceptance harness are the right mechanism (§§6.1, 9), but equivalence cannot be mechanically judged without the exact required domain/control/artifact matrix, and the provider IPC plus `allowedKitCommands` semantics are unspecified.
- **Evidence integrity — 8.5/10.** Fenced attempts, content-addressed admission, semantic validation, one-way staging, redaction, and post-open ZIP verification are unusually rigorous (§§3.2, 4.3, 7–8); however, admission relies on an undefined “signed receipt,” while the worker and provider receipts shown in §6 have no signature/authentication contract.
- **Resumability — 7.3/10.** Immutable attempts, input/completion digests, leases, idempotency, backup verification, and external-command reconciliation are concrete (§§3–4), but the run transition contract contradicts itself: §3.1 omits both `WAITING_OPERATOR → RUNNING` and `PAUSED → RUNNING`, while §5 exposes operator resolution and resume actions that require those transitions.
- **Portability — 6.8/10.** The spec correctly pins the stack and preserves the four-native-host gate (§§9–10), but Lima/rootless Docker, `better-sqlite3`, Claude Code, ARM64 Chromium/ZAP, and macOS x86-64 availability all remain reversal conditions, and no component owns host-helper installation, version compatibility, or upgrades on the physical host.
- **Build-lane contracts — 5.4/10.** The API and internal DTO examples are helpful, but §1.2 creates `apps/provider-*`, `apps/analyzer-*`, `apps/host-helper`, `apps/runtime-broker`, `packages/db`, and `packages/reports`, while PLAN P5 owns none of those app paths and instead names `packages/persistence`, `packages/agent-adapters`, and `packages/reporting`; essential code is therefore orphaned or multiply owned before parallel implementation begins.
- **Operability — 6.4/10.** SSE replay, structured failures, recovery, cancellation, and safe blocked-runtime behavior are solid, but every assessment is forced through two model reviews plus technical and lay human review phases (§3.1), conflating release validation with routine run completion, and there is no retention/GC, disk-capacity preflight, helper repair, or quarantine cleanup policy.
- **Simplicity — 5.3/10.** Contract-first state and a single SQLite writer are sensible, but the MVP commits to 14 phases, four mandatory reviews, numerous app processes, multiple mailboxes, a VM broker, eight scanner families, extensive projections, and optional age wrapping before the major feasibility gates have passed; several of these are release-process concerns embedded in the per-run product.

## Overall

**7.4/10.** The architecture is rigorous about integrity and hostile execution, but it misses the P1 bar for a simple, parallel-buildable freeze because the code ownership map conflicts directly with the approved plan and several critical “frozen” contracts remain future Milestone 0 work.

## Strongest objection

The repository and ownership contract in §1.2 cannot be implemented under the approved PLAN. The contender introduces six essential app families—`provider-codex`, `provider-claude`, `analyzer-*`, `host-helper`, and `runtime-broker`—that are absent from P5’s owned output paths, while renaming PLAN-owned shared packages (`persistence` → `db`, `reporting` → `reports`) and splitting `agent-adapters` across apps/packages without assigning a single owner. P4 is allowed to scaffold boundaries, not implement these services; P5 may only edit its listed paths; P6 owns only `apps/web`. This is the highest-leverage rework risk because the first implementation decision would require either violating the frozen plan or silently changing the architecture, and multiple parallel lanes could reasonably claim the same adapter/runtime/contracts work.

## Other findings

1. **Must-fix — the trusted acquisition boundary is absent from the system diagram.** §2 defines a `Snapshot service`, but §1.1 shows no such process, SSH mount, acquisition network, intake workspace, or protocol. The trust rules merely say “SSH is intake-only.” Implementers must decide whether the API receives SSH keys/network access or whether another privileged helper exists, directly undermining the requirement to freeze every credential and process boundary.
2. **Must-fix — required cross-agent equivalence inputs are deferred.** §10 Milestone 0 says to “freeze `toolchain.lock.json`, `standards-lock.json`, workflow/control matrices,” but P1 itself is supposed to freeze these contracts. The schema catalog in §4.1 permits arbitrary `topic`, `kind`, domain, profile, and artifact strings, so two providers can validate structurally while omitting different discovery topics, assessment domains, or deliverables.
3. **Must-fix — the run lifecycle is internally inconsistent.** §3.1 calls its transition list canonical but lacks `WAITING_OPERATOR → RUNNING` after `POST /operator-inputs` and `PAUSED → RUNNING` after the resume endpoint in §5.2. `AllowedAction` can therefore advertise an action the workflow reducer is required to reject, forcing API, UI, and persistence lanes to invent precedence.
4. **Must-fix — helper fencing is asserted but not implementable from the protocol shown.** §6.3 says the host helper rejects a run/attempt/fence that “is not active,” yet the helper has no database access and no specified authenticated synchronization of current run state, fence increments, cancellation, or restart reconciliation. An HMAC proves the API authored a message; it does not tell the helper that a previously valid message is now stale.
5. **Must-fix — provider exchange and tool-call transport are incomplete.** §6.1 specifies request/result JSON but not how the API delivers it, which paths/volumes the adapter can read and write, how receipt authenticity is established, or how `allowedKitCommands` are invoked and authorized. That leaves both a security boundary and a backend/provider integration contract for P5 to invent.
6. **Should-fix — package/process boundaries contradict the trust prose.** §1.1 says “Only the API process opens SQLite and the final run tree,” while the diagram and §2 present evidence admission, reporter, redactor, and packager as separate components that necessarily read or write the run tree. The spec must say whether these are in-process libraries or separate workers and give the actual mount/access matrix.
7. **Should-fix — human release review is embedded in every run.** The research synthesis calls technical and lay human review a production-release gate, whereas §§3.1 and 7.2 make both mandatory phases for every assessment to reach `COMPLETED`. This prevents unattended completion, adds routine operator coordination, and exceeds what is needed to ensure generated content requires no manual core completion.
8. **Should-fix — append-only safety lacks storage lifecycle.** The defaults permit 10 GiB snapshots, 512 MiB per analyzer output, VM evidence, immutable superseded attempts, backups, quarantine, staging, ZIP, and optional encrypted copies (§§4, 8–9), but there is no free-space preflight, retention class, garbage-collection rule, interrupted-run cleanup, or operator-visible reclamation flow.
9. **Should-fix — source identity is not fully reproducible.** `TargetSnapshot` records useful digests (§4.1), but there is no canonical traversal/manifest algorithm, normalization policy, submodule/LFS behavior, or protection against a local tree changing during export. “Hash before/after” alone does not define whether a mid-copy race is retried, rejected, or admitted.
10. **Nice-to-have — defer optional encryption implementation.** §8 and Milestone 5 require an age workflow even though the research synthesis explicitly classifies age encryption as optional/future. Keeping the schema extension point while postponing UI, key handling, decrypt verification, and wrapper retention would reduce MVP surface without weakening the mandatory validated ZIP.

## Concrete fixes

1. Reconcile §1.2 with PLAN P4/P5/P6 using one authoritative ownership table: exact path, implementing phase/lane, dependency direction, and sole contract owner. Either rename the contender paths to the PLAN names or formally update the PLAN before freezing architecture.
2. Add the acquisition/snapshot process to the context diagram and access matrix. Freeze how SSH/local mounts are provisioned, which process can read them, its network class, intake workspace, sanitization, credential revocation, and evidence handoff.
3. Move the exact discovery-topic vocabulary, assessment domain/control matrix, required artifact matrix, `toolchain.lock.json`, and `standards-lock.json` schemas into P1. Include canonical positive/negative fixtures so Codex and Claude equivalence is mechanically testable.
4. Publish one exhaustive run-transition table with trigger, guard, side effects, and resulting allowed actions. Add the missing operator-resolution and paused-resume transitions and make the API/state reducer tests derive from it.
5. Define provider and helper transport end to end: process topology, exchange roots/mount modes, message authentication, fence-state synchronization, replay protection, restart reconciliation, tool-command authorization, and cancellation acknowledgements.
6. State explicitly which named components are in-process libraries versus isolated processes, then provide a resource/access matrix for SQLite, run tree, quarantine, provider homes, SSH, sandbox credentials, network classes, and HMAC material.
7. Separate product-run completion from product-release qualification. Keep independent security and decision review per assessment where required, but make the technical/lay human checks release-suite evidence or an explicit engagement policy rather than unconditional phases for every run.
8. Freeze the working-tree snapshot algorithm, including canonical path/mode/symlink hashing, submodule and LFS behavior, concurrent mutation detection, retry/fail semantics, file limits, and commit-hash-format handling.
9. Add disk preflight, quotas, interrupted-intake cleanup, quarantine expiry, safe GC for superseded attempts/content-addressed objects, backup retention, and an operator-visible cleanup/audit command.
10. Defer age wrapping until the mandatory static-only package completes through both provider paths and all critical portability gates pass, unless a confirmed customer requirement promotes encryption into MVP acceptance.

## Verdict

**revise.** It clears the bar for evidence integrity, resumability intent, and isolation direction, but misses the exhaustive P1 bar for simplicity and parallel buildability: ownership is incompatible with the approved plan, acquisition/provider/helper boundaries remain incomplete, and several contracts advertised as frozen are deferred to implementation.
