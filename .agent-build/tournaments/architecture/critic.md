# Architecture Critic Scorecard

## Scores

- **Requirements coverage — 9.2/10.** Sections 2, 7.2–7.3, 13, and 14 trace nearly every Must and AC to an owner and gate, including the seven claim labels, six control states, independent security review, all three modernization options, and static-only success when runtime is blocked; the remaining misses are contract-level rather than scope omissions.
- **Hostile-repository isolation — 8.0/10.** Sections 3.2–3.4, 9, 10.2, and 13.1 establish strong default-deny mounts, networks, Compose compilation, and no-execution static analysis, but the trusted handling of untrusted scanner/model text and the provider “task view” are not closed end to end.
- **Source immutability — 9.0/10.** Section 9 fixes the dirty-tree ambiguity with explicit `commit-only` versus approved `frozen-working-tree`, no-follow capture, atomic manifests/archives, and a completion-time live-source comparison; the exact source-digest algorithm and acquisition receipt schema remain undefined.
- **Cross-agent equivalence — 7.8/10.** Sections 7.4 and 17 correctly define outcome equivalence rather than byte/prose identity and require the same domain and acceptance harness, but `EquivalenceCertificate` certifies only one run and omits the common input/fixture, lock digests, workflow digest, artifact-matrix version, and counterpart identity needed to prove two paths were actually compared under equivalent conditions.
- **Evidence integrity — 8.2/10.** Sections 8.3, 11.3, and 14 correctly separate blob content identity from occurrence identity, fence admissions, retain provenance, and validate a reopened ZIP; safe handling stops short of specifying how target-derived strings and links are escaped in the shipped self-contained HTML reports.
- **Resumability — 8.0/10.** Sections 6 and 11 provide durable state machines, fenced attempts, leases, idempotency, transactional events, startup reconciliation, and backup recovery, but helper subcommand transitions and checkpoint capabilities are not represented in the normative DTOs.
- **Portability — 7.7/10.** The architecture honors Node 24, both Linux architectures, macOS/Linux hosts, multi-arch images, and the native four-host gate, while honestly retaining Lima, Chromium/ZAP, Claude, and `better-sqlite3` as release blockers; host-helper bootstrap/update/socket behavior on Docker Desktop hosts is still not specified enough for P4.
- **Build-lane contracts — 6.8/10.** Section 4 gives unusually clear ownership and dependency direction, but Sections 8, 10, and 12 call contracts normative while leaving `HostRequest.body`, `HostResponse.result`, `SourceSpec`, most API request/response objects, task-view construction, and several lifecycle results for downstream lanes to invent.
- **Operability — 7.8/10.** Sections 15–17 cover headroom, ENOSPC, health, audit metrics, recovery, and two-phase deletion well; retention is prose rather than a schedulable lifecycle, and there is no API/contract to restore or cancel a trash-window deletion or clean engagement homes and residual DB data.
- **Simplicity — 6.5/10.** The modular monolith, serialized SQLite writer, and absence of brokers/microservices are appropriate, but the 1,800-line spec introduces multiple partially overlapping profile/certificate/protocol layers whose missing schemas increase rather than reduce implementation ambiguity.

## Overall

**7.9/10.** This improves on the 7.7667 winner baseline and does not regress, but it misses the required 8.0 bar because its most security-sensitive lane boundaries are described in prose/pseudo-types rather than frozen, testable contracts.

## Strongest objection

The spec declares itself “implementation-ready” while its principal cross-lane protocols are not actually closed. In Section 10.1, the authenticated host boundary is typed only as `operation: HostOperation; body: object` and `result?: object`; the operation table refers to undefined types such as `SourceSpec`, contains shape shorthand such as `candidateRelPaths[]` and `expectedReceipts[]`, and never defines legal per-operation command-state transitions or typed rejection/result payloads. Section 10.1 nevertheless says “operation/body mismatch … fails closed,” which cannot be implemented independently by P4 and P5 without those schemas. The same defect appears in Section 12.2, where the “normative OpenAPI” table uses placeholders such as “claim inputs,” “recovery plan/retry IDs,” “technical/lay review,” and “optional encryption” instead of frozen request/response schemas. This directly misses PLAN P1’s done condition that no security-critical boundary or downstream contract be left for P5/P6 to invent, and it is the most likely source of incompatible helper, server, and UI implementations.

## Other findings

1. **Must-fix — customer HTML rendering remains an active-content boundary.** Section 5.2 safely makes raw target artifacts attachment-only and says previews use `textContent`, but Section 14 requires `index.html` and five self-contained HTML reports whose prose, finding titles, paths, links, and excerpts are derived from hostile repository/model/scanner content. Sections 8.8 and 14 specify neither contextual HTML escaping, URL-scheme filtering, CSS/attribute handling, static-report CSP, nor a no-script invariant. A malicious repository name or finding payload can therefore become executable or misleading content when the customer opens the delivered report, despite the otherwise strong UI preview boundary.
2. **Must-fix — the provider task-view boundary is asserted but not specified.** The credential table in Section 3.3 says Codex and Claude receive a “task view read-only,” while Section 8.5 gives only snapshot identity, an evidence allowlist, and five logical commands. It does not define how files are selected/projected, whether repository-owned `AGENTS.md`/`CLAUDE.md`/skills/config are excluded or treated as untrusted data, what path/size limits apply, where the writable proposal outbox lives, or how `codex exec --sandbox workspace-write` is prevented from writing the snapshot. This leaves a prompt-injection and source-mutation boundary to the provider-adapter implementer.
3. **Must-fix — the equivalence certificate proves conformance, not equivalence.** Section 7.4’s certificate contains one `runId` and one `provider` but no `equivalenceCaseId`, counterpart run, target/manifest digest, discovery-input digest, policy/standards/tool locks, workflow graph digest, required-artifact matrix version, or validator build digest. Two unrelated, differently configured runs can each truthfully emit the certificate and be called equivalent. The external harness may intend to pair them, but the durable evidence contract does not preserve that proof.
4. **Must-fix — lifecycle capability and secret DTOs contradict their prose.** Section 10.1 permits `analyzer.pause` “only when manifest supports checkpoint,” but `AnalyzerManifest` in Section 8.6 has no checkpoint/pause/resume field. Section 10.3 makes `SecretHandle.approvalId` optional while `VmSecretEnvelope.approvalId` is mandatory, with no defined approval kind for an offline, explicitly supplied sandbox credential. These are small fields with large safety consequences: adapters will otherwise invent incompatible fallback behavior.
5. **Must-fix — untrusted normalization/rendering execution is not placed.** Section 3.2 correctly treats “scanner parsers/output” as untrusted, but Sections 5 and 8.6 call normalizers trusted and do not say whether native-output parsing runs inside the disposable analyzer container, a separate parser sandbox, or the trusted server/admission process. A memory-corruption or parser-bomb defect in a normalizer could cross directly into the TCB. The spec needs a single owner, resource limits, and a receipt boundary for normalized proposals.
6. **Must-fix — retention/deletion is not a complete durable lifecycle.** Section 15.2 states expiry periods, but Section 15.3 only defines operator-requested deletion. There is no retention sweep state machine, lease/idempotency behavior, restore/cancel operation during the promised 24-hour recovery window, purge receipt, treatment of SQLite rows/backups, or engagement-home cleanup API. `requestRunDeletion` is the only frozen HTTP operation. Consequently “7 days” and “30 days” are not implementable guarantees, trash can accumulate outside headroom accounting, and deleted customer data may remain indefinitely in database backups/provider homes.
7. **Should-fix — source integrity needs one canonical digest recipe.** Section 9.2 uses “source digest,” “tracked/untracked manifest,” “status/manifest repeated,” and later “live source before/after digest” without defining whether Git metadata, ignored files, file metadata, symlink targets, or unreadable/special files participate. `TargetSnapshot` stores only the digest values. Different helper implementations could disagree or fail to detect the same mutation while all satisfying the prose.
8. **Should-fix — package validation certificates are narrative, not contracts.** Section 14.2 relies on nine stage certificates, yet Section 8 defines only `ReportDescriptor` and `PackageManifest`; there is no `PackageStageCertificate` DTO, transition table, validator identity/version, input/output digests, or failure/retry semantics. This weakens resumable packaging and independent audit of the most important release boundary.
9. **Nice-to-have — reduce overlapping identifiers and profiles.** `schemaVersion`, `$id` validation context, `rak-contract`, `rak-workflow`, `rak-export-profile`, tool locks, standards locks, template versions, policy IDs, and acceptance-harness versions are all legitimate, but the spec lacks one immutable `RunProfileSnapshot` binding them. Without that aggregate, every DTO and digest recipe must independently decide which versions matter, increasing accidental omission.

## Concrete fixes

1. Publish strict Draft 2020-12 schemas and discriminated TypeScript unions for every host-helper request, response, status, receipt, rejection, and operation-specific result. Add command-state transition tables, cancel/pause races, idempotent replay semantics, and golden request/response fixtures shared by P4 and P5.
2. Replace every prose placeholder in Section 12.2 with named request and response DTOs, freeze the OpenAPI document in `packages/contracts`, and provide golden API/SSE fixtures consumable by both server and web lanes.
3. Add a `TaskViewManifest` and construction protocol: allowlisted paths/evidence, manifest digest, byte/file limits, read-only snapshot mount, separate writable outbox, explicit treatment of repository instruction/config files, and provider-adapter canary tests proving no snapshot write or undeclared read.
4. Define a safe-report renderer contract: contextual escaping for all target/model/tool strings, no raw HTML or script, allowlisted `https`/internal evidence links only, generated CSP/meta policy suitable for file and HTTP viewing, sanitized anchors/IDs, and adversarial HTML/URL/CSS fixtures. Treat generated HTML as a derived evidence occurrence.
5. Extend equivalence evidence with an `EquivalenceCase` binding both run IDs/providers to the same snapshot, discovery inputs, profiles, locks, workflow/domain/artifact matrices, validator/harness build, and expected capability tier; have the engine issue the pair result only after both individual conformance reports pass.
6. Add `supportsPause`, `supportsResume`, checkpoint schema/version, and cancellation guarantees to `AnalyzerManifest`; reconcile optional versus mandatory credential approvals with a typed sandbox-secret authorization object.
7. Place native-output normalizers and report rendering in explicit processes. Prefer resource-bounded parser/renderer workers that emit fenced receipts to quarantine; if they remain in-process, specify parser limits and justify their inclusion in the TCB.
8. Add retention and deletion state machines plus APIs for deletion status, recovery/cancel during the trash window, engagement-home cleanup, and verified purge. Specify database-row, backup, CAS, provider-home, trash-quota, crash-recovery, and audit-tombstone behavior for each deletion scope.
9. Define one canonical local-source digest algorithm and one `PackageStageCertificate` schema. Add a `RunProfileSnapshot` digest binding every contract, workflow, export, tool, standards, policy, template, and harness version used by attempts, reviews, and packages.

## Verdict

**revise.** The synthesis clears the winner baseline and is strong on requirements, immutable acquisition, evidence occurrence identity, resumability concepts, and storage safety, but it misses the 8.0 acceptance bar because the host/API/task-view boundaries and safe report rendering are not frozen to implementation-ready, testable contracts. One focused contract-closure revision should be sufficient; rejection is not warranted.
