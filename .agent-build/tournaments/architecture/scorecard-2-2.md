## Scores

- **Requirements coverage — 8.0/10.** The contender covers the brief's major flows, six-state coverage accounting, security independence, decision support, dual-provider operation, and validated packaging. However, §5 says only that “all required topics” must be present without freezing the product-intake topic enum, while §§2 and 8 name reports rather than defining the report/export schemas and mandatory content contract P1 is expressly required to freeze.
- **Hostile-repository isolation — 8.0/10.** §6.2 gives analyzers strong fixed-command, no-network, non-root isolation and §6.4 places hostile Compose behind a disposable VM and restrictive broker. The earlier acquisition boundary remains hand-wavy: §2's Snapshot service “resolves commit” and “exports” hostile Git/local input while potentially using SSH, but no clean Git environment, fixed argv, hooks/filters/LFS/submodule policy, protocol allowlist, archive/path limits, or acquisition-process containment is specified.
- **Source immutability — 7.0/10.** The commit-versus-working-tree distinction, content-addressed snapshot, before/after digests, and prohibition on scanning the live tree are correct. The actual capture algorithm is absent: there is no atomicity or retry rule for a concurrently changing local tree, no proof that exported bytes correspond to the resolved Git object, and no behavior for symlinks, hardlinks, alternates, submodules, LFS, filters, or a hostile local `.git/config`.
- **Cross-agent equivalence — 9.0/10.** §§6.1, 7, 9, and Milestone 3 correctly make schemas, workflow, control matrix, deterministic gates, and acceptance fixtures provider-neutral rather than requiring identical prose. The remaining weakness is that “narrow allow rules” for Claude and the enforcement of `allowedKitCommands` are not frozen, so the two adapters can still diverge materially in tool and filesystem authority.
- **Evidence integrity — 8.0/10.** §§4.3, 7, and 8 provide fenced admission, immutable attempts, content-addressing, semantic validation, redaction, and post-ZIP verification. But §4.2's uniqueness constraint `unique (run, digest, evidence type)` combined with a single `activityId` collapses identical bytes produced by distinct attempts or independent reviewers, losing occurrence-level provenance; “material” is also never defined, so completeness validation cannot detect an omitted material finding.
- **Resumability — 8.0/10.** §3 has strong CAS transitions, digested inputs, leases, fences, immutable attempts, downstream invalidation, and startup reconciliation. It does not define a durable helper/broker-side effect ledger, stable external resource naming, or the transaction boundary between creating a VM/container and persisting the result, leaving crash windows where the control DB and privileged external state disagree.
- **Portability — 7.0/10.** The architecture is honest about static-only degradation, pins versions/digests, and treats the four native hosts as release gates. Lima/rootless Docker on all four hosts, Claude Code, `better-sqlite3` on Node 24, Linux ARM64 Chromium, and a multi-arch passive scanner remain unproved critical-path assumptions, so portability is a plan to validate rather than a frozen demonstrated contract.
- **Build-lane contracts — 8.0/10.** The repository ownership, public REST/SSE surface, state machines, and provider task are concrete enough to support parallel UI/backend work. Backend/runtime/security lanes would still have to invent exact broker command payloads and results, helper reconciliation records, analyzer receipt authentication, credential-handle lifecycle, product-intake enums, report schemas, and storage-retention behavior.
- **Operability — 6.5/10.** §9 supplies useful latency targets, resource budgets, structured logs, metrics, and crash tests. It omits the most basic local-appliance capacity contract: there is no run-level disk quota, free-space reservation, inode/file-count accounting for generated data, staging/ZIP amplification bound, retention default, deletion graph, or defined ENOSPC behavior across SQLite WAL/backups, quarantine, immutable attempts, VM disks, staging, plain ZIPs, and encrypted wrappers.
- **Simplicity — 5.5/10.** The threat model justifies a VM boundary and deterministic evidence pipeline, but the MVP contains fourteen phases, four execution protocols, many worker images, two provider adapters, independent model reviews, two mandatory human reviews, extensive append-only history, multiple projections, optional hosted-service approvals, and optional encryption. Deferring hosted dispatch and age would reduce surface while the five acknowledged platform blockers are retired.

## Overall

**7.7/10.** The contender is rigorous on state, evidence admission, runtime isolation, and provider-neutral validation, but it falls below the P1 ship threshold because several operational and security-critical contracts remain assertions rather than implementable invariants. Most notably, the architecture has no capacity or retention model for the large immutable artifact graph on which its availability and privacy claims depend.

## Strongest objection

**Must-fix: §§4.3, 8, 9, and 12 define large append-only evidence, retries, backups, staging copies, a mandatory plain ZIP, optional encrypted copies, and VM disks, yet never define storage admission, headroom, retention, or disk-full recovery.** The defaults alone permit a 10 GiB/1,000,000-file snapshot, up to 512 MiB per analyzer output, repeated immutable attempts, a 40 GiB VM, staging duplication, and ZIP/wrapper duplication. “Unreferenced objects are quarantined for later deletion” is not a lifecycle contract. ENOSPC can occur between DB intent insertion, content fsync, rename, DB admission, backup, or ZIP finalization, exactly where the spec promises crash-safe recovery. It can also retain discovered secrets indefinitely in quarantine, old attempts, backups, and plain ZIPs. Fixing this after implementation would cut across schemas, state transitions, admission, UI, packaging, cleanup, and tests.

## Other findings

1. **Must-fix — hostile source acquisition is not isolated or specified (§2 Snapshot service, §4.1 `target-snapshot`, §5 `CreateRun`).** The first component to touch hostile Git metadata and SSH material has no process boundary or safe Git contract. Later read-only snapshots do not protect against hooks, filters, submodule/LFS behavior, malicious local config, object/path bombs, or concurrent source mutation during capture.
2. **Must-fix — the evidence relational model loses provenance (§4.2 `evidence_entities`).** `unique (run, digest, evidence type)` and one `activityId` prevent representing the same bytes as independently produced by two attempts/tools/reviewers. Content blobs should deduplicate by digest, while evidence occurrences/entities remain independently identified and associated with their generating activities.
3. **Must-fix — privileged-effect idempotency stops at the API boundary (§3.3, §6.3–6.4).** A deterministic `commandId`, HMAC request, and fence do not prove exactly-once external effects. The helper/broker need durable command/effect journals and reconciliation rules for crashes after VM creation, build/start, evidence export, or cleanup but before response persistence.
4. **Must-fix — provider authority is described, not enforced (§1.1, §6.1).** `allowedKitCommands` appears in the task envelope, but the spec does not define how Codex/Claude are prevented from invoking other tools, which snapshot/evidence paths their CLI sandbox can read, or how provider inference egress is restricted separately from arbitrary network access. “Narrow allow rules” is not an interoperable contract.
5. **Must-fix — P1 does not actually freeze all required schemas (§4.1, §§5–6, §8).** Many contracts are field summaries or prose, and the broker result/error taxonomy, report sections/filenames, discovery topics, limitation/materiality rules, redaction result, and export profile inventory remain undefined. Downstream lanes would make incompatible choices in exactly the shared surfaces P1 is meant to freeze.
6. **Should-fix — redaction is overclaimed (§4.3 admission, §7.1 gate 8, §8 step 3).** “Secret/host-path/placeholder scan every format” does not define supported media, transformations, screenshot OCR/metadata handling, archive recursion, binary policy, false-negative treatment, or whether raw secret-bearing evidence is retained or withheld. Seeded-canary tests are necessary but do not make arbitrary content safe.
7. **Should-fix — performance targets do not form a capacity model (§9).** API p95 at selected row counts says little about end-to-end assessment duration, packaging a near-limit run, database size, event replay cost, concurrent analyzer I/O, or a four-core host that is also assigned a four-vCPU VM. Define representative workloads, storage ceilings, throughput/time SLOs, and degradation behavior.
8. **Should-fix — SSE retention and backpressure are incomplete (§5.3, §9).** The server promises replay, supports `event_cursor_expired`, and benchmarks one million events, but never states event retention/compaction, slow-consumer behavior, buffer limits, or when a cursor expires. A stalled browser can otherwise become a memory or resource leak.
9. **Should-fix — encryption increases rather than resolves data-at-rest exposure (§8 step 9, ADR-011).** The mandatory plain ZIP remains after producing an age wrapper, but no default retention or deletion behavior exists for the plain ZIP, decrypted scratch, passphrase/key channel, or failed wrapper attempts. The spec acknowledges operator policy without defining a safe product default.
10. **Nice-to-have — defer non-Must surfaces (ADR-008, §8 step 9).** Optional hosted-service machinery and age encryption add approval, credential, network, redaction, packaging, and recovery paths before the core native-runtime and provider assumptions are proven.

## Concrete fixes

1. Add a storage model with per-storage-class accounting and defaults for control DB/WAL, snapshots, quarantine, admitted evidence, attempts, backups, VM disks, staging, ZIP, wrapper, caches, and provider homes. Define preflight free-space and inode reservations, worst-case packaging amplification, hard/soft quotas, backpressure, operator overrides, and explicit `INSUFFICIENT_CAPACITY`/ENOSPC transitions.
2. Add an inventory-driven retention and purge state machine. Specify what can be deleted at each run state, dependency/reference checks, failed-attempt and quarantine TTLs, plain-ZIP behavior after encryption, backup retention, VM/cache cleanup, deletion audit evidence, and where secure erasure cannot be guaranteed.
3. Crash-test every filesystem/DB boundary under injected ENOSPC and I/O failure: intent insert, quarantine read, content-addressed write, fsync, rename, admission commit, backup, staging freeze, ZIP write/reopen, wrapper, and cleanup. Recovery must deterministically finalize, retry, or roll back without admitting partial bytes.
4. Define a contained `SourceAcquisitionCommand/Result` protocol with fixed Git argv and clean environment; disable or explicitly handle hooks, filters, fsmonitor, LFS, submodules, alternates, redirects, and local config; enforce URL/SSH/path/resource policy; and specify a race-safe commit export and stable working-tree capture algorithm.
5. Split content storage from evidence occurrence/provenance: deduplicate immutable blobs by digest, but give every produced evidence entity/occurrence its own ID, attempt/activity association, declared role, validation state, and derivation edges.
6. Give the host helper and broker durable, fsynced effect records keyed by command ID, stable resource names, typed result/error schemas, duplicate semantics, compensation states, and authoritative reconciliation rules. Add crash injection around every external side effect.
7. Freeze exact provider sandbox manifests for each CLI: readable/writable roots, tool allowlist enforcement, process/network policy, session/credential access, cancellation, output/log limits, and equivalence failure mappings. Test hostile prompt fixtures against credential and arbitrary-tool canaries.
8. Publish the actual versioned product-intake, limitation/materiality, broker, redaction, report, and export-profile schemas before parallel work. Enumerate required discovery topics, decision criteria, report sections, filenames, and package artifact classes so omission is mechanically detectable.
9. Replace format-agnostic redaction claims with a media policy: supported structured/text/image/archive transformations, metadata stripping, screenshot handling, binary withholding, recursion and size limits, raw-secret retention policy, and a fail-closed outcome for unscannable content.
10. Define SSE retention, compaction, slow-client buffering, disconnect thresholds, replay limits, and client resynchronization tests; add representative end-to-end duration, disk, memory, and packaging benchmarks alongside API latency.

## Verdict

**revise.** The contender clears the bar for architectural understanding and has strong foundations for deterministic workflow, evidence integrity, runtime isolation, and dual-agent equivalence. It misses the ship bar because storage exhaustion/retention, hostile acquisition, provenance deduplication, and privileged-effect recovery are not frozen despite directly underpinning the stated security and availability guarantees.
