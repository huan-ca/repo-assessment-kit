## Scores

- **Requirements coverage — 8.1/10.** The requirements map, complete discovery vocabulary, six-state coverage, three-option decision document, security report, and package inventory cover nearly every Must; however, the exact modernization criteria are not frozen, the general baseline for non-web targets is unclear, and run-scoped state is placed under `state/` despite the brief's all-output-under-`generated/<project>-<commit>-<timestamp>/` rule.
- **Hostile-repository isolation — 7.3/10.** The mount-free VM, no-network scanners, compiled Compose intent, no host socket, and quarantined evidence flow are strong, but §§2 and 3.6 cannot enforce per-attempt mounts with long-lived predeclared workers, while §§3.8–3.9 never freeze the accepted/rejected Compose matrix, egress proxy, DNS controls, or one-use secret-delivery channel.
- **Source immutability — 7.5/10.** §3.4 correctly exports a commit or separately identified frozen working-tree snapshot and rejects special/path-escaping files, but it verifies the exported snapshot rather than specifying the required before/after integrity check of the supplied live local repository; `sourceHandle` registration and the claimed intake-only SSH boundary also lack enforceable process contracts.
- **Cross-agent equivalence — 6.4/10.** Separate provider images/homes and one acceptance harness are the right policy, but §§3.7 and 7.5 define only agent-to-control-plane submissions and omit the provider job, admitted-evidence/finding reads, context batching, lifecycle, termination, and resume contracts needed for either agent to synthesize or independently review a run.
- **Evidence integrity — 8.9/10.** §§3.5, 4, and 8 provide an excellent quarantine-to-CAS-to-ledger-to-redacted-stage flow, strict provenance, semantic gates, crash reconciliation, and reopened-ZIP verification; the score is capped because critical provider/reviewer inputs are not defined and the self-referential manifest exceptions need normative schema fixtures.
- **Resumability — 8.3/10.** Immutable attempts, leases, idempotency, checkpoint reconciliation, secret re-entry, explicit retries, and orphan reporting are unusually complete; remaining ambiguity includes provider-session recovery, pause with still-running work, skipped-check-to-coverage mapping, and VM identity being created before any run ID exists.
- **Portability — 6.2/10.** The spec records the four-native-host, SQLite, Claude, browser, ZAP, and Lima gates honestly, but its physical-host-loopback broker route is not shown to be reachable from the outer container, its API bind rule conflicts with a separate web container, and all architecture-sensitive paths remain unproved.
- **Build-lane contracts — 5.9/10.** HTTP, SSE, worker, broker, and data-model detail is extensive, but the provider input/lifecycle seam, worker filesystem transfer, source registration, runtime policy, egress mediation, and secret transfer remain for implementers to invent; §2 also renames PLAN-owned packages and §10 starts backend/frontend work alongside DevOps despite P4's required scaffold/lockfile ownership.
- **Operability — 7.4/10.** Health, failure envelopes, cancellation, emergency VM stop, backup, recovery, resource ceilings, and observability are concrete; engagement/provider-home lifecycle, disk/backup retention, run deletion, host-helper installation/upgrades, source-handle registration, and safe cleanup of non-VM state are absent.
- **Simplicity — 5.1/10.** A single Fastify writer, SSE, fixed commands, and a static-valid-when-runtime-blocked rule are sound simplifications, but the MVP still combines roughly thirty tables, CAS plus hash-chain plus checkpoints plus SQLite, long-lived tool services, two provider images, a host launcher, Lima, a custom broker, a Compose compiler, multiple projections, and optional encryption before the critical seams have feasibility proofs.

## Overall

**7.1/10.** The contender is strongest on evidence integrity and failure accounting, but under a simplicity/buildability lens it is not architecture-frozen: several core flows cannot be implemented from the stated interfaces, and the most security-sensitive runtime behavior is still an assertion rather than a contract.

## Strongest objection

**Must-fix: the provider boundary cannot perform the core assessment it is supposed to own.** Section 3.7 says the model “can invoke only `rakctl`,” and §7.5's only read commands are `run.describe`, `plan.describe`, and `discovery.read`; there is no admitted-evidence, finding, control, coverage, limitation, claim-detail, or decision-draft read operation. Yet §3.10 requires a separate agent reviewer to receive admitted evidence and the draft conclusion, and §§1.3/4.2 require evidence-based architecture reasoning, feature mapping, security conclusions, and decision synthesis. No server-to-provider job/input envelope, bounded evidence bundle, pagination/context strategy, sensitivity policy, session lifecycle, or normalized provider outcome is specified. P5 therefore must invent the central cross-agent contract, and Codex and Claude can diverge while each appears schema-valid. This blocks even the static-only valid-package path, so it is more fundamental than the unresolved dynamic-runtime work.

## Other findings

1. **Must-fix — fixed workers cannot satisfy their stated filesystem isolation.** Section 2 says static workers are predeclared services so the server needs no container API; §3.6 simultaneously says each worker mounts only the selected snapshot read-only and only its current attempt outbox writable. Long-lived Compose services cannot acquire a new per-attempt bind mount. Mounting common snapshot/quarantine parents would let a hostile or compromised worker read other runs and write other outboxes, contradicting the trust boundary; copying objects over the Unix socket would require a different protocol and storage design than §7.6.
2. **Must-fix — the hostile-runtime policy is named, not frozen.** Sections 3.8–3.9 promise pre-parsing, rejection, compilation, scoped build egress, offline runtime, endpoint exceptions, and safe probes, but provide no normative accepted/rejected Compose/Dockerfile feature matrix, transformation rules, DNS/IP enforcement, redirect policy, proxy component, image/build provenance rules, or HTTP/browser action safety-class table. The research and PLAN explicitly require these security-critical decisions in P1, not in P5.
3. **Must-fix — the runtime network and credential paths are incomplete.** Section 7.7 passes a “scoped egress object” and says credential handles are resolved through a “one-use channel,” yet no egress proxy or secret-broker component, protocol, authentication, revocation, crash cleanup, or evidence format exists. The VM is supposed to have an internal runtime network, making approved external endpoint exceptions impossible without an unmodeled gateway.
4. **Must-fix — the deployment routing is internally inconsistent.** Section 3.9 exposes the broker through a physical-host loopback forward while the caller is an outer Docker container; container loopback is not physical-host loopback, and no cross-platform constrained host-gateway route is frozen. Section 7.1 also says the Fastify server starts only when bound to loopback, while §2 describes separate web assets and server services with only the UI port published; a server bound to its container loopback is unreachable from a separate web/reverse-proxy container.
5. **Must-fix — local-source immutability and SSH isolation are not enforceable as drawn.** Section 3.4 records and rechecks the exported snapshot, but does not re-hash/re-status the supplied local source after assessment as AC-2 requires. The launcher registration contract for `sourceHandle` is absent. In addition, Git intake is drawn as a separate trust zone with intake-only SSH access, but §2 defines no intake process/service and says `apps/server` is the one control-plane process; a bind mount visible to that process is not intake-only.
6. **Must-fix — package layout and sequencing conflict with the approved PLAN.** Section 2 substitutes `packages/db`, `assessment`, `provider-adapters`, `tool-adapters`, and `runtime-policy` for PLAN's `persistence`, `analyzers`, `runtime`, and `agent-adapters`, without amending ownership. Milestone 1 then starts backend and frontend implementation in parallel with DevOps, while PLAN requires P4 to own the full scaffold, package manifests, and lockfile before P5/P6. Shared schemas and imports will churn across lanes.
7. **Must-fix — run output escapes the required run root.** Section 2 places SQLite, backups, and registrations under `state/`; §9.4 keeps raw provider transcripts and operational logs outside the deliverable without saying they remain under the run directory. The brief requires all run output beneath the single `generated/...` root. The architecture neither defines a narrow installation-state exception nor inventories, retains, and deletes out-of-root run data.
8. **Should-fix — the modernization decision contract is too generic.** Section 4.2 says only “common criteria,” and `decision_factors` stores a non-numeric weight class without enumerating recoverability, boundaries, security/engineering risk, critical parity, scale, and rebuild feasibility or specifying how conflicting/unknown factors affect recommendation confidence. Backend reasoning, provider prompts, validation, and reports can use different decision semantics.
9. **Should-fix — provider-home isolation has no engagement lifecycle.** Section 3.7 promises engagement-scoped homes, but `POST /runs` has no engagement identity, there is no engagement API, and no component owns home creation, permissioning, rotation, closure, retention, or deletion. Convenient login reuse can therefore become cross-customer session/config leakage.
10. **Should-fix — operational cleanup is incomplete for a high-volume local tool.** The spec allows 20 GiB per run and retains immutable attempts, outboxes, backups, snapshots, ledgers, and provider homes, but exposes no retention preview, safe run deletion, reference-counted CAS cleanup, disk-capacity preflight API, or recovery for partial non-VM deletion.
11. **Nice-to-have — defer additive MVP surface.** Optional age wrapping, optional telemetry, optional hosted-service plumbing, and the broad dynamic-runtime stack should remain versioned capability seams until immutable intake, complete static assessment, evidence review, and validated ZIP succeed through both real providers.

## Concrete fixes

1. Freeze a provider `AssessmentJob`/`AssessmentOutcome` contract and attempt-scoped read surface: role, required domains/outputs, admitted evidence/finding/control/claim bundle or paginated reads, sensitivity filtering, context/size limits, prompt/instruction digests, session/resume token, timeout/signal mapping, and normalized provider failure. Add golden equivalence fixtures for every role.
2. Choose an implementable worker model. Either stream a content-addressed snapshot subset into a worker-owned tmpfs and stream its closed outbox back over a framed protocol, or introduce a narrowly privileged launcher that creates per-attempt containers. Specify peer authentication, quotas, cancellation, object integrity, and cross-run isolation; do not claim dynamic mounts on fixed services.
3. Publish the runtime-policy corpus in P1: exact supported/rejected Compose and Dockerfile constructs, canonical resolution order, generated-project rules, build-context handling, image pinning, network/DNS/redirect enforcement, browser/HTTP method safety classes, resource injection, and negative fixtures.
4. Add explicit egress-gateway and one-use secret-delivery components/contracts, including process location, trust boundary, mTLS identity, destination/IP rebinding defenses, byte/time budgets, revocation, log redaction, restart behavior, and evidence emitted for every allow/deny decision.
5. Freeze and spike the real deployment routes before implementation: browser-to-web-to-API topology, container bind addresses, physical-host-to-container authentication, and outer-container-to-host-broker transport on representative macOS and Linux hosts. Retain the full four-host matrix as the release gate.
6. Define launcher contracts for local-root registration and post-run source integrity. Separate SSH Git intake into an actual least-privilege process if it is to own the SSH mount, and specify submodule/LFS behavior, concurrent source mutation detection, before/after digests, and failure evidence.
7. Reconcile repository paths and milestones with PLAN: preserve its P4/P5/P6 ownership or amend PLAN explicitly; assign one owner to every package and privileged component; publish allowed import directions; and prohibit backend/frontend implementation until P4 has created manifests and the lockfile.
8. Put all run-scoped SQLite/backups/logs/transcripts/registrations under the run root, or define an explicit installation-state exception with run IDs, inventory, retention, cleanup, and AC-8 evidence proving that undeclared run artifacts cannot become customer output.
9. Freeze the exact modernization criteria and factor semantics, and add deterministic validation that all three options use the same criteria, evidence/unknown handling, confidence rules, and reversal conditions.
10. Add engagement/provider-home and storage lifecycle APIs/runbooks: create/close engagement, allocate/reuse/delete home, disk preflight, backup retention, safe run deletion, CAS reference cleanup, and interrupted-cleanup recovery.
11. Sequence the smallest complete product first: immutable intake, discovery, fixed static assessment, provider reasoning/review, evidence admission, decision comparison, redaction, and validated ZIP through both providers. Gate runtime and optional services behind their already-defined blocked-capability contract until the feasibility spikes pass.

## Verdict

**revise.** It clears the bar for evidence-integrity direction, resumability, and honest limitation handling, but misses the P1 freeze bar: the provider path is functionally incomplete, worker isolation is not implementable as specified, runtime policy remains undefined, and deployment/ownership seams would force security and contract decisions into parallel build lanes.
