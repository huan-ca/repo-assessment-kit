# Architecture Contender 3 — Scorecard

## Scores

- **Requirements coverage — 7.7/10.** The requirement trace, discovery vocabulary, three-option criteria, static/runtime paths, and package inventory cover most Musts concretely. However, `POST /runs` hard-codes `profileId:"rak-export-profile/1.0.0"` and provides no baseline/overlay selection contract for AC-7; `.rak/` stores operational run data outside the brief's required `generated/<project>-<commit>-<timestamp>/` root; and packaging is made contingent on technical and lay approval for every run even though the research requires those as release-readiness reviews, not engagement-by-engagement manual completion.
- **Hostile-repository isolation — 8.5/10.** “No component receives a capability merely because another component needs it,” fixed no-shell analyzer workers, compiled rather than passed-through Compose, default-deny runtime egress, and a mount-free VM are strong. The score is capped because the secret path from the no-network credential broker to a VM recipient is only described as a “sealed envelope” and never specified, while the host-helper UDS transport and peer/authentication mechanics remain feasibility gates at the most privileged boundary.
- **Source immutability — 8.8/10.** Commit export, separately identified approved dirty-tree snapshots, refusal to scan the live tree, path/symlink collision checks, and before/after integrity are rigorous. The remaining gap is operational: the text says “the launcher registers an allowed root,” but no launcher, API, or host-protocol contract creates or resolves `sourceRootId`; working-tree “declared exclusions” also lack a strict approval and coverage schema.
- **Cross-agent equivalence — 7.8/10.** Provider-neutral jobs, separate engagement homes, schema-bound proposals, common deterministic validation, and an equivalence harness are the correct direction. Yet the spec never freezes a role-by-role matrix of mandatory inputs, assessment domains, outputs, limitation behavior, and provider termination mapping, so both adapters can satisfy `AssessmentJobResult` while producing materially different coverage.
- **Evidence integrity — 7.7/10.** The one-way quarantine-to-staging pipeline, seven-label provenance, materiality rules, standards projections, and reopened-ZIP verification are excellent. But section 1 says native JSON is canonical, section 5 says SQLite is not canonical, and section 5.3 admits recovery from RAK JSON only “where available”; no durable canonical-document commit or atomic boundary ties admitted files, SQLite indexes, check results, and events together. The architecture therefore lacks a single recoverable source of truth despite claiming one.
- **Resumability — 7.4/10.** Persist-before-dispatch, leases, input digests, attempt tokens, secret-loss behavior, orphan reconciliation, and staging rebuild are useful. The run diagram is not a complete guarded transition table, `failed` is called terminal while also transitioning to `queued`, provider session resume is not represented in the job command, and the host protocol does not contain the enumerate/inspect operations that startup reconciliation explicitly requires.
- **Portability — 6.3/10.** Multi-architecture artifacts and an explicit native four-host gate are honest. Nonetheless, the design depends centrally on mounting a host-created UDS into the outer Docker sandbox, a signed Node SEA, Lima/rootless Docker, `better-sqlite3` on Node 24, Claude unattended operation, and ARM64 browser support; all remain unproved, and the spec itself calls several of them “architecture freeze” or release blockers without a frozen fallback other than reduced runtime coverage.
- **Build-lane contracts — 5.8/10.** HTTP tables, a substantial data model, and several DTOs help, but the proposed repository layout directly conflicts with PLAN ownership: P5 owns `packages/persistence`, `analyzers`, `runtime`, and `agent-adapters`, while section 3 instead creates `db`, `analyzer-adapters`, `runtime-policy`, and `provider-contract`, plus unassigned `apps/credential-broker`, `apps/provider-bridge`, `host/rak-host`, and `runtime/broker`. No package dependency direction is supplied, and source-root registration, secret-envelope transfer, broker responses/errors, reconciliation, and admitted-evidence download are missing at cross-lane seams.
- **Operability — 6.7/10.** Loopback-only launch, resource ceilings, safe-failure behavior, audit, local metrics, backups, cancellation, and package diagnostics are thoughtful. Operators still have no specified path to install/verify/upgrade/rollback `rak-host`, register local roots or known-host records, invoke emergency stop outside the failed control plane, manage retention across every storage class, or package a run without two separate human approvals.
- **Simplicity — 5.3/10.** The single Fastify writer and static-first vertical slice are good choices, but the MVP simultaneously freezes four apps, roughly seventeen shared packages, a signed host executable, two custom framed protocols, a secret broker, disposable analyzer containers, a VM broker, a Compose compiler, two provider adapters, twelve canonical documents, multiple standards projections, optional encryption, and mandatory per-run human gates. Much isolation complexity is justified, but the spec neither aligns it to implementable ownership nor carves out the smallest complete static release before committing to all additive subsystems.

## Overall

**7.2/10.** The security direction is strong and the document demonstrates deep requirements understanding, but under a simplicity/buildability lens it is not a frozen architecture: it expands the implementation graph beyond the approved lane boundaries, leaves critical inter-process contracts unfinished, and bases the control plane on multiple unproved portability assumptions.

## Strongest objection

**Must-fix: section 3's repository placement makes the approved parallel build plan unexecutable.** PLAN assigns P5 an explicit, disjoint set—`apps/server`, `packages/contracts`, `workflow`, `persistence`, `evidence`, `analyzers`, `runtime`, `agent-adapters`, `reporting`, and `packaging`—and says P4 owns the scaffold and shared manifests. Contender 3 replaces several of those names and adds `apps/credential-broker`, `apps/provider-bridge`, `packages/domain`, `db`, `host-protocol`, `provider-contract`, `analyzer-adapters`, `runtime-policy`, `profiles`, `validation`, `host/rak-host`, and `runtime/broker` without assigning implementation ownership or an import/dependency direction. These are not leaf utilities: they contain the state machine, database, provider seam, privileged host protocol, secret boundary, and runtime policy. P4/P5/DevOps/runtime lanes would have to renegotiate paths and shared ownership after architecture freeze, invalidating the plan's claim that parallel outputs are disjoint and concentrating merge and contract churn in the highest-risk modules.

## Other findings

1. **Must-fix — the privileged protocol cannot implement flows the architecture requires.** Section 3.6's exhaustive operation list has no `sourceRoot.register/resolve`, known-host registration, secret-envelope staging/redeem, worker/VM enumeration, inspection, or reconciliation operation. Yet sections 2.1–2.2, 3.5, and 4.3 depend on all of them. The shown request says the MAC covers a “monotonic nonce,” but the envelope has no nonce field, and no response/error schema is defined. Implementers must add security-sensitive authority ad hoc.
2. **Must-fix — AC-7 has no configuration surface.** Section 7.3 accepts only `profileId:"rak-export-profile/1.0.0"`; sections 5–6 model profiles and applicability but expose no way to list, recommend, preview, select, version, or combine a baseline and overlay. Frontend and backend cannot implement the required operator-configurable framework overlay from this contract.
3. **Must-fix — canonical persistence and crash atomicity are unresolved.** Section 1 calls RAK JSON canonical, section 5 calls SQLite operational, and section 5.3 can rebuild only from admitted JSON “where available.” Sections 2.4, 3.10, and 9.2 do not define the commit order or recovery protocol across an admitted object rename, canonical JSON update, SQLite evidence/derivation rows, check/control completion, and event append. A crash can leave conflicting “truths.”
4. **Must-fix — host-to-container transport is an unretired architecture risk.** Sections 1.3 and 3.6 require the outer Docker container to reach a host-side Node SEA through a mounted Unix-domain socket on all four macOS/Linux architecture pairs, while Milestone 0 says to prove that path only later. No TCP/mTLS or other constrained fallback exists if Docker Desktop cannot carry the socket semantics. Since Git intake and every analyzer/VM operation depend on this channel, failure blocks more than dynamic runtime.
5. **Must-fix — per-run human approval is an unjustified requirement escalation.** Section 7.6 rejects packaging until technical and lay reviews are approved, and section 11 calls both human gates. The research synthesis requires human review for production release readiness, while the brief requires generated packages to complete without manual completion of core content. This design turns a validation exercise into a mandatory two-person workflow for every assessment and prevents unattended end-to-end completion.
6. **Must-fix — operational run data violates or at least ambiguously weakens the output-root contract.** Section 3 places the DB, workspaces, and cache under `.rak/`, and section 5.3 places backups there, although the brief says “Store all run output beneath `generated/<project>-<commit>-<timestamp>/`.” The spec never distinguishes installation state from run artifacts rigorously or defines how orphaned quarantine/workspace data is associated with and purged alongside a run.
7. **Should-fix — the lifecycle contract is not executable.** Section 4.2 is an abbreviated diagram rather than a complete transition table. It calls `failed` terminal while allowing `failed -> queued`, omits explicit error transitions from validation/package states, and does not define durable satisfaction of `waiting-input`. UI, workflow, and persistence lanes can disagree even if each follows the prose.
8. **Should-fix — cross-provider equivalence is only schema-level.** `AssessmentJob` identifies a role and one `requiredOutputSchemaId`, but the architecture lacks a closed matrix mapping each role to required assessment domains, minimum evidence/limitation outputs, materiality obligations, prompts/instruction digests, resume behavior, and normalized CLI failure states. The common harness is named, not specified.
9. **Should-fix — the review UI cannot retrieve pre-package evidence content.** Section 7.5 says evidence binary content uses the artifact endpoint, but section 7.6 permits artifact download only for customer-stage/final artifacts. Findings/evidence review occurs before packaging, so the only documented UI path can fetch metadata but not admitted screenshots, logs, or evidence bodies needed for review.
10. **Nice-to-have — defer additive surfaces behind a static release boundary.** Milestone 3 already identifies a static-only validated package as the first vertical slice. Optional age wrapping, hosted-service approvals, the disposable runtime, ZAP fallback, broad readability linting, and per-engagement human workflow can be separately versioned modules after both providers produce the complete static package.

## Concrete fixes

1. Reconcile section 3 with PLAN before freeze: either use the approved P5 paths or amend PLAN explicitly. Publish one owner per app/package/top-level directory and a permitted import/dependency graph; nominate a single contracts owner and a serialized process for schema changes.
2. Freeze complete host and runtime protocols, not just operation names: request/response/error envelopes, nonce and replay state, peer authentication, size/time limits, idempotency, version negotiation, object namespaces, and crash reconciliation. Add narrow operations for source-root/known-host registration, sealed-secret delivery, and tagged resource enumerate/inspect without adding arbitrary paths or commands.
3. Add a versioned assessment-profile API: list pinned baseline/overlays, expose signal-based recommendations separately, preview planned controls and disclosures, select baseline plus overlays before `ready`, and bind the exact profile digest to run/job/export identity.
4. Choose and document one durable canonical source of truth. Define a crash-safe admission transaction that durably writes the content-addressed object and canonical RAK document, atomically indexes it and finalizes check/control/event state, and reconciles every possible crash point on startup.
5. Prove the host-helper transport and `better-sqlite3` path before interface freeze on at least representative macOS and Linux hosts, then retain the full four-host matrix for release. If the UDS path fails, amend the architecture to a constrained authenticated transport before dependent lanes start.
6. Make technical/lay review a release-certification gate and an optional per-engagement approval workflow unless the product owner explicitly promotes it to every-run acceptance. Deterministic package validation and required independent model review should remain mandatory.
7. Put all run-scoped operational state under the run root, or define a strict installation-state exception with run IDs, inventory, retention defaults, cleanup graph, and acceptance evidence proving that no undeclared run artifact remains outside `generated/`.
8. Replace the lifecycle sketch with a machine-readable transition table shared by server, UI, and tests. Cover every state, command, guard, durable side effect, failure destination, retry/new-revision rule, secret loss, cancellation, and packaging recovery.
9. Freeze a provider-role conformance matrix and add a permissioned admitted-evidence content endpoint with sensitivity-aware rendering/download rules so the UI and backend lanes can implement review independently.
10. Establish a smaller release sequence: complete immutable intake, discovery, static analyzers, evidence admission, decision synthesis, redaction, and validated ZIP through both providers first; keep the VM runtime behind the already-defined blocked-capability contract until its feasibility gates pass.

## Verdict

**Revise.** It clears the bar for a serious isolation and evidence strategy, but misses the freeze bar for simplicity and parallel buildability. The module graph must be reconciled with PLAN ownership, privileged protocols and canonical persistence must be completed, and unproved portability dependencies must be retired before implementation lanes can proceed without expensive contract rework.
