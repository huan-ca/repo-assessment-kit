## Scores

- **Requirements coverage — 9.2/10.** §1.2, §§3–11, and the package inventory cover discovery, static and gated runtime assessment, dedicated security, decision support, exact provenance/status vocabularies, both launchers, and customer packaging with unusually little hand-waving; the main uncovered Must-level mechanism is secure delivery of approved sandbox credentials from the outer no-network broker to the in-VM runtime.
- **Hostile-repository isolation — 8.0/10.** The capability matrix, disposable acquisition/analyzer workers, compile-not-pass-through Compose policy, mount-free VM, rootless daemon, guest firewall, no-socket probes, and bounded parsers are strong. However, §§2.2 and 3.3 do not define how an authenticated VM recipient redeems a secret across the broker's local UDS, while §2.1 says the host broker receives only a “sealed envelope”; absent an attested key/channel protocol, implementation must either expose plaintext to the host helper or invent a critical security boundary.
- **Source immutability — 9.0/10.** §3.5 explicitly avoids scanning the live tree, distinguishes commit and working-tree snapshots, disables hooks/filters/LFS/submodules by default, rejects hostile path objects, content-addresses the manifest, and performs before/after checks. The weak point is §8.2's rule that any post-snapshot live-tree change fails package validation: it cannot distinguish assessor mutation from legitimate operator activity and therefore proves drift, not causation.
- **Cross-agent equivalence — 8.7/10.** §§3.4, 6, 11, and Milestone 4 put both providers behind one job/schema/domain/package acceptance contract and correctly reject byte identity. The `AssessmentJob` contract does not freeze the provider-neutral instruction/workflow digest or declared context-selection policy, so two adapters can satisfy the same output schema while being given materially different evidence and assessment intent.
- **Evidence integrity — 8.8/10.** §§2.4, 6, 10, and 11 specify quarantine, bounded parsing, native canonical documents, derivation/provenance, deterministic materiality gates, redaction, JCS manifesting, post-ZIP reopening, and a detached digest. Integrity still depends on an incompletely specified immutable-object store/admission transaction, and the manifest's “special entries without self-referential size/digest” need an exact schema to avoid divergent implementations.
- **Resumability — 7.4/10.** §§4.2–4.3 and 9.2 give durable transitions, input digests, leases, retry classes, cancellation, startup reconciliation, atomic artifact writes, DB backups, and immutable packaged runs. But the host protocol in §3.6 has no durable broker-side command/effect ledger or duplicate-request result semantics; a crash after `vm.create`, `worker.run`, or `vm.stageSnapshot` takes effect but before the server records the reply can repeat or orphan privileged effects despite the assertion that side effects are idempotent.
- **Portability — 7.6/10.** The architecture is honest about native images, static-only degradation, and four-host release blockers, and puts Lima, Chromium, ZAP/fallback, the Node SEA, Claude, and `better-sqlite3` in Milestone 0. Nonetheless those are feasibility hypotheses, not demonstrated portability, and the signed-SEA distribution/trust model is not specified for macOS Gatekeeper/notarization, Linux signature verification, upgrades, or rollback.
- **Build-lane contracts — 8.2/10.** Repository ownership, public HTTP/SSE contracts, tables, schemas, milestones, and acceptance gates allow substantial parallel work. Security-critical internal contracts remain incomplete: credential-recipient authentication/key exchange, host-command replies/error/replay semantics, object-transfer protocol, evidence-admission commit boundary, and provider context/instruction digesting would still be negotiated by backend, runtime, and security lanes.
- **Operability — 8.0/10.** §8.2, §9, and Milestone 7 define safe failures, bounded resources, local metrics, structured logs, audits, cancellation, cleanup, backup/restore, and measurable latency. Privacy operations are under-specified: §9.3 says retention is operator-configured and homes are removed only when selected, but provides no safe default or deletion state machine across quarantine, admitted evidence, staging, ZIPs, SQLite/WAL/backups, provider homes, VM disks, caches, and secret-bearing crash remnants.
- **Simplicity — 6.2/10.** The single Fastify writer and static-first vertical slice are disciplined, but the MVP still commits to a signed host executable, multiple typed brokers, a custom credential service, content-addressed stores, Lima/rootless Docker/firewall/proxying, Compose compilation, nine analyzers, two model adapters, twelve native documents, three projections, human gates, and optional encryption. Much is justified by the hostile-repository promise, but optional age support and broad first-release scanner/runtime breadth enlarge the critical surface before foundational handoff and crash semantics are proven.

## Overall

**8.1/10.** The architecture is strong on requirements mapping, source capture, hostile runtime containment, canonical evidence, and honest capability degradation. It is not ready to freeze because two non-functional claims are still aspirational at precisely the privileged boundaries: secrets cannot yet be transported to the VM under the stated capability matrix, and at-least-once workflow dispatch lacks crash-safe idempotency at the host-effect executor.

## Strongest objection

**Must-fix — the sandbox-secret path in §2.1 “Capability matrix,” §2.2 “Credential compartments,” and §3.3 “Credential broker” is not a realizable security protocol.** The broker is explicitly “no network” and exposes `RedeemSecret` only over a local mode-`0600` UDS, but the intended runtime recipient is the broker inside a separate Lima VM. The host helper is said to receive only a “sealed envelope,” yet the spec defines no VM-broker key generation, attestation, public-key binding to `{runId, recipient, VM identity}`, anti-replay channel, transport operation, or acknowledgement/revocation semantics. `attestationNonce` is merely a field, not authentication. The component that can reach both sides is the high-value `rak-host` helper; unless a real end-to-end scheme is frozen, implementers will either let it see plaintext, make the credential broker reachable over a new network edge, or invent incompatible handoffs. That breaks the explicit least-capability claim and the Must requirement to use only explicitly supplied sandbox credentials without leaking them.

## Other findings

1. **Must-fix — privileged side effects are not crash-idempotent (§3.6, §4.3, §9.2).** The MAC/nonce prevents stale authenticated messages but does not deduplicate a successfully executed request after a lost reply. Neither `requestId` nor job/attempt/output IDs are tied to stable host resource names and a durable broker result record. Startup enumeration can find orphans, but that is cleanup, not exactly-once observable semantics, and it does not prove whether a completed analyzer or staged snapshot should be reused.
2. **Must-fix — the egress contract promises HTTP enforcement the design does not implement (§2.3, §3.8, ADR-003).** A runtime exception names scheme and HTTP methods, while the stated enforcement is nftables, an internal Docker network, and a proxy. IP filtering cannot enforce method or scheme, and an ordinary HTTPS CONNECT proxy cannot inspect them without TLS interception and a target trust policy. DNS rebinding, private/link-local/metadata denial, proxy bypass, direct-IP use, IPv6, and certificate handling are also not frozen. The contract must distinguish enforced network properties from operator-declared purpose.
3. **Must-fix — credential-recipient authentication is asserted rather than specified (§3.3).** “Authenticated declared recipient” and `attestationNonce` have no identity/key lifecycle, peer-credential rule, socket-sharing topology, or compromise behavior. Even within the outer sandbox, a process that can reach the UDS may be able to claim another recipient unless the broker binds OS/process/container identity independently of request JSON.
4. **Must-fix — source drift is conflated with source mutation (§3.5, §8.2).** The package fails if a live local source changes after an immutable snapshot, despite assessment components having only read access. This can block a valid long-running assessment because an operator continued development. Snapshot fidelity and assessor non-mutation should be proved independently; later external drift should be recorded as a limitation unless the assessed snapshot itself is inconsistent.
5. **Must-fix — provider equivalence does not bind inputs tightly enough (§3.4, §11).** `AssessmentJob` references artifacts and an output schema but not the exact provider-neutral instruction bundle digest, control/domain plan digest, context-selection algorithm/version, or truncation record. The same acceptance matrix can therefore validate two runs whose providers were given different material evidence, weakening the “same assessment intent” claim.
6. **Should-fix — the host-helper trust chain is incomplete (§1.1, §1.3, §14).** “Signed Node 24 SEA” does not say who verifies the signature, which key is trusted, how macOS notarization/quarantine and Linux verification work, how helper/protocol/image compatibility is enforced, or how downgrade/rollback is prevented. Because `rak-host` controls host Docker and Lima, this cannot remain a distribution detail.
7. **Should-fix — retention and privacy cleanup lack a complete object inventory (§2.2, §5.3, §9.3).** Engagement homes persist until explicit cleanup; DB backups persist per packaged run; quarantine may contain raw discovered secrets; and the spec gives no default retention, purge ordering, interrupted-cleanup recovery, or verification that VM disks and caches no longer hold sensitive data.
8. **Should-fix — package-manifest recursion needs a normative schema (§10.2).** “Special entries without self-referential size/digest” is sensible but ambiguous about exactly which fields are omitted, whether `manifest.json` declares itself, and how `SHA256SUMS` is represented. Independent packager and validator lanes need golden bytes/fixtures, not prose, for this integrity boundary.
9. **Nice-to-have — reduce pre-proof MVP surface (§10.2, ADR-010, ADR-011).** Optional age wrapping and the full nine-tool scanner suite create licensing, native-binary, update, normalization, secret-handling, and fixture burdens. The architecture should preserve adapters while sequencing optional encryption and lower-value analyzers after the credential, host-effect, and four-host proofs.

## Concrete fixes

1. Define a versioned end-to-end `SecretDelivery` protocol before freezing the runtime boundary: VM-broker ephemeral key generation, identity/attestation evidence, key binding to run/VM/recipient/purpose, authenticated encryption, monotonic use counters, expiry/revocation, acknowledgement, tmpfs injection, zeroization limits, and crash behavior. Add canary tests proving the control plane, host helper, other workers, target siblings, logs, and packages cannot recover the secret.
2. Give `rak-host` a fsynced command/effect journal keyed by a stable command ID and immutable input digest. Derive worker/VM/object names from that ID; define `accepted/effect-created/completed/compensated` states, duplicate-call replies, response retention, and reconciliation after server/host/DB crashes. Run crash injection at every boundary.
3. Rewrite runtime-endpoint policy into enforceable layers. Specify DNS resolution/pinning and rebinding defenses, IPv4/IPv6 and private/metadata denial, proxy routing that cannot be bypassed, TLS CONNECT versus interception behavior, and which fields are advisory. Do not claim HTTP-method enforcement for opaque TLS.
4. Split local-source validation into: immutable snapshot correctness, proof that assessment mounts never had write capability, and observed live-source drift. Fail only capture inconsistency or evidence of assessor mutation; report unrelated post-capture drift without invalidating the frozen snapshot package.
5. Add `instructionBundleDigest`, `assessmentPlanDigest`, `contextPolicyVersion`, selected/omitted artifact IDs with reasons, byte/token limits, and truncation outcomes to `AssessmentJob` and its acceptance harness.
6. Specify recipient authentication for every broker connection using OS peer credentials or per-workload cryptographic identity independent of caller-supplied fields; document socket mount topology and deny behavior after worker replacement/restart.
7. Add a signed-artifact trust/update ADR for `rak-host`, VM images, and protocol compatibility, including verification before execution, key rotation, rollback protection, macOS notarization expectations, and Linux install verification.
8. Add a retention/purge state machine with conservative defaults and an enumerated graph covering DB/WAL/backups, quarantine, admitted objects, staging, packages, provider homes, VM disks, worker outboxes, caches, and logs. Record incomplete deletion and disclose where secure erasure cannot be guaranteed.
9. Publish the exact manifest JSON Schema and golden package fixtures, including self/special entry rules, path-byte ordering, `SHA256SUMS` grammar, tamper cases, and fresh-process validation.

## Verdict

**revise.** Contender 3 clears the bar for detailed architecture, requirement traceability, hostile source/runtime modeling, evidence rigor, and parallel build planning. It misses the ship bar because the runtime credential flow cannot currently satisfy its own capability matrix and because host-level effects are not durably idempotent across crashes. Those boundaries must be frozen and adversarially testable before implementation.
