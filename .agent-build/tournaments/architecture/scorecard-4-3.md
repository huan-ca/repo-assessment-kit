## Scores

- **Requirements coverage — 8.0/10.** Sections 3, 4, 7, and 8 cover nearly every Must with explicit components and gates, but §8.3's mandatory ZIP inventory omits machine-readable coverage and limitations despite AC-5/AC-8, and the discovery topics and three-option criterion matrix are asserted rather than enumerated in a frozen contract.
- **Hostile-repository isolation — 8.8/10.** The mount-free Lima boundary, compiled/rejected Compose features (§7.3), fixed no-network analyzer commands (§3.2), and credential matrix (§7.1) are unusually rigorous; however, the acquisition helper/secret broker are not specified as components or protocols, and §13.4 concedes that a provider handling credentials while interpreting hostile context remains a material residual risk.
- **Source immutability — 8.4/10.** §4.1 correctly distinguishes commit-only from a frozen dirty-tree snapshot, hashes paths/content, avoids scanning the live tree, and performs before/after comparison; it still leaves the export/acquisition algorithm, race handling, submodule/LFS treatment, and failure semantics to implementers.
- **Cross-agent equivalence — 7.3/10.** §3.1 and §10 correctly define equivalence through one adapter protocol and one acceptance harness rather than identical prose, but `AgentTask`/`AgentOutcome` are prose field lists and the promised “required domain/artifact matrix” is absent, so the central equivalence oracle is not actually frozen.
- **Evidence integrity — 8.3/10.** §8.1 supplies a strong one-way admission pipeline, provenance, immutable evidence, redaction, and fresh ZIP verification; §8.3 does not require `data/coverage.json` or `data/limitations.json`, and §8.4's exceptional manifest entries (“omit self-referential size/hash”) need exact schema/verification semantics before independent implementations can agree.
- **Resumability — 6.8/10.** Leases, attempt preservation, idempotency, cancellation, and startup recovery in §4.3 are solid, but §4.2, §4.1, and the revisions API disagree about when a new revision is created, while `runs` uses the ineffective uniqueness constraint `(project_slug, revision, created_at)` and `derived_from_revision` has no unambiguous parent identity.
- **Portability — 6.9/10.** The architecture is honest about native-platform gates and isolates architecture-sensitive pieces, but the host executor/Lima bootstrap, UDS provisioning, guest image delivery, and prerequisite ownership are unspecified, while four-host runtime, Claude, SQLite, Chromium, and ZAP feasibility all remain open release blockers (§13).
- **Build-lane contracts — 5.9/10.** §2.2, §10, and §11 identify packages, fixtures, and sequencing, but §3.1, §3.2, §3.3, §5.3, and §6.2 mostly name contracts without defining their schemas; moreover, “P5 owns the server and shared packages” (§2.2) conflicts with six supposedly path-separated backend lanes (§11), leaving dependency and edit ownership unresolved.
- **Operability — 7.5/10.** The API, SSE replay, health checks, recovery, failure modes, and audit signals are useful and concrete, but no component owns host-helper installation/upgrades, secret-handle lifecycle, database backup retention, disk-capacity preflight, or safe repair when migration/lock verification fails.
- **Simplicity — 5.8/10.** The static-first vertical slice and rejection of arbitrary plugins are good YAGNI choices, but the MVP still commits simultaneously to a plugin framework, 19 native schemas, eight static tools, a host executor, VM broker, two provider images, many report projections, optional hosted analyzers, and age wrapping before the highest-risk feasibility spikes are proven.

## Overall

**7.4/10.** Strong security architecture and evidence thinking, reduced by a substantial gap between the document's breadth and the contract completeness needed for independent build lanes.

## Strongest objection

The architecture declares itself normative and says the public schemas are “frozen before P5 and P6 begin” (§2.2), yet Milestone 1 is itself tasked with inventing those schemas. `AgentTask`, `AgentOutcome`, `EvidenceBundle`, `RuntimeCommand`, `RuntimeOutcome`, `RunSummary`, `RunDetail`, the discovery-topic vocabulary, and the cross-provider domain/artifact matrix are either prose lists, names, or not shown at all (§§3.1–3.3, 5.3, 6.2, 10–11). This is the highest-rework defect: provider, workflow, evidence, runtime, reporting, and frontend lanes cannot implement independently without making mutually incompatible decisions about cardinality, version negotiation, error semantics, sensitivity, materiality, and coverage completeness.

## Other findings

1. **Must-fix — run/revision identity is internally inconsistent.** §4.1 says revisions increment only after completed/packaged runs or immutable-input changes; §4.2 allows `failed -> draft (new revision)`; `/revisions` is described for “Complete/frozen input changes”; and the schema's `(project_slug, revision, created_at)` uniqueness does not prevent duplicate revisions. Resume, artifact-root selection, event replay, and freeze boundaries will diverge across persistence/API/workflow implementations.
2. **Must-fix — the customer package contract does not carry all canonical coverage data.** §5.3 names `coverage` and `limitation` schemas, but §8.3 omits corresponding machine-readable files. A prose coverage report and `data/controls.json` cannot reliably satisfy AC-5's machine-checkable scope, exclusions, limitations, blocked checks, and untested areas.
3. **Must-fix — privileged/helper boundaries have nouns but not lifecycle contracts.** The component table names source intake and host executor, while §7.1 introduces an “acquisition helper token” and “ephemeral broker” without defining who creates them, where they run, how handles expire/revoke, or how the UDS is authenticated and permissioned. Those are security-critical build decisions, not local implementation detail.
4. **Must-fix — the lock/profile contracts required by the research synthesis remain deferred.** §7.2 lists `toolchain.lock.json` fields and §8.2 lists standards, but neither freezes full schemas, digest-verification failure behavior, update cadence, compatibility/migration rules, or profile pinning for resumed/completed runs. Milestone 1 therefore still has policy decisions hidden inside implementation.
5. **Should-fix — parallel ownership contradicts itself.** §2.2 assigns all shared packages to P5, while §11.3 divides those same packages among six “path-separated lanes.” Without one owner per package plus declared dependency direction, the proposed parallelism creates schema churn and merge contention at precisely the boundaries it claims to freeze.
6. **Should-fix — delivery risk is concentrated too late.** The four-host VM/runtime, real Claude path, SQLite native driver, ARM64 browser, and ZAP proof appear in Milestone 7 or §13, after substantial framework work. These are reversal conditions from the research synthesis and should be short, early feasibility gates before building generalized adapters and projections.
7. **Nice-to-have — trim secondary MVP surfaces.** Optional hosted analyzer behavior (§3.2), scrypt/X25519 UI handling (§6.2), cross-run revision capacity targets (§9.1), and broad observability metrics (§9.3) can follow the safe static package slice unless an acceptance criterion specifically exercises them.

## Concrete fixes

1. Add normative JSON Schema excerpts or field tables for every cross-lane DTO, including required/optional fields, enums, cardinality, version negotiation, error/outcome mapping, limits, and canonical fixtures. Include the exact discovery-topic list, assessment-domain/control matrix, required artifact matrix, and modernization criteria.
2. Define one revision aggregate: state whether a revision is a row under a stable assessment ID or a new run, give it a real uniqueness key such as `(assessment_id, revision)`, identify its parent explicitly, and align state transitions, API paths, filesystem roots, freeze rules, and resume behavior.
3. Add `data/coverage.json` and `data/limitations.json` to the mandatory ZIP inventory, require security-domain filtering/links in machine-readable findings, controls, evidence, and review data, and freeze the manifest/SHA special-entry schema plus verification order.
4. Specify acquisition-helper, secret-broker, and host-executor deployment/lifecycle contracts: process owner, UDS path/mode/authentication, token creation and expiry, crash cleanup, upgrade compatibility, allowed source roots, and failure evidence.
5. Freeze `toolchain.lock.json` and `standards-lock.json` schemas and policies now, including digest/signature verification, offline behavior, update cadence, compatibility, profile versioning, and immutable-resume rules.
6. Replace the broad P5 ownership statement with a package ownership/dependency table. Assign one schema owner and require contract changes through reviewed versioned fixtures rather than “no lane changes a contract unilaterally.”
7. Move thin feasibility spikes for `better-sqlite3`, real Claude unattended/resume, host-executor/Lima lifecycle on at least one macOS and one Linux architecture, and ARM64 browser image availability ahead of framework implementation; retain the full four-host matrix as the release gate.
8. Defer optional hosted analyzers and optional encryption UX until the static-only local assessment produces a validated package through both real provider adapters, unless the product owner explicitly promotes them to release acceptance.

## Verdict

**revise.** It clears the bar for trust-boundary direction and evidence strategy, but misses the bar for a frozen, parallel-buildable architecture because the most important contracts and revision semantics still require implementers to make hidden product and security decisions.
