## Scores

- **Requirements coverage — 8.5/10.** The requirement-to-component map and package inventory cover nearly every Must, including the ten discovery topics, six control states, three-option decision, separate security review, blocked runtime, and both launch paths; however, the promised “fixed required domain matrix” and ecosystem-specific depth/unsupported rules are not actually enumerated.
- **Hostile-repository isolation — 8.0/10.** The provider/analyzer/host/VM separation, default-deny resource matrix, generated restricted Compose project, and offline runtime are strong, but the security-critical protocol still exposes `BridgeRequest.payload: object`, `BridgeResponse.result?: object`, and a broadly parameterized `runtime.call`; the claim that no downstream lane can add an unsafe capability is therefore not yet enforceable from this spec.
- **Source immutability — 8.8/10.** Commit-only versus explicit frozen-working-tree semantics, deterministic manifests, read-only snapshots, and before/after attestations are unusually concrete; the remaining weakness is that the exact export algorithm, symlink/submodule handling, Git object-format validation, and behavior when an operator independently changes the live tree during a long run are left to implementation.
- **Cross-agent equivalence — 7.5/10.** The shared phases, schemas, acceptance gates, and provider-specific adapters correctly define outcome equivalence rather than byte identity, but the provider phase-output schemas, exact `rak-source`/`rak-evidence`/`rak-job` command contracts, and equivalence comparator are only named, not frozen.
- **Evidence integrity — 7.9/10.** The quarantine-to-staging flow, derivation model, release gates, and ZIP reopen algorithm are strong, but most canonical RAK documents are only inventory rows rather than complete contracts, while digest representations vary between bare strings and `sha256:`-prefixed values; that leaves semantic and serialization choices open.
- **Resumability — 6.7/10.** Jobs have attempts, leases, idempotent dispatch, immutable admission, and package replay, but the state model contradicts operations: phase/job states omit `waiting` while bridge loss says jobs are “waiting,” `failed -> running` has no explicit recovery action or preconditions, accepted actions return an `actionId` with no retrieval contract, and VM/runtime reconciliation after restart is unspecified.
- **Portability — 7.2/10.** Multi-arch pinning and explicit release blockers are honest, but Node SEA distribution/update/verification, Lima installation and privilege prerequisites, browser fallback selection, and native-host launcher behavior remain gates rather than frozen operational architecture; the four-platform promise is therefore plausible, not yet implementation-ready.
- **Build-lane contracts — 6.0/10.** Ownership seams and milestone ordering are explicit, but the spec says Milestone 0 will “Create RAK 1 schemas, OpenAPI, bridge protocol schemas, fixed phase/control catalog,” even though P1 is required to freeze those before P2/P3/P5/P6. The partial API tables, three TypeScript shapes, and open protocol payloads cannot safely serve as parallel-lane contracts.
- **Operability — 6.9/10.** Loopback bootstrap, opaque handles, failure behavior, emergency stop, quotas, logging, and package visibility are good operator-facing choices, but there is no complete launcher/supervision/update flow, action-status API, orphan inventory/reconciliation algorithm, storage-pressure workflow, or precise SSH-handle selection for `POST /runs`.
- **Simplicity — 7.0/10.** A modular monolith, SQLite, SSE, fixed analyzers, and no generic plugin system are appropriate simplifications, and the VM boundary is justified by the threat model. Still, fourteen focused packages, multiple canonical projections, a host SEA, a VM broker, and mandatory dual human sign-off create substantial operational surface; the spec does not identify a thinner first vertical slice that preserves release safety while retiring uncertainty early.

## Overall

**7.5/10.** The architecture has a sound high-level security shape and excellent requirement mapping, but it misses P1’s implementation-ready contract-freeze bar. The weighted result emphasizes simplicity and buildability: those are precisely where deferred schemas, generic privileged payloads, and inconsistent recovery states create expensive downstream coordination.

## Strongest objection

**Must-fix — the spec calls itself schema-first while deferring the schemas and control catalogs that P1 exists to freeze.** In **“Canonical RAK 1 contracts,”** the table gives prose inventories and **“Key canonical shapes”** defines only `ControlResult`, `EvidenceEntity`, and `Finding`; it does not freeze the actual JSON shapes and semantic rules for target snapshots, discovery/assertions, provenance activities/agents, tool invocations, coverage/limitations, decisions/factors, artifacts, manifests, or export profiles. In **“Internal protocols,”** the privileged bridge is still typed as `payload: object` and `result?: object`. Most decisively, **“Milestone 0 — Freeze contracts and fixtures”** says to later “Create RAK 1 schemas, OpenAPI, bridge protocol schemas, fixed phase/control catalog, policy profiles.” That work is an explicit P1 deliverable, not a P4/P5 implementation task. If frozen as written, safety and design specs plus backend/frontend/DevOps lanes must invent the missing fields, transitions, and error semantics independently, defeating the plan’s contract-first dependency structure.

## Other findings

1. **Must-fix — recovery semantics are internally inconsistent.** **“Fixed phase graph”** limits phase/job states to `pending | leased | running | succeeded | failed | cancelled`, while **“Availability and failure modes”** says bridge loss will “Mark dispatched jobs waiting.” **“Run state machine”** permits `failed -> running`, but `RunAction` provides no `recover` action or failed-resume conditions, and the spec does not define how a surviving Lima VM, rootless daemon, or broker operation is discovered and reconciled after control-plane/bridge restart. This can produce duplicate target execution or orphaned privileged resources.
2. **Must-fix — the narrow host-control guarantee is asserted more strongly than it is contracted.** **“Host bridge protocol”** allows `payload: object`; `runtime.call` carries a generic `operation`, `inputArtifactIds`, `policyId`, and approvals without operation-specific request/result schemas. The bridge and broker are the highest-privilege interfaces in the system, so “IDs resolve through bridge-owned registrations” is not enough to prove that a later artifact type or policy cannot become an arbitrary image, Compose document, destination, environment, or file path.
3. **Must-fix — the cross-agent contract is too abstract to test equivalence.** **“Provider job contract”** supplies a generic `requiredOutputSchema`, but the actual phase schemas, command exit/error taxonomy, read/search limits, evidence-view semantics, retry/session rules, and equivalence comparison algorithm are absent. “Same schema/domain-equivalent outputs” in Milestone 3 cannot be implemented consistently from this document alone.
4. **Must-fix — source acquisition is ambiguous for SSH and complex Git trees.** `POST /runs` accepts an SSH URL/ref but no SSH handle, while `snapshot.acquire` has optional `sshHandleId?`; the spec does not say how multiple registered keys/configs are selected. **“Run and target identity”** also does not specify submodule inclusion, Git LFS placeholders, sparse checkouts, case/Unicode collisions, special files, symlink targets, or export failures, all of which affect the assessed identity and first-class ecosystem fixtures.
5. **Must-fix — static coverage is promised but not frozen.** **“Complete static assessment”** relies on a “fixed required domain matrix,” and **“Static analyzer jobs”** lists tools, yet no domain/control catalog maps the seven first-class ecosystems to required techniques, degraded modes, unsupported versions, or analyzer failure effects. Two providers could therefore pass the same structural schema while delivering materially different assessment depth.
6. **Should-fix — accepted asynchronous actions have no observable lifecycle contract.** **“Actions”** returns `actionId` and `state:"queued"`, but there is no action resource, status endpoint, event type contract, or terminal error retrieval. UI and operator recovery behavior will otherwise depend on polling the run and guessing which action failed.
7. **Should-fix — contract duplication and type errors undermine freeze confidence.** `ControlState` repeats `"pass" | "fail" | "partial" | "blocked"`; **“One-way artifact flow”** and **“Milestone 0/1”** are duplicated. Hash fields alternate between plain strings and examples such as `"sha256:..."`, and `byteLength` is a string without a canonical integer-string rule. These are not merely editorial in a schema-centric design: implementers will encode different wire formats.
8. **Should-fix — simplicity is described mainly as rejected infrastructure, not bounded MVP work.** **“Repository and deployable layout”** introduces numerous packages before contract fixtures exist, and **“Milestone 0”** combines schemas, OpenAPI, bridge protocols, control catalogs, policy profiles, two architecture spikes, and four host SEA spikes. A smaller contract/evidence vertical slice and an explicit critical-path spike order would reduce simultaneous uncertainty and make failure cheaper.
9. **Nice-to-have — source-integrity failure is over-broadly defined.** The host bridge compares the live source “before and after export/assessment” and any change is a failure, although the assessment uses an already frozen snapshot. The spec should distinguish a kit-caused mutation (a safety violation) from an operator-caused later edit (an attestation mismatch/limitation) rather than necessarily failing an otherwise immutable snapshot run.

## Concrete fixes

1. Move Milestone 0’s contract creation into the architecture deliverable: append or reference complete versioned JSON Schemas, OpenAPI, phase/control catalog, bridge/broker protocol schemas, policy-profile schemas, and positive/negative fixtures. Downstream milestones should implement frozen artifacts, not create them.
2. Replace every `object`/generic privileged payload with a discriminated, operation-specific closed schema. Define exact allowed IDs and artifact kinds, resolved lockfile fields, destination rules, limits, response/error codes, size limits, idempotency semantics, and policy-validation order for each bridge and runtime operation.
3. Repair and formally tabulate run, phase, job, action, runtime, admission, and package states with allowed transitions, triggers, guards, terminality, retry safety, and restart reconciliation. Add an action-status/read API and define VM/broker orphan discovery plus exactly-once cleanup behavior.
4. Freeze provider command semantics and every phase input/output schema, then define equivalence as a deterministic matrix comparison over required domains, controls, provenance/evidence rules, coverage reasons, and package inventory. Include fixtures where one provider omits or mislabels a required domain.
5. Define the immutable export algorithm for Git URL and local-handle inputs, including SSH-handle selection, submodules, LFS, symlinks, special files, dirty/untracked content, Unicode/case collisions, size limits, and external live-tree changes.
6. Publish the seven-ecosystem assessment/control matrix with baseline tools, expected outputs, unsupported/degraded states, coverage effects, and minimum substantive-result gates. Make this catalog part of the shared acceptance harness.
7. Normalize wire types and remove duplicates: use one canonical digest representation, specify safe integer/string encoding for byte counts, fix `ControlState`, and eliminate repeated sections before declaring version `1.0.0`.
8. Re-sequence the first implementation slice so contract fixtures, SQLite/Drizzle proof, and one typed dummy bridge/evidence-admission flow retire the riskiest assumptions before the full package graph and four-host release matrix expand.

## Verdict

**Revise.** It clears the bar for a strong architecture direction and threat-boundary proposal, but it misses the required ≥8/10 critic threshold and, more importantly, P1’s “implementation-ready, no downstream invention” gate. Freeze the missing canonical and privileged-interface contracts, reconcile lifecycle recovery, and tighten the first build slice before selecting it as the tournament winner.
