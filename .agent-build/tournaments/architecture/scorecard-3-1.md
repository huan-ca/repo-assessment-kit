# Architecture Contender 3 — Scorecard

## Scores

- **Requirements coverage — 8.2/10.** The requirement-to-component trace and package inventory cover nearly every Must, but the public run contract hard-codes `profileId:"rak-export-profile/1.0.0"` and exposes no assessment-profile/overlay selection even though AC-7 requires an operator-configurable framework overlay; operator/customer documentation is also only named as release work, not contracted.
- **Hostile-repository isolation — 8.3/10.** The spec earns credit for treating repository content, Compose, scanner inputs, provider output, and web content as malicious; for fixed no-shell/no-network analyzers; and for putting dynamic execution behind a mount-free disposable VM. However, the most privileged broker interface omits required source and secret flows, and dynamic evidence is admitted without a defined trust downgrade if the explicitly acknowledged “guest-kernel or hypervisor escape” residual occurs.
- **Source immutability — 9.0/10.** “Never scan the live tree,” commit export, separately identified approved working-tree snapshots, collision/symlink rejection, and before/after live-tree checks are strong. The remaining weakness is that “declared exclusions” for working-tree capture lack a schema, authorization rule, and mandatory coverage projection, leaving room for an operator or implementation to omit material content without a uniform contract.
- **Cross-agent equivalence — 8.4/10.** `AssessmentJob`, schema-bound proposals, separate provider homes, identical deterministic validators, and a common acceptance harness correctly define equivalence as outcomes rather than byte identity. The exact role-to-required-output/domain matrix and adapter lifecycle/error mapping are deferred to Milestone 1/4 rather than frozen here, so two lanes can still implement nominally valid but materially different assessment workflows.
- **Evidence integrity — 8.5/10.** The one-way quarantine/admission/staging flow, canonical RAK documents, materiality rules, independent review, JCS manifest, checksums, and reopened-ZIP verification are strong. The spec does not define an atomic admission commit protocol tying filesystem object durability to SQLite indexing, and evidence returned from a potentially compromised runtime VM has no explicit origin trust level or corroboration requirement.
- **Resumability — 8.0/10.** Persist-before-dispatch, immutable input digests, leases, attempt tokens, startup reconciliation, lost-secret behavior, and staging rebuild are credible. But the state diagram is not a complete transition table with guards, and the missing atomic job-output/admission protocol leaves crash windows where an outbox/object, evidence row, check result, and event can disagree.
- **Portability — 7.2/10.** Multi-architecture images, native VM images, Node SEA distribution, and the four-host matrix are explicit. Still, Lima/rootless Docker, the signed SEA, Claude, Linux ARM64 browser support, and `better-sqlite3` are all unproven release blockers; “Architecture is sound” in the risk table overstates what is currently established for the required platform promise.
- **Build-lane contracts — 6.8/10.** The data model, HTTP surface, provider job shape, component ownership, sequencing, and package contract offer substantial parallel-build guidance. The host boundary—the highest-risk integration seam—is internally incomplete: the allowed operation list has no operation for launcher registration of a local `sourceRootId`, no secret-envelope stage/redeem operation for the VM, no defined result/error envelope, and a MAC said to cover a “monotonic nonce” that is absent from the shown message. These omissions force backend, host, and runtime lanes to invent security-critical protocol behavior.
- **Operability — 7.8/10.** Loopback launch, capabilities, structured failures, audit, cancellation, orphan cleanup, backup/restore, resource limits, and local metrics are strong. Distribution/update/rollback and signature verification for `rak-host`, host prerequisites/installation, provider-home retention safeguards, and operator recovery from a broken host helper are not specified beyond “refuse new work.”
- **Simplicity — 6.4/10.** A single Fastify writer and static-only vertical slice are sensible simplifications, but the MVP still commits to a custom signed host binary, two UDS protocols, a secret broker, multiple worker types, a disposable VM control plane, a custom Compose compiler, many canonical documents, numerous workspace packages, and mandatory human gates. Much is justified by the threat model, but the spec does not isolate a smaller release slice or prove that each custom subsystem is necessary for the first customer-ready static package.

## Overall

**7.9/10.** The architecture is correctness-oriented and substantially better than a generic “agent in Docker” design, but it is not ready to freeze because its most sensitive cross-boundary contracts are incomplete and one Must-level configuration path is missing.

## Strongest objection

**Must-fix: the host capability boundary is conceptually narrow but contractually incapable of carrying required workflows.** Section 3.6 says the only operations are `worker.run/cancel` and `vm.preflight/create/stageSnapshot/inspectRuntime/acquireBuildInputs/build/start/probe/collectEvidence/stop/destroy/emergencyStop`, and insists there is no generic path or file-copy operation. Yet section 3.5 says “the launcher registers an allowed root” so the API can send `{sourceRootId,relativePath}`, while sections 2.1–2.2 say the host broker stages a sealed runtime-secret envelope into the VM. Neither local-root registration/resolution nor secret delivery/redeem appears in the protocol. The shown envelope also omits the “monotonic nonce” that its MAC allegedly covers. This is not documentation polish: backend, launcher, host-helper, credential-broker, and runtime lanes cannot implement the Must-level local-path and sandbox-credential flows without independently adding capabilities at the highest-privilege seam, creating both integration rework and an isolation regression.

## Other findings

1. **Must-fix — AC-7 has no API/configuration contract.** Section 7.3 accepts only `profileId:"rak-export-profile/1.0.0"` on `POST /runs`; sections 6.4 and 5.2 model framework applicability and controls, but no endpoint or config selects baseline plus overlays, versions them, previews their controls, or records triggering signals. Consequence: the UI/backend lanes cannot build the required configurable overlay flow consistently.
2. **Must-fix — evidence admission is not crash-atomic.** Sections 2.4, 3.10, and 9.2 say admitted objects are immutable and writes use `fsync` plus atomic rename, but they never specify the order/idempotency contract across object rename, SQLite `evidence`/derivation rows, check/control finalization, and durable event append. A crash can produce an orphan object, dangling index, duplicated admission, or a succeeded check whose evidence was never committed.
3. **Must-fix — state semantics are prose, not an executable transition contract.** Section 4.2 shows an abbreviated diagram, while sections 4.3, 7.3, 7.6, and 8.2 introduce additional guards and failure behavior. It is unclear which phase can transition the run to `failed`, whether `validation`/`packaging` failure may resume under the same run despite “require operator action or a new revision,” and how `waiting-input` requirements are durably satisfied. Separate UI, API, and workflow implementations can disagree.
4. **Should-fix — runtime evidence trust is under-modeled.** Section 8.1 acknowledges guest-kernel/hypervisor escape, but sections 3.8–3.10 admit broker output like other evidence and section 6.2 lacks an origin trust/attestation strength field. A hostile workload that compromises its disposable guest cannot reach the host package, but it can potentially forge observations later presented as “observed.” The evidence contract should preserve that distinction and require corroboration for decision-critical runtime claims.
5. **Should-fix — cross-provider equivalence stops one level too early.** Section 3.4 defines a generic job/result and section 11 names a matrix gate, but does not enumerate per role the mandatory inputs, output schema, assessment domains, minimum evidence/limitation outputs, retry classification, or adapter normalization of CLI termination states. Schema validity alone does not ensure equivalent coverage.
6. **Should-fix — working-tree exclusions are under-governed.** Section 3.5 permits “declared exclusions” but does not say which paths may be excluded, whether the operator must approve them, whether excluded byte/file counts are evidenced, or how they affect workflow/parity/security coverage. This weakens the otherwise strong source-identity story.
7. **Should-fix — host-helper supply-chain and lifecycle contracts are incomplete.** Sections 1.3 and 14 call `rak-host` “signed,” but do not define who signs it, how launchers verify it, how versions/protocol compatibility are negotiated, or how upgrade/rollback works across four native binaries. A compromised or mismatched helper owns Docker and Lima.
8. **Nice-to-have — simplify the initial delivery boundary.** Milestone 3 already identifies a static-only package as the first vertical slice, but section 12 still freezes most VM, browser, encrypted-package, readability, and human-review contracts before that slice. Explicitly separating a release-capable static core from the additive runtime module would reduce coordinated surface without weakening blocked-runtime honesty.

## Concrete fixes

1. Publish complete strict schemas for host requests and responses, including explicit nonce/replay state, peer authentication, size limits, error codes, object namespaces, and idempotency. Add narrowly scoped operations for `sourceRoot.register/resolve`, acquisition result transfer, and `vm.stageSecretEnvelope` (or document a safer equivalent), with recipient attestation and zero generic path/copy semantics.
2. Add a baseline/overlay profile contract and API: list supported pinned profiles, preview planned controls and applicability disclaimers, select baseline plus overlays at run creation or before `ready`, record signal-based recommendations separately from operator-confirmed selection, and bind the selected profile digest into run/job/package identity.
3. Define evidence admission as a recoverable transaction protocol: content-addressed temporary object, verified durable rename, idempotent SQLite transaction for artifact/evidence/derivation/check state/event, startup orphan reconciliation, and explicit behavior for every crash point.
4. Replace the run diagram with a machine-readable transition table shared by domain, API, and UI. Specify source state, command, guards, side effects, destination, retryability, and recovery for every transition, including validation/package failures and `waiting-input`.
5. Add `originTrust`, runtime attestation linkage, and compromise/collection limitations to evidence. Require separate corroboration or visible qualification before VM-originated evidence can support a material “observed” claim after any guest-integrity anomaly.
6. Freeze a provider-role matrix mapping each role to required inputs, exact output schema, mandatory assessment domains, limitation behavior, materiality obligations, adapter status mapping, and equivalence assertions.
7. Make working-tree exclusions a strict approved object with normalized paths/rules, counts/digests, rationale, immutable inclusion in `target.json`, and deterministic coverage/limitation effects.
8. Add a host-helper distribution ADR covering signed artifacts, trust roots, launcher verification, version/protocol negotiation, upgrade/rollback, installation prerequisites, and recovery when helper/database/runtime versions disagree.

## Verdict

**Revise.** It clears the bar for a defensible isolation strategy and evidence architecture, but misses the freeze bar for correctness and contracts: two Must-level privileged data flows are absent from the broker protocol, framework-overlay configuration is not exposed, and crash-atomic evidence admission is unspecified. Fix those seams before downstream lanes build against this spec.
