## Scores

- **Requirements coverage — 8.5/10.** The phase DAG, package inventory, six-state control model, dedicated security review, decision records, and shared launcher acceptance harness cover nearly every Must; however, §5.2 leaves `decision_options.criterion results` open-ended instead of freezing the brief's required common criteria, and §5.3 invokes “materiality” without an enforceable definition.
- **Hostile-repository isolation — 7.5/10.** §7.3 gives the hostile runtime a credible mount-free Lima/rootless-Docker boundary and rejects dangerous Compose features, while §3.2 gives static tools strong no-network/non-root controls; the uncontained gap is source acquisition itself, which is trusted but not given an isolated helper, safe Git command/config protocol, or adversarial transport rules.
- **Source immutability — 7.5/10.** §4.1 correctly distinguishes commit-only from frozen dirty-tree assessment, records a deterministic manifest, avoids scanning the live tree, and compares before/after source state. It does not specify the atomic export algorithm, protection against source mutation during capture, safe handling of Git filters/hooks/submodules/LFS/alternates, or verification that exported bytes correspond to the resolved commit/snapshot rather than merely to their own post-copy manifest.
- **Cross-agent equivalence — 9.0/10.** §3.1 and ADR-1 make schemas, required task kinds, domain/package gates, failure classifications, conformance fixtures, and the acceptance harness canonical across Codex and Claude; equivalence is appropriately outcome-based rather than byte-based. Event ordering, backpressure, and partial-output/resume semantics remain underspecified in `AgentEventSink`.
- **Evidence integrity — 8.5/10.** §8's quarantine → admission → immutable evidence → redacted staging flow, exact-version normalization, semantic validation, provenance, collision-safe packaging, fresh-process ZIP verification, and detached digest are rigorous. The spec still cannot deterministically enforce its promise that every “material” claim is linked because materiality and the closed set of decision factors are not defined, and SHA-256 provides no authorship (correctly disclosed).
- **Resumability — 7.5/10.** §4.2–4.3 provide CAS transitions, leases, immutable attempts, resume-context digests, cancellation intent, reconciliation, and startup recovery. “Requests are idempotent by `commandId`” is asserted without specifying the executor's durable effect ledger or the transaction boundary between an external VM/container effect and the stored response, leaving a crash window that can duplicate or orphan privileged work; SQLite restore also says to “replay” idempotent operations without defining a surviving journal.
- **Portability — 7.5/10.** Digest-pinned multi-arch artifacts, native-architecture execution, capability gates, static-only degradation, and explicit four-host release blockers are honest. The mandatory Lima/rootless-Docker/cgroup path, Linux ARM64 browser, Claude image, and `better-sqlite3`/Node 24 combination remain empirical blockers, so the architecture is not yet a demonstrated macOS/Linux ARM64/x86-64 contract.
- **Build-lane contracts — 8.5/10.** §2.2 assigns clear package ownership, §6 freezes a substantial HTTP/SSE contract, and §10 supplies shared fixtures before parallel work. Several security-critical internal contracts are only named—`TargetResolution v1`, `RuntimeCommand/Outcome v1`, ephemeral credential channel, executor authentication, and `AgentEventSink`—so independent lanes would still need to invent protocol fields and lifecycle semantics.
- **Operability — 8.5/10.** §9 supplies measurable latency/resource targets, bounded readers, structured safe logging, useful metrics, health semantics, failure responses, cleanup, and explicit static-only readiness. Retention/deletion is too vague for a system that quarantines secrets: no default or purge graph covers quarantine, admitted artifacts, SQLite rows, backups, provider homes, VM disks, and shared caches, and “recoverable through trash” can conflict with privacy deletion expectations.
- **Simplicity — 6.5/10.** The spec avoids arbitrary plugins and sequences a static vertical slice before runtime, but the MVP still introduces a control plane, privileged host executor, VM broker, Compose compiler, rootless daemon, two adapter families, many analyzers, 11 shared packages, native schemas, multiple projections, and optional hosted/encryption paths. Much is justified by the threat model, but optional hosted analyzers and age support increase first-release surface before the four central feasibility blockers are proven.

## Overall

**8.1/10.** This is a high-quality, unusually concrete architecture whose strongest portions are the runtime trust boundary, one-way evidence flow, explicit degradation semantics, and provider-neutral acceptance model. It misses the ship bar because the first hostile-input boundary—Git/local source acquisition—and privileged-effect idempotency are not specified with the same rigor as downstream execution.

## Strongest objection

**Must-fix: §3's `Source intake`, §4.1, §6.2 `POST /runs`, and §7.1 give a trusted acquisition component access to a hostile Git/local repository and opt-in SSH material, but never define how that component is contained or how Git is invoked safely.** “Resolves ... and exports” plus “local path canonicalized/allowlisted” is not a security contract. There is no acquisition-helper process/container boundary, fixed argv protocol, environment/config clearing, `GIT_CONFIG_NOSYSTEM`/hook/filter/fsmonitor disablement, protocol and URL allowlist, host-key policy, submodule/LFS/alternates behavior, archive/path limits, redirect handling, or rule for hostile local `.git/config`. A malicious input can therefore attack the trusted intake process before the read-only snapshot and analyzer isolation exist, potentially reaching the only phase permitted to use SSH material. This is the highest-leverage rework risk because all later isolation and evidence claims depend on the snapshot being safely and faithfully acquired.

## Other findings

1. **Must-fix — crash-safe external effects are asserted, not contracted (§3.2, §4.3, ADR-7).** `commandId` idempotency needs a durable executor-side state/effect record and explicit create/observe/commit/reconcile protocol. Otherwise a crash after VM creation but before response persistence can repeat creation, while a corrupted/restored SQLite database may not contain the records the recovery algorithm says it will replay.
2. **Must-fix — egress policy overclaims enforceability (§7.3).** Endpoint exceptions claim exact scheme/host/port/method/data-class policy, but a normal TLS proxy cannot enforce HTTP method or data class without trusted interception, and hostname allowlists are vulnerable to resolution changes unless addresses are pinned and private/metadata routes are continuously denied. The spec does acknowledge allowed-destination exfiltration, but it must distinguish enforced network properties from operator-declared purpose.
3. **Must-fix — deterministic evidence completeness has an undefined semantic escape hatch (§5.2–5.3, §8.1).** `decision_options` does not enumerate the brief's required criteria, and no rule defines a material finding or decision factor. A provider can omit an inconvenient factor and still satisfy schema/reference validation because the validator cannot detect what never entered the model.
4. **Must-fix — several contracts needed by parallel lanes are placeholders by name (§3.1, §3.3, §7.1).** `AgentEventSink`, `RuntimeCommand/Outcome`, `TargetResolution`, executor authentication/key lifecycle, and the credential broker's handle issuance/expiry/revocation are not specified enough for backend, runtime, provider, and QA lanes to implement independently.
5. **Should-fix — privacy lifecycle is incomplete (§9.2).** “Operator-configurable” retention and recoverable trash do not define secure purge behavior across quarantine, admitted evidence, staging, packages, backups, SQLite, engagement homes, VM images/disks, and caches. Defaults and deletion evidence are needed, especially when raw outputs may contain discovered secrets.
6. **Should-fix — source manifests need race semantics (§4.1).** Before/after equality proves the assessor did not leave a change in the common case, but not that files were stable throughout export. The algorithm needs a stable snapshot primitive or bounded re-read/retry rule and a clear failure/limitation outcome for concurrent mutation.
7. **Should-fix — the platform claim remains conditional (§13 risks 1, 2, 3, and 5).** The spec correctly labels the four-host runtime, Claude, SQLite, Chromium, and ZAP paths as blockers. Those empirical gates must occur before downstream implementation depends deeply on Lima or native modules, not only at Milestone 7.
8. **Nice-to-have — defer non-core extension surface (§3.2, §6.2, §8.4).** Hosted analyzer approval machinery and scrypt/age interactive-channel behavior are thoughtful but add contracts and test burden. Keeping the analyzer SPI while deferring hosted dispatch and optional encryption would reduce first-release failure surface without weakening a Must.

## Concrete fixes

1. Add a versioned `SourceAcquisitionCommand/Outcome` contract and a disposable, no-output-access acquisition helper. Define fixed Git argv, clean environment/config, hook/filter/fsmonitor/LFS/submodule/alternates policy, allowed URL schemes and SSH options, host-key behavior, redirect/size/path limits, timeout/resource limits, sanitized logging, and destruction of SSH-bearing state before evidence admission.
2. Specify a race-safe snapshot algorithm: resolve an object ID, export from the object database without checkout for commit-only mode, validate every archive/path entry, hash the resulting tree, and for working-tree mode use an atomic filesystem snapshot or repeated pre-copy/post-copy manifests until stable, otherwise return a documented `SOURCE_CHANGED_DURING_CAPTURE` failure.
3. Define executor-side durable command records with states such as `accepted/effect-created/completed/compensated`, stable resource names derived from `commandId`, fsynced result persistence, duplicate-request behavior, reconciliation sources of truth, and backup/restore semantics. Add crash-injection tests at every transition.
4. Split egress fields into enforced controls and declared purpose. Specify DNS resolution/pinning and rebinding defense, private/link-local/metadata route denial, proxy trust model, TLS behavior, and what cannot be inspected; never claim method/data-class enforcement unless the architecture actually terminates and validates that protocol.
5. Freeze a closed decision-criteria enum containing recoverability, boundaries, security risk, engineering risk, critical parity burden, expected scale, and rebuild feasibility. Define materiality deterministically (or require explicit reviewer classification) and validate that every criterion and every high-impact finding has an evidence/unverified/conflicting disposition.
6. Expand the named internal schemas with required fields, error taxonomies, ordering/replay/backpressure rules, credential-handle TTL/revocation/use-count semantics, protocol-version negotiation, and golden malformed/crash fixtures before parallel lanes begin.
7. Add a retention/deletion policy with safe defaults and an inventory-based purge state machine covering every storage class, including backups and failed/quarantined material; record deletion outcomes and disclose where secure erasure cannot be guaranteed.
8. Move the four-host Lima spike, real Claude conformance, SQLite driver test, and ARM64 browser validation ahead of deep runtime implementation. If a gate fails, invoke the stated architecture amendment before other lanes bake in the dependency.

## Verdict

**revise.** The contender clears the bar for requirements understanding, trust-boundary design after snapshot creation, evidence packaging, cross-agent equivalence, and operational thoughtfulness. It misses the ship bar on the uncontained hostile source-acquisition boundary and on crash-safe privileged-effect semantics; both must be frozen before implementation.
